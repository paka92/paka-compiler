# M4-44b · Where edit-to-running time goes

Measured with `paka-bench 5000 2` (M4-44) on a release build, with timers added around each phase
for the measurement only and not committed. Times are the mean per edit over 35 edits of all six
classes; the first run, which compiles the whole program, is left out. The classes differ by about
6 %, because the same whole-program work dominates each.

Edit-to-running time grows with the program, not with the edit: about 130 ms at 100 definitions,
1.4 s at 1,000 and 7.2 s at 5,000.

## 1. The split at 5,000 definitions

| Process | Component | Phase | ms |
|---|---|---|---:|
| server | checker | `Workspace::edit` checks every definition | 756 |
| server | database | `Session::located` splits every file to find the edited one | 152 |
| server | database | `failing`, `edited`, `installed`: scans and a copy of every file | 8 |
| server | transport | the load request written to the runner a few bytes at a time | 2,330 |
| runner | transport | the request parsed, the source assembled | 9 |
| runner | checker | `paka::check` of the whole program | 676 |
| runner | code generator | Cranelift IR built for every definition | 474 |
| runner | code generator | that IR printed as text for its key, 199 MB | 1,911 |
| runner | code generator | SHA-256 of that text | 728 |
| runner | code generator | compiling the definitions with a new key (one for most edits) | 4 |
| runner | installer | loading, a new record table, the slot swap | 22 |
| runner | run | the app | about 8 |
| | | total | about 7,080 |

The measured edit-to-running time is about 7,200 ms; the rest is the reply.

The transport line is the time `Live::ask` spends writing: it formats the `Value` straight into
the unbuffered pipe, and `Display` writes each piece separately, so a 4 MB request becomes millions
of system calls. One definition's IR is about 1,300 lines, most of them overflow and trap checks.

## 2. Fixes and expected gains

Gains are for 5,000 definitions and add up, since each removes a separate line above.

| # | Fix | Gain |
|---|---|---:|
| 1 | Format the runner request to a string and write it once. | 2,330 ms |
| 2 | Build IR only for definitions an edit can change: key each definition first by a cheap digest of its core form and the interfaces and layouts it reads, and keep the IR key for an unchanged digest. | 3,110 ms |
| 3 | Check only the definitions `Workspace::rechecked` names, reusing the rest of the last check. | 750 ms |
| 4 | Give the runner the edit, not the program: it holds its own `Workspace` and so checks as little as fix 3 does. | 670 ms |
| 5 | Index each definition's file in the session. | 150 ms |
| 6 | Keep the record table when layouts do not change; this also stops one table leaking per edit. | 20 ms |
| 7 | Keep the failing set and the runnable files up to date instead of scanning and copying. | 8 ms |

Fixes 1, 2 and 5 to 7 leave about 1.4 s, all of it checking; fixes 3 and 4 are needed to come
under 100 ms. After all seven the whole-program work left is the scans inside the incremental
check, which this profile does not split; M4-45 measures it again after each fix.

A cheaper key alone (hashing IR without printing it) would save only the 1,911 ms of printing,
and digests in fix 2 must cover everything the IR reads, or code goes stale; M4-43's edit
sequences with plants 6 and 7 are the check.

## 3. After M4-45

Fixes 1, 5, 6 and 7 are in. Fixes 2 to 4 are replaced by one narrower path: an edit that changes
one function's text and keeps its signature is checked alone in a small program, in the server and
in the runner, and only that function is compiled. `paka-bench 5000 3`, 95th percentile:

| Class | ms |
|---|---:|
| body-small | 20 |
| body-medium | 23 |
| body-large | 32 |
| signature | 5,091 |
| add | 5,003 |
| delete | 5,095 |

Signature, add and delete edits still take the whole-program path, and so does any edit with an
error. They are outside the gate; fixes 2 to 4 remain the way to speed them up.
