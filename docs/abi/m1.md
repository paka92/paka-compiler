# Paka M1 ABI

How compiled Paka code and the Rust runtime `paka-rt` share data and calls in milestone 1.
The runtime (M1-16, M1-17), the IR emitter (M1-18) and the build command (M1-19) are written from
this text. Its reference IR is [`light.ll`](light.ll), the hand-written IR of `examples/light.paka`.

Status: provisional. It follows the rulings of DECISIONS.md M1-14 and the run rules of
[`spec/m1.md`](../../spec/m1.md) section 9. M4-05 lays every type out afresh and rules which of
these points stay. Section 12 lists what this document had to settle on its own.

ABI version: **1**. The version is the number in the entry's name, `paka_rt1_run` (section 10).

## 1. Target and module header

- One target: x86-64 Linux with glibc. Words are 8 bytes, little-endian.
- The IR starts with `target triple = "x86_64-pc-linux-gnu"`. It has no `target datalayout` line:
  clang fills it in from the triple, and clang 21.1.8 prints nothing about it.
- That is safe only for M1's IR: it loads and stores nothing but `ptr` and `i64`, with the
  default alignments, which are the target's own. A later milestone that writes other types or
  an `align` must look at this rule again.
- rustc builds the runtime for `x86_64-unknown-linux-gnu`. The two triples name the same ABI.
  clang is given no `--target`: with one that differs from the module's triple it prints
  `warning: overriding the module target triple`.
- Both sides use the C calling convention. The IR names no other convention; Rust writes
  `extern "C"`.
- Everything runs on the thread that entered `main`. The runtime starts no thread.

## 2. Values

Every value is made of 8-byte words at 8-byte boundaries, so there is no padding.

| Value | Words | IR type | Meaning |
|---|---|---|---|
| message | 1 | `i64` | the variant's position in its enum, counted from 0 in declared order |
| string | 2 | `ptr`, `i64` | pointer to the bytes, number of bytes; no ending zero |
| effect | 3 | `{ i64, ptr, i64 }` | tag, pointer, length |
| effect list | 2 | `{ ptr, i64 }` | pointer to the first effect, number of effects |

The same shapes in Rust:

```rust
#[repr(C)] struct Effect { tag: u64, ptr: *const u8, len: u64 }  // 24 bytes, align 8
#[repr(C)] struct List   { ptr: *const Effect, count: u64 }      // 16 bytes, align 8
```

**Effects.** The tag is the effect's number. A field an effect does not use holds zero.

| Effect | Tag | Pointer | Length |
|---|---|---|---|
| `Print(text)` | 0 | the text's bytes | the text's byte count |
| `Exit` | 1 | null | 0 |

**Strings.** The bytes are the string's value exactly as the spec defines it (section 3 there). The
runtime treats them as plain bytes and never tells Rust they are valid UTF-8. A string of length 0
is written with a null pointer.

**Lists.** The effects lie one after another, 24 bytes each. An empty list is
`{ ptr null, i64 0 }`.

**Empty values.** A length of 0 or a count of 0 decodes to an empty slice that the runtime makes
itself. The pointer is not passed to Rust: `slice::from_raw_parts(null, 0)` is undefined, and a
build with debug assertions aborts on it. One check still looks at it: a list header whose
pointer is not a multiple of 8 is refused even when its count is 0 (section 7).

**Memory.** Every pointer compiled code hands over points at constants that live for the whole
process. The runtime only reads through them, never past the count or length it was given, and
never frees. There is no heap in the ABI: compiled code and the runtime share no allocator and no
ownership rule.

## 3. The update function

```llvm
define internal i32 @p_update(i64 %m, ptr %out)
```

```rust
type Update = extern "C" fn(msg: u64, out: &mut List) -> i32;
```

- `%m` is the message. There is no state argument and no context pointer.
- The function writes its result, one effect list, through `%out`, the last argument, and returns
  a 32-bit status: 0 = finished, 1 = trapped (M4-05 section 5).
- `%out` points at a 16-byte slot on the runtime's stack, 8-byte aligned. Compiled code writes
  exactly those 16 bytes through it, reads nothing through it and does not keep the pointer. That
  is what lets Rust type it `&mut List`, so a fake update in a test needs no unsafe.
- Before the call the runtime sets the slot to `{ null, 1 }`, a value its own decoder refuses, so
  a function that returns 0 without storing is an internal error and not an empty list.
- Status 1 is a trap when compiled code reported one first (below); any other status but 0 is an
  internal error (section 7).

This is the only function the runtime calls. Since M6-07 its body may run statements over `Int`
and `Bool` and call other compiled functions, each `define internal i32 @p_<name>(<args>, ptr
%out)` with the same statuses (`%out` only when the function has a result). Only the functions
`update` calls get IR. A trap calls the runtime, then returns 1, and every caller passes the
status on:

```llvm
declare void @paka_rt1_trap(ptr, i64) cold nounwind   ; text: <kind> at <file>:<line>:<col>
```

## 4. The entry and `main`

The IR owns `main`. The runtime exports one function:

```llvm
declare i32 @paka_rt1_run(ptr, i64, ptr, i64, i64)

define i32 @main() {
  %st = call i32 @paka_rt1_run(ptr @name, i64 5, ptr @p_update, i64 0, i64 1)
  ret i32 %st
}
```

```rust
#[unsafe(no_mangle)]
pub unsafe extern "C" fn paka_rt1_run(
    name: *const u8, name_len: u64, update: Option<Update>, start: u64, grants: u64,
) -> i32
```

The entry is `unsafe` because it reads through raw arguments: its caller promises what section 2
says about them.

| Argument | Meaning |
|---|---|
| `name`, `name_len` | the app's name, as a string |
| `update` | the function named by `update:`; null is refused and never called |
| `start` | the message named by `start:` |
| `grants` | one word of bits: bit 0 (value 1) is `Console`; any other bit set is refused. A program's other grants (`ReadFiles`, `WriteFiles`) are left out of the word: no effect this ABI carries needs them |

- `main` takes no parameters. The runtime reads the command-line arguments itself, from the
  operating system's list for the process, and only counts them: the start message of every
  program this ABI carries has no fields, so the count must be 0, else the usage stop (section 7).
  Delivering the arguments to compiled code is M4-05's.
- `main` returns what the entry returns, and that is the process status. The entry returns only
  0, 2, 3 or 4 (section 7).
- The runtime never calls process exit, so the C library shuts down normally when `main` returns.
- The runtime passes `start` to `update` unchanged; it cannot know the enum's size. The emitter is
  responsible for it.
- Rust's own start-up never runs, because `main` is not Rust's. What it would have done is either
  done by the entry or given up:

| Rust's start-up | Here |
|---|---|
| sets SIGPIPE to ignored | the entry does it, and SIGXFSZ too (section 6) |
| flushes standard output at exit | nothing to flush: `Print` writes to descriptor 1 itself (section 5) |
| reopens a closed descriptor 0, 1 or 2 on `/dev/null` | not done; a closed descriptor 1 makes `Print` fail (spec 9.5) |
| installs the stack-overflow handler that prints a message | not done; an overflow is a plain SIGSEGV. The M1 runtime does not recurse |
| names the main thread | not done; a panic message says `<unnamed>` |

## 5. What the entry does

In this order:

1. Sets SIGPIPE and SIGXFSZ to ignored (section 6).
2. Runs everything below inside `catch_unwind` (section 8).
3. Decodes the app name.
4. Refuses a `grants` word with any bit other than bit 0 set.
5. Refuses a null `update`.
6. Counts the command-line arguments after the program's name. When the count is not 0, stops
   with the usage line (section 7); nothing has been called or written. The count is made before
   the panic net of step 2 starts, and cannot panic.
7. Sets the result slot to `{ null, 1 }`, calls `update(start, &mut slot)` once, stops with the
   trap line on status 1 after a reported trap and refuses any other non-zero status.
8. Decodes the list header.
9. Takes the effects one at a time, in list order. For each: decode it, test its grant, perform
   it.
   - `Print`: when bit 0 of `grants` is 0, stop with the refused line. Otherwise write the text
     and one line feed to descriptor 1. A failure stops with the failed line.
   - `Exit`: return 0. The effects after it are not decoded, not tested and not performed.
10. When the list ends without `Exit`: stop with the ended line.

Decoding the app name (step 3) and taking the handles of the standard streams happen just before
the panic net of step 2 starts and cannot panic.

A refusal in steps 3 to 5 and 7 to 9 is an internal error. An effect is decoded only when its turn
comes, so what earlier effects wrote stays written, and nothing after an `Exit` is ever read.

**Writing.** All program output goes through one runtime function that returns the error instead
of panicking. The runtime never uses `println!` or `print!`, which panic on a failed write.

- The text and the line feed are one buffer handed to the operating system in one write. A short
  write is continued and an interrupted write is retried. Any other error, or a write that accepts
  no bytes, is a failure. (`write_all` on Rust's standard output does exactly this for a buffer
  that ends in a line feed.)
- The buffer goes to file descriptor 1 itself, through a handle the runtime owns, not through
  Rust's buffered standard-output stream: that stream reports success on a closed descriptor, and
  a closed descriptor must be a failed `Print` (EBADF, `write error`). Nothing is buffered, so
  nothing is left to flush when `main` returns, whatever way the program ends. The runtime takes
  the handle once, before the panic net starts; if the descriptor is closed there is no handle and
  every `Print` fails the same way.
- The buffer is the runtime's own temporary memory, private to it. This one reservation does not
  abort: when it fails, that is the internal error `out of memory`. An allocation Rust's library
  makes for itself (its standard-output handle, a panic's payload) aborts the process when it
  fails; that is outside M1.
- A line for standard error is written without allocating: its pieces (app name, `: `, the fixed
  texts, the line feed) are written to standard error in order. So reporting `out of memory`
  cannot itself abort. A failure to write the line is ignored and changes no status.

## 6. Signals

The entry's first action is `signal(SIGPIPE, SIG_IGN)` and then `signal(SIGXFSZ, SIG_IGN)`
(`SIGPIPE` = 13, `SIGXFSZ` = 25, `SIG_IGN` = 1), one hand-declared libc call behind one safe function
in paka-rt's unsafe module. The `paka` tool calls the same function before it interprets a program,
so `paka run` and an executable behave alike:

```rust
unsafe extern "C" { fn signal(signum: i32, handler: usize) -> usize; }
```

It installs no handler. A write to a pipe whose read end is closed then fails with EPIPE, and a
write past a file-size limit with EFBIG, both ordinary write errors, so the program never dies by
SIGPIPE or SIGXFSZ whether it was started with the signals ignored or not. The IR declares no libc
function and knows nothing about signals.

The runtime changes no other signal.

## 7. Statuses and standard-error lines

| Status | When |
|---|---|
| 0 | `Exit` was performed |
| 2 | the program was given a number of arguments its start message does not take |
| 3 | the program stopped: ended without `Exit`, an effect refused, an effect failed, a trap |
| 4 | internal error: the runtime or the compiled code is at fault, never the program |

Each stop writes one line and a line feed to standard error. `<app>` is the app name passed to
the entry. The first four lines are the spec's (sections 9.1, 9.3 to 9.5), copied byte for byte; the
interpreter prints the same ones and M1-20 compares them.

```
<app>: expected 0 arguments, got <n>
<app>: ended without Exit
<app>: effect Print refused: grant Console is missing
<app>: effect Print failed: <reason>
<app>: trap <text>
<app>: internal error: <reason>
```

The trap line is the first line of the interpreter's trap report (M2-06), with the text compiled
code passed to `paka_rt1_trap`. Release prints no detail or frame lines.

Reasons of a failed `Print`:

| Cause | `<reason>` |
|---|---|
| the write fails with ENOSPC (28) or EDQUOT (122) | `no space left on device` |
| the write fails with EPIPE (32) | `broken pipe` |
| any other failure | `write error` |

The internal-error line is this document's own. Status 4 appears in no expectation, so it always
fails a case. Its reasons, in the order the entry meets them:

| `<reason>` | When |
|---|---|
| `bad app name` | the app name is refused; `<app>` is then `?` |
| `bad grants` | a bit other than bit 0 is set in `grants` |
| `update is null` | `update` is null |
| `update returned a non-zero status` | the status of `update` is not 0, nor 1 after a reported trap |
| `bad effect list` | the list header is refused |
| `unknown effect tag` | an effect's tag is not 0 or 1 |
| `bad effect` | the text of a `Print` is refused, or an `Exit` has a non-zero pointer or length |
| `out of memory` | the output buffer cannot be reserved |
| `runtime panicked` | a panic was caught (section 8) |

**Refused inputs.** The runtime refuses, before reading through the pointer:

| Input | Refused when |
|---|---|
| string (app name, `Print` text) | length not 0 and pointer null; length above 2^63 − 1; length not 0 and pointer + length above 2^64 − 1, so a string whose last byte is at the last address is refused too |
| `grants` | any of bits 1 to 63 set |
| `update` | null |
| list header | pointer not a multiple of 8, whatever the count; count not 0 and pointer null; count above 384307168202282325 (more than 2^63 − 1 bytes of effects); count not 0 and pointer + 24 × count above 2^64 − 1, so a list whose last byte is at the last address is refused too |
| effect | tag above 1; tag 1 with a non-zero pointer or length |

A refused input is never read through, never called and never becomes a Rust slice.

## 8. Panics

- paka-rt keeps Rust's default unwinding panics; it is never built with `panic = "abort"`.
- The whole body of the entry after the SIGPIPE call runs inside `catch_unwind`, so nothing unwinds
  into compiled code. A caught panic gives the `runtime panicked` line and status 4. The line
  names the app; a refused name prints `?`, as in every internal-error line. Decoding the app name
  and taking the handles of the standard streams happen before the net and cannot panic.
- No panic hook is installed. Rust's own message, with file and line, stays on standard error and
  the internal-error line follows it.
- Compiled code cannot panic or unwind.

## 9. Building and linking

```
clang -O3 light.ll libpaka_rt.a -lgcc_s -lutil -lrt -lpthread -lm -ldl -lc -o light
```

- One clang 21 command compiles the IR at `-O3`, with no CPU flag (M6-02), and links. The linker
  is the system linker: no `-fuse-ld`, and no `--target` (section 1).
- `libpaka_rt.a` is paka-rt built by rustc as a static library (`staticlib`). The system libraries
  are the ones `rustc --print native-static-libs` names for it, in that order. rustc 1.96.1 on the
  build machine prints `-lgcc_s -lutil -lrt -lpthread -lm -ldl -lc`. A new rustc version means
  running that command again and updating this line.
- The executable is linked dynamically and needs `libgcc_s.so.1`, `libm.so.6` and `libc.so.6`
  at run time. `-static` is not supported in M1: the link fails for want of a static `gcc_s`.
- **No LTO, on either side.** paka-rt is built to machine code with no `lto` and no
  `-C linker-plugin-lto`; clang gets no `-flto`. rustc's LLVM 22 and clang's LLVM 21 cannot read
  each other's intermediate files, and keeping them apart keeps Rust's optimizer promises out of
  Paka code.
- A clean build prints nothing. A clang status other than 0 is the spec's `clang-failed`.

## 10. Version rule

Any change or addition to a layout, the tag numbers or the grant bits, and any change to the
signature of the update function or to the signature or meaning of the entry, renames the entry:
`paka_rt1_run` becomes `paka_rt2_run`, in the runtime, the emitter and this document together. A
new tag or grant bit counts: an older runtime would refuse it only at run time. A program linked
with a runtime library of another version then fails at link time:

```
undefined reference to `paka_rt2_run'
clang: error: linker command failed with exit code 1 (use -v to see invocation)
```

`paka build` reports that as `clang-failed`, status 1. Nothing is checked at run time.

## 11. IR text rules

The emitter's output for a program is `light.ll` without its first line, the comment, and with
these parts changed. The first line of emitted IR is the `target triple` line.

| Part | Rule |
|---|---|
| `@name` | the app's name, `private constant [N x i8]` |
| `@s0`, `@s1`, ... | one `private constant [N x i8]` per non-empty `Print` text, in list order. The numbers count the constants, not the effects: an empty text takes no number, so they run without a gap |
| `@fx` | `private constant [N x { i64, ptr, i64 }]` for the N effects of the list, N ≥ 1: `[` ends the first line, then one record per line in list order, each indented by two spaces and followed by `,` except the last, which is followed by ` ]`. Left out when the list is empty |
| `@p_update` | `internal`, named `p_` plus the function's Paka name; its body is its statements (section 3), then the one `store` and `ret i32 0` |
| the `store` | the whole record at once: `{ ptr @fx, i64 N }`, or `{ ptr null, i64 0 }` for an empty list |
| the call in `main` | name and its length, the update function, the start message's number, the grant bits |

- Every string byte is hex-escaped as `\` and two upper-case hex digits, printable or not.
- A `Print("")` is the record `{ i64 0, ptr null, i64 0 }` and has no `@s` constant.
- The type written in the `store` is exactly `{ ptr, i64 }`. A wider store through `%out` writes
  past the runtime's slot and cannot be seen at run time, so M1-18's test checks that type text.
- Pointers are the opaque `ptr`. There is no metadata and no `getelementptr`; the only attributes
  are those of the trap entry's declaration.
- No attributes is right only while every argument and result that crosses to the runtime is a
  `ptr`, an `i64` or the `i32` status; a `Bool` is an `i1` only between compiled functions. A
  value narrower than 32 bits crossing the boundary would need `zeroext` or `signext`, and this
  rule would have to change with it.
- Constants carry no `align`: the target's own alignment for `{ i64, ptr, i64 }` is 8 or more.
- The `p_` prefix keeps a Paka name from clashing with `main`, the entry or libc.
- None of these words appears anywhere in the IR, comments included: `nsw`, `nuw`, `inbounds`,
  `noalias`, `fast`, `nnan`, `ninf`, `nsz`, `arcp`, `contract`, `afn`, `reassoc`.
- `clang -c light.ll -o /dev/null` prints nothing.

## 12. Settled here

DECISIONS.md M1-14 leaves these open. Each is the smallest rule that lets both sides be written.

1. **Internal-error reasons.** The nine texts of section 7, and `?` for an app name that was
   refused. The decision fixes only `runtime panicked`.
2. **When an effect is decoded.** One at a time, when its turn comes, and before its grant is
   tested. So nothing after `Exit` is read, and a `Print` the runtime cannot decode is status 4
   even without `Console`.
3. **"No allocator".** Read as: none in the ABI. The runtime makes one private buffer per `Print`
   so that the text and its line feed are one write, as spec 9.2 asks.
4. **Other functions.** A function no app names gets no IR. The decision fixes the convention only
   for a function with an enum parameter, and no M1 program can call another one.
5. **The start number.** Passed to `update` unchanged; the runtime cannot test it.
6. **Arguments.** Counted by the runtime from the process's own argument list, with no change to
   the entry's signature; a built program with a start message that has fields is not buildable
   in M1 (`unsupported-form`), so the expected count is always 0 and the usage line has no field
   list. `tests/cases/parse/variant_payload` therefore passes on the interpreter, and `paka build`
   refuses it with `unsupported-form` until M4-05 delivers start fields. The grant word keeps its meaning: grants beyond `Console` are not passed because no
   effect of this ABI could use them.
