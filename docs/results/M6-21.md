# M6-21 · Release faults the generator reaches

Command, for each plant P: `PAKA_PLANT=P paka-diff --fuzz-release 0 1200 KEEP`, a release build of
`paka-diff`, the eleven runs (P = 0 and 9 to 18) side by side. Time is from the start of the run to
its first `differ` line, shrinking included. Without a plant, all 1,200 seeds agree: 1,091 compared
with release, 73 not compared (the interpreter ends in a stack trap), 36 refused by `paka build` for
a hole.

Each plant is a `sed` script run on the IR `paka build` hands clang (`RELEASE_PLANTS` in
installer/src/bin/paka-diff.rs), so the back end itself is untouched.

| Plant | Kind | What it does | Seed | Time |
|---|---|---|---|---|
| 9 | wrong comparison (M6-20) | `>` built as `>=` | 0 | 1 s |
| 10 | folded float operation | Float `+ - * /` marked `fast`, as if no value were NaN or infinite | 279 | 206 s |
| 11 | removed bounds check | the bounds check of a List index left out | 7 | 6 s |
| 12 | removed overflow check | the overflow check of checked arithmetic left out | 48 | 41 s |
| 13 | missed stack check after inlining | the stack check of each function small enough to inline left out | 4 | 4 s |
| 14 | wrong generic instance | `sort`'s Float instance built as its Int instance | 45 | 38 s |
| 15 | owned value dropped twice | each `paka_rt1_drop` call made twice | 0 | 1 s |
| 16 | wrong Map layout | a String-keyed Map row of word values laid out as an Int-keyed one | 1 | 1 s |
| 17 | removed shift check | the count check of a shift left out | 56 | 46 s |
| 18 | removed range check | the range check of `to_int` left out | 29 | 26 s |

No reference counts or stale handles exist (docs/decisions/M2-10.md), so plants 15 and 16 stand in
for those two kinds: an ownership fault and a layout fault of the runtime's values. Plants 17 and 18
are two more left-out checks.

## What the generator gained

- Recursive functions: a function calls itself on `p0 - 1` down to 0, or on `p0` for good past 100
  levels, which runs out of stack on every back end (plant 13). Depths between 101 and the stack
  limit are never made, as there the interpreter and release legitimately differ.
- Integer leaves at the overflow edges (`9223372036854775806`, `-9223372036854775807`,
  `3037000500`, `-3037000500`), so checked arithmetic overflows (plant 12).
- List reads near the end, `xs[len(xs) - k]` with k from 0 to 2, so a read just past the end is
  common (plant 11).
- Two more negative Float leaves, and the handler prints a sorted copy of some List results, so a
  sort of negative Floats is seen (plant 14).

## Coverage

A unit test in paka/src/llvm.rs (`generated_programs_build_in_release_with_every_kind`) builds the
IR of each generated program without a hole and lints it: of seeds 0 to 9,999, 9,707 built, none
refused, and together they hold every core-form node kind but a view's and a hole's. The rarest are
`Callee::Value` (366 programs) and `Compound::Float` (932). The other 293 have a hole, and
paka/tests/generated.rs checks `paka build` refuses each with `error[hole-in-build]` naming every
hole.

installer/tests/diff.rs finds plants 11, 13, 15 and 16 from their seeds above, each of which agrees
without the plant, and plant 9 from seed 0 as before.
