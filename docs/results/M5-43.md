# M5-43 · Visual edit loop timing

Command: `cargo build --release -p paka -p paka-installer`, then
`target/release/paka-bench --visual|--window ITEMS 50` (`installer/src/bin/paka-bench/visual.rs`).

Method: the bench serves the to-do sample of bench/ui/todo with the `paka` beside it, runs the
app, and fills it with ITEMS items through one click on Add with a temporary `add_item`. It then
makes 50 view-body edits (`todo_row`'s Row gap between 8 and 9) and 50 handler-body edits
(`add_item`'s cleared draft text), each timed from request written to reply read; by then the
new tree is built. `--visual` runs the app with no window, in the server, on the interpreter.
`--window` runs it in a window, in the dev runner, also on the interpreter, and times each view
edit to the `PAKA_FRAME_LOG` line of its presented frame. A handler edit leaves the tree as it
was, so no frame follows it. Every process of a run is pinned to one logical CPU, so the server,
runner and window share it. Before and after ran back to back, each size and mode in the same
minute; the before build is the sources at commit fc29295 with timing lines to standard error.

Machine: AMD Ryzen 9 3900X 12-Core Processor; kernel 7.0.0-38-generic; governor schedutil; boost
on; pinned to logical CPU 23.

## Where the time went, 10,000 items in a window

Before, per view edit: the window laid the tree out twice, about 205 ms each, nearly all in
shaping every text again; drew every node, about 160 ms, shaping again; and the runner wrote the
whole tree text into its install reply, and again into a `look_tree` the server sent before each
edit to learn whether the window was still open.

Changes:

- Text keeps each measure by text and wrap width, up to 65,536 before it drops them all
  (gui/src/text.rs). Layout of an unchanged 10,000-item tree takes about 4 ms.
- A window lays a tree out once for its width and scale, not again on the redraw that follows
  (gui/src/window.rs).
- Drawing skips a node whose rectangle starts past the image's right or bottom edge
  (gui/src/draw.rs): about 0.8 ms.
- An install builds no tree text; no install's caller reads it (paka/src/session/visual.rs).
- The server asks the runner `shows`, answered with a flag, in place of `look_tree`
  (paka/src/session/runner.rs, installer/src/bin/paka-runner.rs).

After, per edit at 10,000 items: the view run again on the interpreter, about 19 ms; copying the
state and keeping element state across the new tree, about 4 ms; writing and syncing the edited
file, about 4 ms; checking the program, 0.5 ms. In a window, also handing the tree to the window,
about 2 ms, and the `shows` request, about 2 ms, which also hands the tree over.
