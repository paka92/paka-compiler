# M4-05 · The dev-mode calling convention, trap returns and value layouts

Status: approved by the owner on 2026-10-15.

Base: no options page was recorded in DECISIONS.md; each point states the recommended choice, which
**stands**, and the options not chosen.

This page fixes how compiled dev-mode code calls, fails, lays out values and frees them. It builds on
M4-01 §7 (Cranelift 0.136.3), M4-04 (runner process, explicit checks, slot table), the M1 ABI
(docs/abi/m1.md, M1-14), M2-03, M2-05, M2-06, M2-09, M2-12, M2-14 and M2-15. All words are 8 bytes,
little-endian, x86-64 System V.

## 1. Crates

**Cranelift 0.136.3 (`cranelift-codegen`, `cranelift-frontend`) generates the code; the emitter is
safe code in `paka`, used only in runner mode. A new crate, `paka-installer` (M4-23), turns the bytes
into runnable machine code and holds the slot table and the calls into compiled code. The runtime's
unsafe code stays in `paka-rt`, inside its one unsafe module tree `abi`.**

- Why: `paka` stays `forbid(unsafe_code)`. The installer is the only unsafe code on the calling side
  (mmap, copy, mprotect, never writable and executable at once; transmute to a function pointer).
  The runtime's unsafe code (raw allocation, reading values through pointers from generated code)
  belongs with the runtime it serves, which release builds also link.
- Not chosen: **all unsafe in the installer** (M4-04's wording); the allocator and value walkers would
  then live apart from the runtime that release links. **`cranelift-jit`**: not vendored (M4-01 §7),
  and it pulls in more than the few lines the installer needs.

## 2. The dev runtime extends paka-rt

**The dev runtime is new modules in `paka-rt`, not a new crate. `paka_rt1_run` and the M1 modules
stay for the `paka build` path (§13).**

- Why: release (M6) links `paka-rt` as a static library; one runtime and one layout table serve both
  back ends, so M1-16 and M1-17 (one runtime crate, linked statically) hold unchanged.
- Not chosen: **a separate dev runtime crate**; release would need a second copy of the allocator,
  collections and effect performer, or a later merge.

## 3. What the interpreter shares

**The interpreter shares the effect performer (a new safe module `paka_rt::effects`) and the
existing layout-free routines in `paka_rt::ops` (Int, Float and text rows, per M2-03 §2.9 and
M2-14 §3). It shares nothing that touches native layout: allocator, collections, copy, release,
equality walkers, trap record and the native run loop stay native-only.**

- Why: the performer is where output, file and exit behaviour must match byte for byte; `ops` is
  already shared and takes plain Rust values. Native layout code works on raw words the interpreter
  never sees. The text rows in `paka/src/interp/text.rs` move into `ops` under M4-32.
- Not chosen: **the effect performer only**; it would undo the `ops` sharing M2-03 and M2-14 already
  record. **Sharing the collections**; the interpreter would have to build native layouts to call
  them.

## 4. The context pointer

**Every compiled function takes a context pointer `ctx` as its first argument. `ctx` points to a
`repr(C)` runtime struct whose first four words are fixed for generated code; the rest is private to
the runtime.**

| Offset | Field | Use |
|---|---|---|
| 0 | `slots` | Slot table base: one word per definition (§7). |
| 8 | `rt` | Runtime function table base: fixed order, never swapped. |
| 16 | `stack_limit` | Lowest stack address a function may start below (§6). |
| 24 | `interrupt` | Nonzero when the run must stop; read with an atomic load. |
| 32… | private | Trap record, allocator, ledger, memory cap. |

- Why: one pointer carries everything per run, so generated code holds no absolute address and
  needs no relocation; two runs could use two contexts.
- Not chosen: **thread-local runtime state**; needs TLS access in generated code. **Globals patched
  into code**; needs relocations and rules out a second context.

## 5. Signatures and status returns

**A compiled function is `fn(ctx, args..., out) -> i32`. `out` is present only when the function
has a result; the result is written whole through it. The returned word is a status.**

| Status | Meaning |
|---|---|
| 0 | Finished; `out` holds the result. |
| 1 | Trapped; the trap record holds kind, site, operands and frames. |
| 2 | Stopped by the interrupt flag. |

A caller checks the status after every call to a function or a runtime routine that can fail and
returns any nonzero status at once (after §6's frame push for 1). `out` is unwritten on nonzero.

Arguments, by type:

| Type | Passed as |
|---|---|
| `Int`, `Bool`, function value | 1 × I64 (`Bool` is 0 or 1) |
| `Float` | 1 × F64 |
| read-only `String` | 3 × I64: ptr, bytes, chars (a prefix of §8's header; a slice is a part) |
| read-only `List[T]` | 2 × I64: ptr, len (a prefix of §8's header; a slice is a part) |
| read-only `Map[K, V]` | 1 × I64: the map word |
| read-only record, enum, `Option`, `Result`, `Effect` | 1 × pointer to the value |
| `inout` of any type | 1 × pointer to the resolved place |

Arguments are borrowed: the caller owns them and frees them (M2-05, never moved). Results are owned
by the caller once written (M2-05: a local moves, a parameter copies).

M4-34 kept one rule instead of the prefixes: a read-only `String` or `List` passes as a pointer to
its words, as a record does. A List slice passes as a pointer to a view in the caller's frame: ptr
at the first item, len, cap 0, so it owns nothing and makes no block. The callee needs the words in
memory either way, so the prefixes would only move the store into it. A String slice is still a new
String until a view of one needs the byte offset of a code point from `rt.text`.

- Why: status in a register and the result through memory gives one uniform rule for every type and
  keeps the check to one compare. It extends M1-14.1 rather than replacing it.
- Not chosen: **status numbers that are trap kinds** (the prototype); M2-06 §3 already rules 0/1
  with the kind in the record. **Multi-value returns for small results**; a second rule for no
  measured gain.

## 6. Traps, frames, the stack check and the interrupt poll

**A failed check calls `rt.trap(ctx, kind, site, a, b, c)` and returns 1. After a callee returns 1,
the caller calls `rt.push_frame(ctx, call_site)` and returns 1. Every function starts with the
interrupt poll, then the stack check; every loop head polls the interrupt.**

- `site` is `def_id << 32 | offset`, the offset counted from the definition's first site so an
  edit elsewhere leaves its code unchanged (M4-37); `Program::place` decodes it. The site table (source position per site) lives in the
  runner's Rust memory, built by the emitter, not in emitted data.
- `a`, `b`, `c` are the detail operands (M2-06 §3): numbers as words; a `String` key as a pointer to
  its header. Unused ones are 0.
- The trap record keeps the first 8 frames and an overflow flag (M2-06 §3). A frame is a call site.
- **Interrupt poll:** atomic load of `ctx.interrupt`; nonzero → return 2. No frame, no record.
- **Stack check:** `sp < ctx.stack_limit` → `rt.trap(ctx, stack, 0, 0, 0, 0)` and return 1. The
  function has no own position, so the first pushed call site is the trap's position.
- Each run executes on a runner thread with a 64 MiB stack; `stack_limit` sits 1 MiB above its
  bottom. The emitter refuses, as an internal error, a function whose stack slots pass 256 KiB, so
  the 1 MiB margin always holds one frame plus any runtime routine.
- Runtime copy and release are iterative worklists and never recurse (M2-05). Emitted equality of
  user types may recurse and trap `stack`.

Trap kind numbers (M2-06 §1 order):

| Kind | Number |
|---|---|
| `overflow` | 1 |
| `divide_by_zero` | 2 |
| `out_of_bounds` | 3 |
| `bad_conversion` | 4 |
| `assert` | 5 |
| `hole` | 6 |
| `stack` | 7 |
| `memory` | 8 |

`stale_handle` gets no number until something raises it. A hole compiles to `trap(hole)` plus return
1; an example compiles to a function with a `Bool` result (M2-06 §3).

- Why (stack): a stack-position check is one compare against a value already in `ctx`, needs no
  counter to keep in step on every return path, and measures what actually runs out. M2-06 §1.4
  compares only kind and status for `stack`, so the depth at which it fires need not match the
  interpreter.
- Not chosen: **a depth counter in `ctx`**; an increment and decrement on every call and every
  failure return. **A guard page and signal handler**; M4-04 rules out signal handlers.

## 7. Slots and calls

**The slot table is one word per definition id: a code address for a function or a variant
constructor, the type record address (§10) for a type. A call loads `ctx.slots[id]` and calls it
indirectly. A function value is its definition id; calling one is the same load with a run-time id.
`==` on function values compares ids.**

- Ids run functions, examples, constructors, the definition that builds the app's state (when the
  app has one), then type records. A constructor is compiled for each
  variant with fields of an enum the program uses, in declaration order, as a function of its
  fields; it is what a variant used as a function value calls (M4-37b).
- Slot loads use trusted memory flags (never trap, aligned). The installer swaps a slot only between
  messages (M4-04).
- Runtime routines are called through `ctx.rt[n]` with a fixed numbering in `paka-rt`.
- A string literal is a runtime allocation plus immediate stores of its bytes; no data section.
- Why: no relocations, no absolute addresses, swap is one word (M4-04, M2-09 §3).
- Not chosen: **direct calls patched on swap**; faster calls, but every caller must be relinked.
  **Read-only data blocks for literals**; needs addresses in code or a second table.
- **Rebuilds (M4-37):** a definition's cache key is the SHA-256 of the compiler version, target,
  mode and its Cranelift IR. The IR holds each callee's signature and slot id and each layout the
  code reads, so it stands for the interface hashes of the definitions used: a signature edit
  changes the key of exactly the users whose code changes. Code under a known key is reused; the
  new code is installed in one mapping and every slot is swapped as one group, or nothing when a
  definition is refused. Ids and type numbers follow program order, so adding a definition or a
  new type recompiles the definitions numbered after it. That costs compile time, not
  correctness, and stays until it shows up in practice.

## 8. Value layouts

**Every value is a whole number of 8-byte words, aligned 8, no padding. Fields are in declared
order. Every heap block comes from the runtime allocator.**

| Type | Words | Layout |
|---|---|---|
| `Int` | 1 | i64 |
| `Float` | 1 | f64; NaN bits unobservable (M2-03) |
| `Bool` | 1 | 0 or 1 |
| function value | 1 | definition id |
| `String` | 4 | ptr, bytes, chars, cap. UTF-8, no NUL. ptr is null when cap is 0. `bytes == chars` means ASCII (M4-32's fast path). |
| `List[T]` | 3 | ptr, len, cap. Items contiguous at T's size. ptr is null when cap is 0. |
| `Map[K, V]` | 1 | null, or a runtime-owned block: len, cap, then the entries in rising key order. An entry is the key (8-byte Int or 4-word String), then the value. |
| record | sum of fields | fields in declared order; a record with no fields is 0 words |
| enum | 1 + largest payload | tag word (declared position, from 0), then the payload's fields |
| field-less enum | 1 | tag word |
| `Option[T]` | 1 + T | `Some` 0, `None` 1 |
| `Result[T, E]` | 1 + max(T, E) | `Ok` 0, `Err` 1 |
| `Effect[Msg]` | 1 + largest payload | `Print` 0, `ReadFile` 1, `WriteFile` 2, `Exit` 3, `ExitWith` 4 |
| box | 1 | pointer to a heap block holding one value; null only while not yet built |

**A field whose type reaches the enclosing type by value (through records, enums, `Option` or
`Result`) is stored as a box.** M4-22 finds these fields; a `List` or `Map` already breaks the cycle.

`Effect` payloads in M2-15 order: `Print(text)`; `ReadFile(path, then, or)`; `WriteFile(path, text,
then, or)`; `ExitWith(status)`. The core form always gives both `then` and `or`: function values
(definition ids) or, for `then: Msg` (M2-15), a box holding the message. A trap while the effect is
built can leave the box word 0; release skips it.

- Why (String 4 words): byte length for copying and UTF-8 output, code point count for `len` and
  indexing in O(1) on the ASCII path, capacity for growth. Keeping all four in the value means a
  read-only pass is three registers with no load.
- Not chosen (String): **a pointer to a heap header**; one word to pass but a load on every use and a
  block even for the empty string. **No code point count**; `len` becomes a scan.
- Not chosen (Effect): **M1's three-word effect**; it cannot hold `WriteFile`'s four payload fields.

## 9. Who frees each value

**Each value has one owner: a local, a field, a list item, a map entry, a box, or the run state. The
owner frees it on scope end or overwrite; M4-33 places the frees. Arguments are never freed by the
callee.**

| Value | Owner | Freed by |
|---|---|---|
| `Int`, `Float`, `Bool`, function value, field-less enum | holder | nothing to free |
| `String`, `List`, `Map` | holder | `rt.release` on its heap block, after releasing items |
| box | the field holding it | `rt.release` of the boxed value, then the block |
| record, enum, `Option`, `Result`, `Effect` | holder | release of each owned field, per the type record |
| argument | caller | the caller, after the call |
| result | caller, once written | the caller, as any owned local |
| message | run loop | the run loop, after the handler finishes or traps |
| returned effect list | run loop | the run loop, after performing it |
| run state | runner | kept across runs in the runner heap; freed on a state type change (M5) or runner exit |
| anything else allocated in a run | allocator | freed at run end; the ledger reports leaks (M4-40) |
| values live when a run traps | allocator | freed at run end; the unwind drops nothing, so they are not leaks (M4-42) |

Allocation goes through `rt.alloc(ctx, bytes)`. It checks the per-run cap (M4-04); past it, it
records a `memory` trap and the caller returns 1. Release never traps.

## 10. Type records

**Each user type has one constant type record in its slot, built by M4-22 and used by the runtime's
generic code (M2-09 §3).**

| Word | Field |
|---|---|
| 0 | size in bytes |
| 1 | equality function (definition id), or the runtime's for a built-in type |
| 2 | order function, or 0 when the type has no order |
| 3 | owned-field count n |
| 4… | n entries: offset, kind (String, List, Map, box), item type record, value type record (Map only) |

For an enum the owned-field table is per variant: the entry list starts with the variant count and
each variant's owned fields. Copy and release walk these tables iteratively.

M4-33 fixed the words (`paka_rt::abi::dev::records`). An entry is four words: offset, kind, then
two by kind. `STRING` (1) uses neither. `LIST` (2) holds the item's record, 0 when items own
nothing, and the item's size. `VALUE` (5) is a tagged value held inline, with its record. A tagged
type sets bit 63 on word 3 (`TAGGED`), whose low bits are the variant count; each variant then
gives its n and n entries. `BOX` (4) holds the boxed value's record, 0 when it owns nothing, and its
size (M4-36). `MAP` (3) holds the value's record, 0 when values own nothing, and a shape word:
bit 63 (`STRING_KEY`) for a String key, the value's size in the low bits (M4-38b).

M4-38 emits equality inline at each `==`, `contains` and `find`: a List item by item, a record
field by field, a variant by tag then fields. So words 1 and 2 stay 0; no runtime code asks a type
for its equality yet. Equality on a recursive type and ordering on held types are refused until a
case needs them. The List rows that change a List (`append`, `pop`, `sort`, …) and `list_of` are
one runtime body, `rt.items`, told the item's record and size; `sort_by` is `rt.sort_by`, which
calls the comparator through its slot and passes its trap or stop on as a call's. Editing a user
definition therefore recompiles no collection code.

- Why: one walker serves every type; per-type emitted code is only equality (M2-09).
- Not chosen: **emitted copy and release per type**; more code per type and recursion that could
  trap `stack` in release, which M2-05 forbids.

## 11. Running an app

**The update function is `fn(ctx, state, msg, out) -> i32`: `state` is an inout pointer to the run
state, `msg` a read-only pointer to the message, `out` receives the owned `List[Effect[Msg]]`.**

- The runner builds the state from its defaults and the start message from argv: one `String` per
  start field, wrong count gives the usage line and status 2, a non-UTF-8 argument the argument line
  (M2-15).
- The run loop and queue are native-only Rust in `paka-rt`; it hands each effect to the shared
  performer (§3). `then`/`or` are applied when the answer reaches the front of the queue (M2-15).
- A handler that returns 1 performs none of its effects; a headless app keeps no rollback (M2-15).
  Status 2 ends the run with `stopped: "time"` (M4-04).
- **M4-36:** the loop is `paka_rt::abi::dev::app::serve`; it calls definitions through the
  installer's `Slots::session`, which holds the slots for the whole run. The performer, the start
  arguments and the host world are `paka_rt::effects`, which the interpreter calls with its own
  decoded values. A handler with no state is `fn(ctx, msg, out)`. An answer function is
  `fn(ctx, text, out)`; the loop frees the text after it returns. Native trap reports and the
  `time` stop's line come with M4-39 and M4-40.
- `ExitWith` takes 0 or 5..255; any other value stops with status 3 (M2-15).
- `Print` writes fd 1 directly and flushes per effect. The runner ignores SIGPIPE and SIGXFSZ once at
  start.

## 12. M1-14 rules

| M1-14 rule | Dev mode | Note |
|---|---|---|
| C calling convention | **kept** | System V via Cranelift's default. |
| 14.1 status `i32` return, out pointer last | **kept** | `ctx` added in front. |
| 14.2 8-byte words | **kept** | Every layout is whole words. |
| no context pointer | **changed** | `ctx` first in every function (§4). |
| message is an `i64` variant position | **changed** | A pointer to the message; a field-less message is still one tag word. |
| three-word effect | **changed** | §8's `Effect` layout, `Exit` is tag 3. |
| 14.3 plain-argument entry | **changed** | No C entry in dev mode; the runner calls update directly. `paka build` moves to a record (§13). |
| 14.4 version in the entry name | **kept** | The build entry becomes `paka_rt2_run`. |
| 14.5 SIGPIPE ignored at entry | **kept** | Set once by the runner; SIGXFSZ too. |
| 14.6 status 4 for internal errors | **kept** | |
| any non-zero status is an internal error | **changed** | 1 trapped, 2 stopped; anything else is internal (4). |
| flush per `Print` | **kept** | |
| no cross-compiler LTO | **kept** | Applies to the `paka build` path. |
| grants word, bit 0 Console | **kept** | Carried in the app record (§13) and in the runner. |
| no heap | **changed** | Runtime allocator with ledger and cap (§9). |

## 13. The `paka build` path

**`paka build` keeps the M1 LLVM emitter and M1's update convention. Its entry becomes
`paka_rt2_run(app)`, where `app` points to a `repr(C)` record: name ptr, name len, update, start
variant position, start field count, grants. The runtime checks argc against the field count and
argv for UTF-8 (M2-15 lines and status 2) before the first update.**

- Why: this is M1-14.3's look-again trigger (more entry arguments) and the smallest step that lets a
  start variant carry fields. `tests/cases/parse/variant_payload` (a `Start(path: String)` start
  with a constant body) then leaves the UNSUPPORTED list in `paka/tests/native.rs`.
- The other cases there need computed bodies (state, `ExitWith` operands, reading a start field);
  they leave when the dev back end runs them (M4-36) and, for `paka build`, at M6.
- Not chosen: **widen the M1 template emitter to state and computed bodies**; it would grow a second
  code generator that M6 replaces. **Leave `paka build` untouched**; no native case would gain start
  fields here.

## 14. What this changes in TASKS.md

- **M4-22:** builds the type records of §10 and finds boxed fields (§8); layouts are §8's.
- **M4-23:** creates `paka-installer`: mmap, copy, mprotect, slot table, the unsafe call into
  `fn(ctx, …) -> i32`.
- **M4-24:** slots hold code addresses or type record addresses (§7); swaps between messages only.
- **M4-25:** `rt.alloc` checks the cap and records a `memory` trap; the ledger feeds M4-40.
- **M4-26:** scalars per §8; overflow, division and conversion checks call `rt.trap` with §6's
  numbers.
- **M4-27:** status returns 0/1/2, `push_frame` on unwind, interrupt poll then stack check at entry,
  poll at loop heads, 64 MiB run thread with 1 MiB margin, 256 KiB frame limit.
- **M4-30:** a hole is `trap(hole)` plus return 1; an example returns a `Bool` through `out`.
- **M4-31, M4-31b:** enums, `Option`, `Result` per §8's tag rule.
- **M4-32:** `String` and `List` per §8; text rows move from `paka/src/interp/text.rs` into
  `paka_rt::ops`; the interpreter shares `ops` and the effect performer (§3).
- **M4-33:** places frees per §9; arguments borrowed, results owned.
- **M4-34:** `inout` is a place pointer; read-only `String`/`List` and slices pass as §5's prefixes.
- **M4-36:** update is `fn(ctx, state, msg, out)`; start fields from argv; `ExitWith`; the run loop
  in `paka-rt` and the shared performer `paka_rt::effects`.
- **M4-37b:** a function value is a definition id; no capture, so no closure layout.
- **M4-38:** generic code is driven by §10's type records.
- **M4-38b:** done: `rt.map` finds (binary search), adds and removes entries; equality is emitted
  inline entry by entry.
- **M4-40:** the clean report reads the allocator ledger of §9.
- **M1 build path (this task):** `paka_rt2_run` with the app record of §13; `variant_payload` leaves
  UNSUPPORTED.
- **docs/abi:** a new `docs/abi/dev.md` mirrors §4–§11 when M4-27 lands; `docs/abi/m1.md` gains the
  `paka_rt2_run` entry.
