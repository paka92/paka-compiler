# M2-09 · Generics, interfaces and function values: decision

Base: the recorded M2-09 page in DECISIONS.md, written out as one closed table, one matching
rule, one hash rule and one compilation rule, with the fix text on every refusal and worked
samples. All seven recorded picks stand. Two settled lines are made stricter, marked **tightens**;
each closes a hole and refuses nothing the task classes write. One settled line is made exact,
marked **exact**, so an M1 case keeps its result.

The whole design: users write no generic definitions and no interfaces. The only generic things
are the built-in types and the built-in rows written with `T`, `K`, `V`, `E`; a use is checked
from the row and the argument types by a finite walk that reads no body (lines 81, 136, 152).
Every type has `==` by structure; three types have order; `+` joins Strings; interpolation takes
Int, Bool and String. A function value is a name: a user `fn` without inout, or a user variant
with fields; its type is `fn(A, B) -> R`; it carries no data and is equal to itself by
definition. Built-in generic code is one shared copy driven by a layout record per type. The
interface hash is line 285 with labels and inout marks, and every named type a signature reaches.

## 1. Resolutions, point by point

### 1.1 No user generics, no interfaces: what it buys and what it costs

No type parameter, no `interface`, no seventh definition kind (line 265 lists six; line 354 stays
open until after 'go'). A helper that two types need is written once per type. This is M2-01.2
kept.

It satisfies the paper and the task classes because every M2-01 task is one file with concrete
types, and the only operations a task needs across types (length, order, equality, join) are rows
of the table in 1.2. It costs: a helper such as `first` or `swap_pair` written twice when a program
has two item types (no task class shows one), and the habit spellings `fn first<T>`, `interface`,
`trait`, `impl`, which are refused with the fix (section 5). Adding type parameters later is a
strict addition: a `<` after a definition name is an error today, so no program, hash or row would
change.

```
fn first<T>(xs: List<T>) -> T { xs[0] }     // rejected: unexpected-token at <: "Paka has no type
                                            //   parameters; write it for one type: fn first(xs: List<Int>) -> Int"
interface Shape { fn area(s: Shape) -> Float }   // rejected: unexpected-token at interface: "Paka has no
                                            //   interfaces; write one function per type and pass it by name: sort_by(&xs, before)"
fn first_int(xs: List<Int>) -> Int { xs[0] }     // accepted
```

Why not type parameters without interfaces: sound and checkable from signatures, but it needs a
declaration form, a substitution step, a hash rule for generic signatures and a "T can only be
moved, compared and stored" rule that models trip on; no task class needs it. Why not interfaces:
the most new rules for a model to get wrong, for nothing a task needs (M2-01.2).

### 1.2 The closed table

One row per operator or built-in name; only the language adds rows; a user `fn` has one signature
with written types and may not reuse a row's name (`duplicate-name`, M2-02). Both operands of a
two-sided row must have one and the same type (line 47: nothing converts). Rows owned by M2-03 and
M2-14 are listed here so the table stands in one place; their exact results are theirs.

| Row | Accepts | Result |
|---|---|---|
| `==` `!=` | every type, both sides one type (1.4) | Bool |
| `<` `<=` `>` `>=` | Int, Float, String (1.5) | Bool |
| `+` | Int, Float, String (joins) | the operand type |
| `-` `*` `/`, unary `-` | Int, Float | the operand type |
| `%` | Int | Int |
| `+=` | Int, Float, String (appends); `-=` `*=` `/=` Int, Float; `%=` Int | none; the target is a place |
| `!` `&&` `\|\|` | Bool | Bool |
| `min` `max` | Int, Float, String | the operand type |
| `abs` | Int, Float | the operand type |
| `len` `is_empty` | String, List<T>, Map<K, V> | Int; Bool |
| `contains` `find` | String with String; List<T> with T (items by `==`) | Bool; Option<Int> |
| `sort` | List<Int>, List<Float>, List<String> | none (in place) |
| `sort_by` | List<T> with fn(T, T) -> Bool, any T | none (in place) |
| `x[i]` | String with Int (read only); List<T> with Int; Map<K, V> with K | String; T; V |
| `x[a..<b]` | String, List<T> | the same type |
| `for x in` | List<T>; an Int range | binds T; Int |
| `"{e}"` | Int, Bool, String (1.6) | text |
| every other M2-14 row | one signature with `T`, `K`, `V`, `E` | per row |

A row applied to a type outside its set is `type-mismatch` at the operator, or for a call at the
argument that does not fit, as M2-03 already reports `%` on a Float; the message names the row's
types and the repair for that row. `x % 2.0` reads the same whichever side is the Float.

```
max(len(a), len(b))      // accepted: Int, Int
max(1, 2.0)              // rejected: type-mismatch at 2.0: "max takes two of one type; write 1.0"
"n = " + n               // rejected: type-mismatch at +: "no + between String and Int; write an interpolation: \"{n}\""
xs + ys                  // rejected: type-mismatch at +: "no + on List; write extend(&xs, ys)"
len(5)                   // rejected: type-mismatch at 5: "len takes a String, List or Map"
fn len(s: String) -> Int { 0 }   // rejected: duplicate-name at len: "len is a built-in; rename it"
let count = len(xs)      // accepted: a local may hide a built-in name (M2-02 §1.3)
```

Exact results fixed upstream and kept: Int arithmetic traps `overflow`; Float is IEEE; String `<`
is by code point, a proper prefix first (M2-03). `max` and `min` on Float: a NaN argument gives
NaN; `max(-0.0, 0.0)` is `0.0` and `min(-0.0, 0.0)` is `-0.0` in either argument order. `s + t`
joins left then right; `s += t` means `s = s + t`, done in place where M4-33 can. No `+` on Lists.

### 1.3 How a built-in row is checked from its signature alone

The "generic definition" of the task's done-when is always a row; its row is its signature and it
has no body. A use is accepted or rejected from the row and the types written on the arguments, by
this walk:

1. Arguments that carry their own type are checked first, left to right, each against the row's
   parameter type. A letter seen for the first time is bound to the argument's type at that place;
   a letter already bound must match exactly. Matching is structural: walk the two types together,
   no subtyping, no conversion. An argument carries its own type when it is a name, a literal
   other than `[]`, `[:]` and `None`, or a call whose result has no free letter after its own
   arguments.
2. Letters still free take their binding from the type the call's position expects, by matching
   the row's result type against it (the hole rule, M2-06.4).
3. The remaining arguments (`[]`, `[:]`, `None`, a hole, a call that still had a free letter) are
   checked against their parameter types with the bindings put in.
4. A letter still free that the row's result does not carry is `cannot-infer` at the argument
   that needed it, with M2-02 §5's text. A letter the result carries stays open for the call's own
   position, which must fix it the same way. The result type is the row's result with the bindings
   put in.

Step 1 is enough for almost every call because on every row the value worked on is the first
parameter (M2-14), so `T` is bound before `item: T` is seen. Steps 2 and 3 exist for the grid and
graph idiom `list_of([], count: n)` and for `[] == xs`. No other definition's body is read, so
lines 136 and 152 hold, and line 49 is never tested: nothing is inferred across definitions.

```
var xs: List<Int> = []
append(&xs, 1)                         // T = Int from xs; accepted
append(&xs, "a")                       // rejected: type-mismatch at "a": "expected `Int`, found `String`"
sort_by(&ps, before)                   // T = Player from ps; before must be fn(Player, Player) -> Bool
let n = unwrap_or(get(m, k), 0)        // K, V from m: Map<String, Int>; k against String; 0 against Int
var adj: List<List<Int>> = list_of([], count: n)   // step 2 binds T = List<Int> from the var; [] checked last
let g = list_of([], count: 3)          // rejected: cannot-infer at []: "write it: let g: List<List<T>> = ..."
let e = Err("no")                      // rejected: cannot-infer at Err: "write it: let e: Result<T, String> = ..."
_ = len([])                            // rejected: cannot-infer at []: "cannot infer the type of []; write it: let x: List<T> = ..."
_ = [] == []                           // rejected: cannot-infer at the left []; None == None and _ = [] likewise
contains([[1], [0]], [0])              // T = List<Int> from the first argument; accepted
```

### 1.4 Equality: every type, by structure

`==` and `!=` take two values of one type and give Bool; `!=` is the negation. The walk is deep and
stops at the first difference; a value nested too deep traps `stack` (M2-05).

| Type | Equal when |
|---|---|
| Int, Bool | same value |
| Float | IEEE: `NaN == NaN` is false, `-0.0 == 0.0` is true, also inside any aggregate |
| String | same code points in order |
| List<T> | same length, items equal by position |
| Map<K, V> | same keys, the value under each key equal; written order never matters (M2-14 stores in key order) |
| record | every field equal; declared order is irrelevant |
| enum, Option, Result, Effect | same variant, then its fields equal |
| function value | the same definition (1.10) |

No type is excluded, so an example may compare a whole state or a whole effect list, function
values inside. `n == 1.5` with an Int is `type-mismatch`, fix "write to_float(n)". A record that
holds a NaN is not equal to itself; the reference says so in one line.

```
example same_graph {
  var g: Map<String, List<String>> = [:]
  g["b"] = ["a"]
  g["a"] = ["b"]
  g == ["a": ["b"], "b": ["a"]]                              // accepted
}
example asks_for_the_file {
  var s = Tally {}
  update(&s, Start("a.txt")) == [ReadFile("a.txt", then: Loaded, or: Failed)]   // accepted: function values compare
}
```

Why not `==` refused on function types: no example could check an effect list. Why not a per-type
opt-out: a second rule for nothing a task needs.

### 1.5 Order: Int, Float and String only

`<` `<=` `>` `>=`, `min`, `max`, `sort` and Map keys. Float order is IEEE (every comparison with
NaN is false; `sort` uses `<` and leaves a NaN where the fixed merge puts it, M2-14). String by
code point. Bool, enums, records, Lists, Maps, Options, Results and function values have no order;
a program that wants one writes a `before` function or compares a field. No order is ever taken
from field or variant position: moving a field or a variant must not change a result.

```
fn ahead(a: Player, b: Player) -> Bool { a.score > b.score }   // accepted
a > b                     // rejected: type-mismatch at >: "Player has no order; compare a field: a.score > b.score"
sort(&players)            // rejected: type-mismatch at &players: "Player has no order; write sort_by(&players, before)
                          //   with fn before(a: Player, b: Player) -> Bool"
```

Why not order by structure: a refusal with the fix is one edit; a silent reorder after a field
move is a failed hidden test pointing at nothing.

### 1.6 Text: nothing automatic

`"{e}"` accepts an Int, a Bool (`true`/`false`) or a String. Any other type is `type-mismatch` at
the expression with the fix for that type: a Float "write {fixed(x, digits: 2)}" (M2-03); a
List<String> "write {join(xs, \", \")}"; any other List or a Map "build the text in a loop"; a
record "write its fields: {p.x}, {p.y}"; an Option or Result "match it first"; an enum "match it
and write each variant's text"; a function value "a function has no text". There is no to-text
built-in and no debug form a program can reach.

The tools' value text form (failed comparisons in `paka examples`, M5-16 tree text) is the one
the recorded page fixed: a value prints as written in source, `Toggle(7)`, `Point { x: 3, y: 4 }`
in field order, `[1, 2]`, `["a": 1]` in key order, `"a\n"` with M2-03's escapes, a Float as M2-14
prints it, `ReadFile("a.txt", then: Loaded, or: Failed)`, and a function value as its definition
name. It is help, not meaning.

Why not a debug form: tasks print exact output, so `Print("{p}")` would pass the checker and fail
the case; the agent would learn it from a diff instead of a message with the fix.

### 1.7 Function values: what, type, where

A function value is the bare name of a user `fn` none of whose parameters is inout, or of a user
enum variant that has fields, standing for its constructor. Nothing else: no function written in
place, no capture, no partial application, no method. It carries no data (M2-05 §1.9 builds on
this). A variant without fields written bare (`Exit`, `Saved`, `None`) is a plain value of its
enum, never a function.

Its type is `fn(A, B) -> R`, `fn(A)` for no result, `fn()` for no parameters; one space after each
comma and around the arrow is the canonical spelling in messages. Labels and the `;` are not part
of the type: `fn pad(text: String; width: Int) -> String` has type `fn(String, Int) -> String`,
and `Loaded(text: String)` of `Msg` has type `fn(String) -> Msg`. Two function types are the same
when their parameter lists and results match structurally. No function type contains itself, so
no value is ever applied to itself. `inout` inside a `fn` type is `unexpected-token`: "no inout in
a function type".

A function type may stand anywhere a type may: parameter, result, local, record field, variant
field, List item, Map value (not a key, M2-14). `let f = by_length` needs no annotation: a name has
the type of its signature. An app's state may not reach one (1.11).

Why named functions only: the one habit that matters is a lambda in a `sort_by` call, and M2-14
has no `map`, `filter` or `fold` for a lambda to go to. One accepted snippet would buy a value that
carries data: a new layout, a new `==` rule, level-4 work in M4-37b and M6-15, and every M2-05 rule
reopened for capture. The refusal names the two-line edit instead. If practice runs show the
lambda habit costing many counted edits, "anonymous, no capture" is the free loosening: a lambda
that uses only its parameters is a named function with the name left out, and nothing else here
changes.

### 1.8 Passing, calling, `&`, effects

Written bare where a function type is expected: `sort_by(&ps, before)`, `then: Loaded`. Called
with `( )` by position: `less(a, b)`, `s.on_done(x)`, `xs[0](y)`, `f()`. Argument count and types
are checked against the function type with M2-02's call rules; a label is `wrong-label`, fix "drop
the label: calls through a function value are positional"; a wrong count is
`wrong-argument-count`. A name whose type is not a function type followed by `( )` is
`not-a-function`: "n is an Int, not a function". Name resolution for `name(...)` is the ordinary
order: a local or parameter, then a user definition, then the built-in table (M2-02 §1.3).

A function type has no inout, so a call through a value takes no `&` (`unexpected-inout-mark`,
M2-05 §1.4); the callee gets its arguments as read-only parameters under M2-05's rules unchanged,
and the value itself is a fresh operand with no storage. So a call through a value never changes a
caller's place and never aliases anything: M2-05's forest holds with no new rule.

A built-in that calls a function value (`sort_by` calls `before`) makes a nested call of its own: the
call that would be the 10,001st traps `stack` at the built-in's name token (`sort_by`), not inside
`before` (M2-06 §1.4).

Effects and grants: a function has no effects (line 165), so a value has none and never carries a
grant (line 167). Any function may build an effect list; only the list the app's `update` returns
is performed, where the grant is checked (M2-15). A `then:` or `or:` value is called when the
answer's turn comes in the queue; it returns a Msg that goes through `update` like any other; a
trap inside it is a trap of that turn. Passing a function value changes nothing about what a
program may touch.

```
fn shorter(a: String, b: String) -> Bool { len(a) < len(b) || len(a) == len(b) && a < b }

fn by_length(ws: List<String>) -> List<String> {
  var out = ws
  sort_by(&out, shorter)                 // accepted: row sort_by(xs: inout List<T>, before: fn(T, T) -> Bool)
  out
}

type Job { done: fn(Int) -> Msg }        // accepted: a field of function type
fn run(j: Job) -> Msg { j.done(3) }      // accepted: call through a field, positional

less(a: x, b: y)                         // rejected: wrong-label at a:: "drop the label: calls through a function value are positional"
less(&x, y)                              // rejected: unexpected-inout-mark at &: "less is a function value and takes no inout; drop the &"
ReadFile(p, then: Failed)                // rejected (Failed(why: String, code: Int)): type-mismatch at Failed:
                                         //   "expected fn(String) -> Msg, found fn(String, Int) -> Msg (Failed)"
sort_by(&xs, cmp)                        // rejected (cmp gives Int): type-mismatch at cmp: "expected fn(Row, Row) -> Bool,
                                         //   found fn(Row, Row) -> Int (cmp)"
then: Exit                               // rejected: type-mismatch at Exit: "expected fn(String) -> Msg, found Effect<Msg>"
sort_by(&ps, |a, b| a.score > b.score)   // rejected: unexpected-character at |: "no function written in place; write it at
                                         //   top level and pass its name: fn before(a: T, b: T) -> Bool { ... }; a local it would
                                         //   have used becomes a parameter or a field"
```

### 1.9 Built-ins and bare names

A built-in function (`len`, `max`, `fixed`) or a built-in variant with fields (`Some`, `Ok`,
`Err`, `Print`, `ReadFile`, `WriteFile`, `ExitWith`) cannot be a value: its row takes several
types or is generic in `T`, `E` or `Msg`, so it has no single function type, and the labels of
`fixed`, `insert` and `list_of` would be lost. A user `fn` with an inout parameter cannot be a
value either (1.8). All three are `not-a-value` at the name, with the fix a one-line user
function. Fieldless built-in variants (`None`, `Exit`) are plain values.

**Exact.** Where a name of function type stands bare in a position that expects its own result
type, the diagnostic is `wrong-argument-count`, not `type-mismatch` or `not-a-value`: the missing
parentheses are the likeliest slip and that code names the fix. This holds for built-in and user
variants and for user functions alike, so `[Print, Exit]` keeps M1's `wrong-argument-count` at
`Print` (case `check/print_without_argument`).

```
let f = len                  // rejected: not-a-value at len: "len is a built-in and cannot be a value;
                             //   write fn wrap(...) -> R { len(...) } and pass wrap"
then: Some                   // rejected: not-a-value at Some: "Some is a built-in variant and cannot be a value;
                             //   write fn some_of(value: String) -> Option<String> { Some(value) }"
let step = update            // rejected: not-a-value at update: "update has an inout parameter and cannot be a
                             //   value; give it a result instead of inout, or call it directly"
[Print, Exit]                // rejected: wrong-argument-count at Print: "Print takes 1 argument (text), got 0; write Print(...)"
let n: Int = compute         // rejected: wrong-argument-count at compute: "compute takes 2 arguments (a, b), got 0; write compute(...)"
[Print("hi"), Msg]           // rejected: unknown-name at Msg: a type name is never a value (M1 case type_as_value)
```

### 1.10 Identity and equality of function values

Two function values are equal when they name the same definition: the same `fn` or the same
variant. `Loaded == Loaded` is true, `Loaded == Failed` is false, two different functions with the
same body and type are unequal. The comparison needs both sides of one function type, like any
`==`. The identity is the definition itself, which in the derived database is its stable id (line
277): editing a body or installing a new body in the definition's slot in dev mode (line 304) keeps
the id, so every stored function value and every `==` on it is unchanged (M4-37b); renaming a
definition makes a new one. Release code may share machine code between two definitions but may
not merge their ids: `==` on function values is an id compare in every back end, so the answer is
exact and the same everywhere (line 161).

### 1.11 App state holds no function type (tightens)

**Tightens.** No type reachable from an app's `state:` type may hold a function type, through a
field, a variant field, a List, a Map value or an Option, in a headless app as in a visual one.
Rejected at the `state:` value with `type-mismatch`: "state Tally holds a function type in field
after; keep a message value instead and match on it in update". With this, a function value lives
only in locals, arguments, results and the effect list of the current handler, and the only
function values that outlive a handler are the `then:` and `or:` fields of queued effects, which
the run loop calls through their ids. The recorded line gave this rule to visual apps only; one
rule for both app kinds is one line fewer in the reference and one check (M2-32) instead of two,
it costs no task (pending file names are Strings, M2-15), and it closes the only way a stored value
could name a definition that an edit has removed (M5-28 then needs no migration of function
values). A record that is not reachable from a state may hold a function type freely.

```
type Tally { words: Int = 0 }                         // accepted as state
type Later { after: fn(String) -> Msg }               // accepted as a type; rejected as state:
app wc { state: Later ... }                           //   type-mismatch at Later: "state Later holds a function type in field after; ..."
```

The function-type check comes before the default check: `Later` is `type-mismatch` although
`after` has no default.

### 1.12 Counter-examples tried against the rules

- `twice(twice)` with `fn twice(k: fn(Int) -> Int) -> Int`: `type-mismatch`, no function type
  contains itself.
- `[] == xs`: step 3 checks `[]` after `xs` bound `T`; accepted. `[] == []`: `cannot-infer`.
- `len([])`: `cannot-infer`; there is nothing to count.
- `var seen = list_of(false, count: n)`: `false` carries its type; `T = Bool`.
- `m[parts[0]] = unwrap_or(parse_int(parts[1]), 0)`: every letter bound by step 1.
- A `fn` with a labelled parameter passed to `sort_by`: accepted, labels are not in the type; the
  call inside the sort is positional.
- `Idle` where `fn(Int) -> Mode` is expected: `type-mismatch`, a value of Mode, not `not-a-value`.
- `let len = 3` then `len(xs)`: `not-a-function` on an Int; the local hides the row.
- A program-wide recursion `type A { bs: List<B> }`, `type B { a: Option<A> }`: one hash group
  (section 3); editing either rechecks users of both.
- `f == g` with `f: fn(Int) -> Int` and `g: fn(Int) -> Bool`: `type-mismatch`, two types.

## 2. Grammar (additions to M2-02 §2)

None. M2-02 §2 already has

```
type = UPPER [ "<" type { "," type } ">" ]
     | "fn" "(" [ type { "," type } ] ")" [ "->" type ]
```

A function value is the existing `LOWER` or `UPPER` primary resolved to a `fn` or a variant with
fields; a call through it is the existing postfix `( args )`. Type arguments stand only in type
positions, so `<` in an expression is always a comparison and the bracket-versus-comparison trap of
M2-17 does not exist; `>>` is not a token, so `List<List<Int>>` closes two brackets (M2-03). The
reserved list gains nothing. The habit spellings are refused by the parser as M2-02 §1.2 refuses
habit spellings, under existing codes with the fix in the message: `<` directly after the name of
a `fn`, `type` or `enum` definition (`unexpected-token`); a definition starting with `interface`,
`trait`, `protocol`, `impl`, `extension` (`unexpected-token`); a lone `|` where an expression
starts (`unexpected-character`), `=>` or `->` outside a match arm or a type (`unexpected-token`).

**Amends.** The same lambda text of section 5 ("no function written in place; ...") is the message
of every other spelling of a function written in place: `(a, b) => a < b` and `a -> a` (the `=>` or
`->`), `|| 3` (the `||`), `fn(a: Int) -> Bool { ... }` in an expression (the `fn`), and a `fn`
definition inside a body (the `fn`). The code is `unexpected-token` for all of them, `unexpected-character`
only for a lone `|`. The parser change is M2-17's.

## 3. Implementation rule: checking, dev mode, interface hash

**Checking.** The signature table (M2-16) holds every user `fn` with its resolved parameter types,
inout marks, labels and result, every variant with its field list, and the closed table. Typing a
bare name reads that table and nothing else. A row call runs the four-step walk of 1.3; a row with
several accepted types tests the first argument's type for membership after step 1. Equality and
order are rows like any other. The state check of 1.11 is a walk over the finite set of types the
state type reaches, memoised per type; the app-definition task (M2-32) runs it with every other app
rule, and the table only records the state type and the update function.

**Dev mode.** Built-in generic code (List, Map, Option, Result, Effect and the rows over them,
the fixed merge sort included) is shared runtime code: one body per row for every item type,
compiled with the toolchain, never with the program. It is driven by a layout record per type
(M4-22): size, alignment, copy, release, equality, and for Int, Float and String the order
function. The compiler emits, once per user record and enum type, a constant layout record and one
equality function the size of the type; these belong to the type's own slot and are regenerated
only when the type's interface hash changes. A user definition's slot (line 304) therefore never
holds collection code, and editing any user definition recompiles no collection code (M4-38's
reworded done-when, shown by the compile counter). `xs == ys` on `List<Point>` is a call into the
runtime's one list equality with Point's layout record, which calls Point's emitted equality.

A function value at run time is the definition's id, the index of its slot. A call through a value
is an indirect call through that slot; installing a new body swaps the slot's content and the id
stays (M4-37b). A variant with fields gets a constructor the compiler emits once, in a slot of the
same space. `==` on function values is an integer compare. The interpreter holds the same ids.

Release may make one copy of a collection routine per type (M6-14) and must give the same results
in the same order, the sort's sequence of `before` calls included; it keeps the id table.

**Interface hash.** The hash of a definition's signature after name resolution:

- a `fn`: for each parameter in order, its type, its inout mark, and its label when it is a
  labelled parameter (after `;`); then the result type. Positional parameter names are not in it:
  renaming one changes no caller.
- a record: field names, field types and default values, in declaration order (the layout).
- an enum: variant names, their field names and types, in order.
- an app: its keys and what they name, as lines 282 to 286 have it.
- types inside a signature: a built-in type by name with its arguments; a function type
  structurally; a named user type replaced by that type's interface hash **wherever it stands**
  (**tightens**): by value, inside a List, Map, Option, Result, Effect or function type. Line 285
  names "everything a user's compiled code is built from": a function whose parameter is
  `List<Point>` compiles Point's field offsets for `xs[0].x`, so Point's layout is in that
  function's hash even though the List holds Point behind a pointer. The over-approximation is
  small (a Point edit touches the definitions whose signatures reach Point) and it is the one rule
  that cannot miss.
- a recursive group: when hashing a type reaches a type already being hashed, the back reference
  is written as that type's name; the strongly connected group is hashed as one text and each
  member's hash is the group hash plus its own name. Finite, deterministic, and a change anywhere
  in the group changes every member, which is right because their layouts depend on each other.

Not in it: bodies, comments, source layout, positional parameter names, and nothing derived. There
is nothing to derive: every type has `==`, three built-in types have order, whether a `fn` can be a
value follows from the inout marks already hashed, and a function used as a value is a plain use
of its name, caught by name resolution in the user's body hash (line 283).

What changes what: a body edit, nothing. A signature edit, every direct user (M4-12). A field
added, reordered, retyped or given a new default in Point, every definition whose signature reaches
Point, transitively. A variant added, every definition whose signature reaches the enum, and every
match on it through the body hash. A label renamed, callers using it. A positional name renamed,
nothing.

## 5. New diagnostic codes

One new code. Check (status 1, at the named token; each message ends in the repair):

- `not-a-value` at the name: "NAME is a built-in and cannot be a value; write fn wrap(...) ->
  R { NAME(...) } and pass wrap" / "NAME is a built-in variant and cannot be a value; write fn
  NAME_of(value: T) -> R { NAME(value) }", with the name in lower case and T and R the types the
  position expects, left as the row's letters where no type is asked for (`then: Some` gives `some_of(value: String) -> Option<String> { Some(value) }`) / "NAME has an inout parameter and cannot be a
  value; give it a result instead of inout, or call it directly".

Kept and reused, with the messages fixed here:

- `type-mismatch`: a row on a type outside its set ("T has no order; compare a field: a.score >
  b.score" / "T has no order; write sort_by(&xs, before) with fn before(a: T, b: T) -> Bool" /
  "no + between String and Int; write an interpolation: \"{n}\"" / "no + on List; write extend(&xs, ys)" / "max
  takes two of one type; write 1.0"); interpolation of a type outside Int, Bool, String with the
  per-type fix of 1.6; a function value of the wrong shape, both types in the canonical spelling
  ("expected fn(Player, Player) -> Bool, found fn(Player, Player) -> Int (cmp)"); a state type
  that reaches a function type (1.11).
- `wrong-argument-count`: a name of function type bare where its own result type is expected
  ("NAME takes N arguments (labels), got 0; write NAME(...)"); a wrong count through a value.
- `wrong-label`: "drop the label: calls through a function value are positional".
- `unexpected-inout-mark` (M2-05): `&` through a value.
- `cannot-infer`: a row letter left free (1.3), M2-02 §5's text.
- `not-a-function`: "NAME is an Int, not a function".
- `duplicate-name`: a user definition named like a row or a built-in type, "len is a built-in;
  rename it".
- `unexpected-token` / `unexpected-character` (parse): the habit spellings of section 2, each with
  its fix: "Paka has no type parameters; write it for one type: fn first(xs: List<Int>) -> Int" /
  "Paka has no interfaces; write one function per type and pass it by name: sort_by(&xs, before)" /
  "no function written in place; write it at top level and pass its name: fn before(a: T, b: T) ->
  Bool { ... }; a local it would have used becomes a parameter or a field" / "no inout in a
  function type".

Why one code and not one per habit: M2-02 §1.2 refuses every habit spelling under
`unexpected-token` with the fix in the message, and a row on a wrong type is already
`type-mismatch` in M2-03; a code is for a situation whose fix shape no existing code describes,
which here is only "this name cannot be a value". Practice runs count habits by message text.

No trap kind is added; `stack` on a deep `==` is M2-05's.
