# M7-02 · The foreign-code model: declaration, named grant, process boundary, trusted list

Status: approved by the owner on 2026-10-26.

Base: the recorded M7-02 page in DECISIONS.md. All seven points **stand** as recommended there. The
page was written while M2-15 was open; M2-15 is approved since and fixes how an effect is written,
how it fails and when a grant is checked. Three lines are **amended** to follow it: a foreign effect
takes both `then:` and `or:`, a failure arrives through `or:` as a reason text, and a call without
its grant is refused when it is performed, as every effect is. One line is **amended** to follow
M4-06 as built: the approved-crates list is `.cargo/approved-crates.txt`, which becomes `TRUSTED`.

GENESIS 3.5: foreign code is outside every Paka guarantee, needs its own named grant and by default
runs in a separate process. A separate process is not a sandbox: the C code keeps the user's rights.

## 1. Points

**1.1 A C library is declared as a seventh definition kind.** `foreign Name { ... }` in the
program's source names what to compile or link, the header, and each callable C function. Its name
is the grant.

```
foreign Sum {
  source: "sum.c"
  header: "sum.h"
  Checksum(text: String) -> Int = "sum_bytes"
}
// in the app block:
//   grants: [ReadFiles, Console, Sum]
```

**1.2 Each C function is one effect.** A function line defines a typed effect with an Upper-case
name and the C symbol behind it. It is used like `ReadFile`: its own arguments, then `then:` and
`or:`, both required (M2-15 §1.3). **Amends** the page's sample, which had `then:` only.

```
fn update(s: inout Total, m: Msg) -> List<Effect<Msg>> {
  match m {
    Start(path)  => [ReadFile(path, then: Loaded, or: Failed)]
    Loaded(text) => [Checksum(text, then: Summed, or: Failed)]
    Summed(n)    => [Print("{n}"), Exit]
    Failed(why)  => [Print(why), ExitWith(5)]
  }
}
```

**1.3 Four plain types cross, copied.** Arguments are Int, Float, Bool and String; results are Int,
Float, Bool or nothing. Each maps to exactly one C type. No pointer, handle, struct or callback
crosses; a C function of another shape gets a few lines of wrapper C beside the program.

```
// Paka:  Checksum(text: String) -> Int = "sum_bytes"
int64_t sum_bytes(const char *text, int64_t text_len);
// Int = int64_t   Float = double   Bool = bool
// String = pointer + length, read-only, valid during the call,
//          with a zero byte after the end
```

**1.4 One host process per library, kept.** The first call starts one helper process (the host) for
that declaration. It stays up until the app ends and answers calls one at a time, in order, so the
library may keep state between calls.

```
app starts          no host
first Checksum      host for Sum is started, answers
later Checksum      the same host answers
app ends            host is killed
```

**1.5 Approving a foreign grant covers the declaration and its named files.** The grants record
holds the full text of the `foreign` declaration and the SHA-256 of every file it names. A system
library is covered by name only.

```
[1/1] examples/sum, app sum, grants
  approved: [ReadFiles, Console]
  now:      [ReadFiles, Console, Sum]
  + Sum: runs C code with all your rights, in a separate process
      source sum.c (41 lines)   header sum.h
      Checksum(text: String) -> Int = "sum_bytes"
Approve this item? yes / no:
```

**1.6 The host's unchecked code is generated C, built by the pinned clang.** The toolchain writes one
small C file per declaration that includes the header and calls each function with real C types,
plus one fixed C file for the pipe loop. clang builds them with warnings as errors; one line per
function fails the build unless the header's type is exactly the declared one. No crate is added.

```
#include "sum.h"
// fails to build unless the header's type is exactly this
static int64_t (*const f0)(const char *, int64_t) = sum_bytes;
static void call_0(paka_req *r, paka_rep *p) {
  paka_str text = paka_get_str(r);
  paka_put_int(p, f0(text.ptr, text.len));
}
```

**1.7 The trusted list is one owned text file, `TRUSTED`,** at the repository root, one line per
library: name, version, licence, where it runs, purpose. It is the approved-crates list M4-06 built
(`.cargo/approved-crates.txt`, name and version today), moved and widened, and made an owned file in
M7-01's store. **Amends** the page, which expected M4-06 to write `TRUSTED` itself.

```
# name      version    licence                         runs in    purpose
cranelift   0.136.3    Apache-2.0 WITH LLVM-exception  toolchain  dev-mode code
libc        system     -                               programs   C runtime
# drawing and text rows follow M5-08 and M5-10, still open
```

**Not chosen,** one line each (the page gives the reasons):

- 1.1: a manifest file beside the program; reading the C header for every function.
- 1.2: one generic call effect with the C name as text; a call written like a function.
- 1.3: one byte buffer each way; structs, pointers and handles.
- 1.4: a new process per call; in-process loading on request.
- 1.5: the grant name only; pinning system library bytes too.
- 1.6: a Rust host crate with hand-written `unsafe` stubs; an outside FFI crate such as libffi.
- 1.7: a table in toolchain source; a list derived from `vendor/`.

## 2. Rules that follow

**Declaration**

- Line kinds: `library:` names a system library to link; `source:` names C files to compile into the
  host; `header:` names the one header to include. At least one of the first two. Every name is a
  plain file name beside the program, with no path and no leading dash. A system header is reached
  by including it from the named header.
- A function line gives the effect name, typed parameters, the result and the C symbol. `then:` takes
  a function of the result (`then: Summed` where `Summed(n: Int)`); a function with no result takes a
  message value, as `WriteFile` does. `or:` takes a function of the reason text.
- The declaration's name is Upper-case and unique in the program's one pool of names (M4-48). It is
  a grant name beside `Console`, `ReadFiles` and `WriteFiles`.
- `foreign` is a reserved word, reserved now by a task of its own (M7-02a), ahead of M7-13.

**Calls and failures**

- A failure is a message, never a trap: the `or:` function gets one of four reasons: `no host` (it
  could not be built or started), `host died`, `timed out`, `bad reply`. A C function's own error code
  is an ordinary Int result.
- A call without its grant is refused when it is performed, as every ungranted effect is (M2-15
  §1.5), and no host is built or started. The checker does not prove which app reaches which effect.
- Each call has a fixed limit of 10 seconds. On expiry the host is killed, the call answers
  `timed out`, and the next call starts a fresh host. No per-library setting.
- The run loop waits for each answer, as it does for a file read; the answer joins the back of the
  queue (M2-15 §1.5). A slow call freezes a visual app's window until it answers or times out.
- No callbacks: C code cannot call into Paka or send messages on its own.

**The host**

- Interpreter and dev mode build and start it at the first call and cache the build, keyed by the
  declaration, its files and the compiler version. A released program carries its hosts beside the
  binary and never builds one (M7-03).
- It is built from copies of the named files in an empty directory, so an `#include` of an unnamed
  nearby file fails and nothing outside the approved hashes gets in.
- If it dies, the call in flight answers `host died` and the next call starts a new one; C-side state
  is lost. It is never rolled back with a trapping handler, nor migrated.
- Wire format: the host's standard input and output are the pipe. It first moves them aside, points
  its standard output at standard error and its standard input at nothing, so a library that prints
  or reads cannot corrupt the protocol. Frames are length-prefixed: a function number, then Int as 8
  bytes, Float as its 8 IEEE bytes, Bool as 1 byte, String as length plus bytes. Exact layout is
  M7-14's.
- Dev-mode swaps: the host survives a swap of Paka code. An edit to the declaration or its files
  rebuilds and restarts it; calls in flight answer `host died`.

**Approval and trust**

- Before approval, dev mode and the interpreter run a newly listed foreign grant (M7-01, stopped at
  merge and release), so agent-written C runs with the owner's rights there. This adds nothing an
  agent with a shell cannot already do. The merge gate never compiles C; release refuses until the
  grant is approved.
- Examples never start a host. Function examples only inspect the effects `update` returns; UI
  examples drop an allowed effect and treat a disallowed one as live (M5-06).
- Nothing in GENESIS 3.5 is claimed for the C side. A foreign result is outside input, like a file's
  contents.
- Libraries on the trusted list run inside the program's process and need no grant. Every `foreign`
  declaration runs in its own process and needs its grant. User-declared C cannot be marked trusted.
- Adding or updating a vendored or linked library, toolchain crates included, needs the owner's
  signature on `TRUSTED`. One list serves the vendoring check, the M7-16 test and the notices file.

**Owner must still**

- Approve the first `TRUSTED` through `paka approve` when M7-16 lands. Downloads of the libraries
  themselves stay with the tasks that fetch them and still need the owner's yes there.
