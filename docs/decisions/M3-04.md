# M3-04 · Counted, reserve and practice tasks

Status: approved by the owner on 2026-10-14.

Base: the recorded M3-04 page in DECISIONS.md. Points 1.2 (written fresh) and 1.3 (many exact rules)
**stand**. Point 1.1 (task count) is **amended** from 30 to 20 tasks to fit the usage cap of M3-02
§1.8. Points 1.4 (tags) and 1.5 (spread) are **amended** to follow. The task outlines below are taken
from the recorded list; ten recorded tasks are left out (§3).

Every task follows the M2-01 limits: ASCII input; files under 200 lines; every value within
±(2^53 − 1); no float result on a rounding tie; recursion under 200 deep; a fixed number of arguments;
no standard input. Every task has at least one error case with an exact message on standard output
and exit status 20. Missing files are tested only in file-tool tasks.

## 1. Points

### 1.1 How many tasks? (amends)

**20 tasks: 14 counted, 4 reserve, 2 practice** (recommended). 56 counted runs per language (M3-02
§1.4).

- Why: each task costs a long statement, 10 hand-worked cases and three reference solutions, and each
  counted task costs about 0.7 million tokens of counted runs. Two per class still covers every class.
- Not chosen: 30 tasks, 22 counted (the recorded list; about 30 million tokens in all, and half again
  the writing) · 11 tasks, 7 counted (the pilot of M3-02 §1.8; one per class, and the only firm answer
  is stop on a gross loss).
- Look again when: more than 4 tasks need swapping (M3-03 §1.4).

### 1.2 Written fresh or taken from public sets? (stands)

**Written fresh** (recommended). No solution can be recalled.

- Not chosen: public exercise sets (the known languages pass by recall, and it needs a download).

### 1.3 What makes a task hard? (stands)

**Many exact rules** (recommended). Ordinary work with a long, exact statement: tie-breaks, rounding,
error cases and an output format, checked by hidden cases on the edges. Reference solutions run 100 to
300 lines.

- Not chosen: classic hard algorithms (pass or fail by recall) · large programs (long, costly runs and
  clumsy whole-file edits).

### 1.4 Does the list include tasks where Paka is expected to pay? (amends the number)

**Yes, 5 of 14 tagged** (recommended), about a third, as recorded. The tags are published before the
runs: a tree type that contains itself (P3), in-place grid changes (G2), mixed Int and Float maths
(N2), and two file tools (F1, F2).

- Lost from the recorded tags: a priority queue (R2, left out) and a custom sort order (T3, now first
  in the reserve). The report says that the priority-queue cost is not measured.
- Not chosen: neutral tasks only (hides the costs the experiment should see) · spread by class only
  (nobody can tell afterwards whether the list was kind to Paka).

### 1.5 How are the counted tasks spread over the seven M2-01 classes? (amends)

**Two per class** (recommended).

```
text processing 2 | parsing and interpreters 2 | state machines 2
grids and dynamic programming 2 | graphs by list index 2
integer and float reports 2 | file tools 2
```

- Not chosen: weighted to everyday work (more text, report and file tasks; the classes most likely to
  be passed first try by every language) · three in the classes that separate best (needs evidence
  that does not exist yet).

## 2. The tasks

Each entry: outline; what it stresses; why Rust or TypeScript may fail; the Paka means that make it
expressible in headless Paka as built in M2. Every task reads its input with `ReadFile`, prints with
`Print` and ends with `Exit` or `ExitWith(20)`.

### Counted (14)

| Id | Class | Tag |
|---|---|---|
| T1 wrap and justify | 1 text processing | |
| T2 column table | 1 text processing | |
| P1 calculator | 2 parsing and interpreters | |
| P3 nested config | 2 parsing and interpreters | tagged |
| S2 ledger with holds | 3 state machines | |
| S3 comment stripper | 3 state machines | |
| G1 line diff | 4 grids and dynamic programming | |
| G2 falling sand | 4 grids and dynamic programming | tagged |
| R1 build order | 5 graphs by list index | |
| R3 islands and bridges | 5 graphs by list index | |
| N1 invoice | 6 integer and float reports | |
| N2 group statistics | 6 integer and float reports | tagged |
| F1 include resolver | 7 file tools | tagged |
| F2 split by key | 7 file tools | tagged |

- **T1 wrap and justify.** Wrap paragraphs to a given width, spread extra spaces left first, split
  words longer than the width. Stresses index arithmetic. Rust: unsigned underflow and off-by-one
  widths. TypeScript: off-by-one spacing that no type catches. Paka: `words`, `len`, `repeat`, string
  joins.
- **T2 column table.** Quoted, delimited rows to an aligned table; numeric columns right-aligned with
  a total line. Stresses telling numbers from text. Rust: parsing mixed columns. TypeScript:
  `Number("")` and `"1e3"` count as numbers. Paka: `chars` with a quote state, `parse_int`,
  `pad_left`, `pad_right`.
- **P1 calculator.** Integer expressions with precedence and brackets, variables across lines,
  division truncating toward zero, errors with a column. Stresses a recursive parser. Rust: boxing a
  type that contains itself, error plumbing. TypeScript: `/` gives fractions. Paka: an `inout`
  position, `Result` with `?`, a `Map<String, Int>` of variables, Int `/`.
- **P3 nested config** (tagged). Parse a brace-nested format with strings, escapes and lists; print
  sorted flat key paths; report the exact first error. Stresses a tree type that contains itself. Rust:
  ownership of the tree. TypeScript: union types under strict mode. Paka:
  `enum Value { Text(s: String), Items(list: List<Value>), Table(map: Map<String, Value>) }`, legal
  because the enum has another variant; `keys` gives sorted order.
- **S2 ledger with holds.** Open, deposit, hold, capture, release and transfer, with rejection rules,
  in whole cents. Stresses many rules on shared state. Rust: two accounts changed at once.
  TypeScript: cents parsed as fractions. Paka: a `Map<String, Account>` of records changed through
  `&accounts[name]`; a transfer binds one side first, as the overlap rule requires.
- **S3 comment stripper.** Remove comments from C-like text with strings, escapes, nested block
  comments and line joins. Stresses a character state machine. Rust: look-ahead over characters.
  TypeScript: silent reads past the end. Paka: `chars`, a `while` loop over positions, an enum state.
- **G1 line diff.** Longest-common-subsequence diff of two files with a fixed tie-break and hunk
  format. Stresses walking back through a table. Rust: unsigned index minus one. TypeScript: rows that
  share one array. Paka: two `ReadFile` steps, a `List<List<Int>>` table, `lines`.
- **G2 falling sand** (tagged). Move grains on a grid under fixed rules until nothing moves. Stresses
  in-place grid changes. Rust: reading and writing the grid at once. TypeScript: shared rows. Paka: a
  `List<List<String>>` grid assigned by index; moving a grain reads the cell into a `let` first.
- **R1 build order.** A dependency file to an order with an ASCII tie-break; on a cycle print it in a
  fixed form and exit 20. Stresses a graph kept as lists by index. Rust: name-to-index maps and
  borrowing. TypeScript: `Map` lookups that may be `undefined`. Paka: `Map<String, Int>` to positions,
  `List<List<Int>>` edges, a scan for the smallest ready name.
- **R3 islands and bridges.** Connected groups and the links whose loss splits one; inputs are small,
  so the plain method removes each link, recounts and puts it back. Stresses search with state
  restored between tries, and it is the class 5 task that changes the graph during the algorithm
  (M2-01). Rust: search over shared arrays. TypeScript: stale state between tries. Paka: `remove_at` and
  `insert` on `&g.adj[a]` inside a `while` walk, `List<Bool>` seen.
- **N1 invoice.** Quantities, cent prices, percentage discounts, tax in hundredths of a percent, round
  half up per line. Stresses exact money rounding. TypeScript: fractional arithmetic on money. Rust:
  rounding negative values. Paka: Int arithmetic only, `/` and `%`.
- **N2 group statistics** (tagged). Mean, median and standard deviation per group to two decimals,
  with rules for empty and single groups. Stresses mixed Int and Float. Rust: ordering floats.
  TypeScript: the default sort orders numbers as text. Paka: explicit `to_float` steps, `sort`, `sqrt`,
  `fixed(x, digits: 2)`.
- **F1 include resolver** (tagged). Follow nested include lines, read each file once, name the chain on
  a cycle, write the merged file. The number of reads is known only at run time; a missing file is an
  error case. Stresses chained file steps. Rust: error handling across many file steps. TypeScript:
  missing-file errors thrown instead of reported. Paka: `ReadFile` chained through `update`, the
  waiting path kept in state because answers carry no path, `WriteFile`, `ReadFiles` and `WriteFiles`.
- **F2 split by key** (tagged). One input file to one output file per key plus an index file; file
  names are worked out at run time. Stresses many writes and exact names. Rust: error plumbing over many
  writes. TypeScript: write errors thrown. Paka: one `update` returns a `WriteFile` per key, with the
  count of answers kept in state.

### Reserve, in swap order (4)

A swapped task is replaced by the unused reserve task of its class, else the next in this order.

- **T3 natural sort** (text, tagged). Sort lines with digit runs compared as numbers, case-blind,
  stable. Stresses a custom sort order. TypeScript: the default sort is by text. Rust: a comparator
  over mixed chunks. Paka: `sort_by` with a named `fn`; the sort is stable.
- **V2 car-park billing** (state machines). Fees from entry and exit events with tariff bands and a
  daily cap. Stresses rule order and minute arithmetic. Rust: a map entry changed while read.
  TypeScript: division gives fractions. Paka: `Map<String, Int>` of entry minutes, Int arithmetic.
- **N3 calendar** (reports). Days between dates from 1900 to 2100, weekday, add working days skipping
  listed holidays. Stresses date arithmetic. TypeScript: the built-in date type counts months from zero
  and rolls bad days over. Rust: no date type, all by hand. Paka: Int arithmetic, `Map<Int, Bool>`
  of holidays.
- **V6 pack and unpack** (file tools, tagged). Pack several files into one text archive and unpack it.
  Stresses many file steps and exact framing. Rust: error plumbing. TypeScript: thrown missing-file
  errors. Paka: chained `ReadFile`, one `WriteFile` per entry, a length line per entry.

### Practice (2)

Used only to shake down the harness and the reference wording. Their results never enter the verdict.

- **X1 word counts** (text). The top N words with tie rules. Stresses sorting by two keys. Rust: a
  two-key comparator. TypeScript: the default text sort. Paka: `words`, a count `Map`, `sort_by`.
- **X2 numbered join** (file tools). Join two files with line numbers into a written file; a missing
  file is an error. Stresses the written-file check and the error path. Rust: error plumbing.
  TypeScript: a thrown missing-file error. Paka: two `ReadFile` steps, the `or:` reason, `WriteFile`,
  `ExitWith(20)`.

## 3. Left out of the recorded list, and why

- T4 run-length codec, P2 stack machine: each class keeps two; these overlap with P1 and S3.
- S1 lift simulation and G3 packing: the recorded page says they fail on rule order or ties in any
  language, so they separate the languages least.
- R2 cheapest route: a third graph task. Its priority-queue tag is lost; the report says so.
- F3 three-way merge: a third file tool; F1 and F2 already cover chained reads and run-time names.
- V1, V3, V4, V5: the reserve shrinks from 6 to 4. The kept reserve covers the classes with tagged
  tasks first.

## 4. Settled without asking

- Cases per task: 2 visible and 8 hidden, each with written hand working: 200 cases in all.
- Error status: 20 in every task.
- Tasks outside every class: none.
- Statements describe arguments, files, standard output and exit status only. They name no language
  feature and no grant.
- Tags under swaps: a reserve task brings its own tag. The report gives the final number of tagged
  tasks.
- The outlines are the approved list. M3-11 writes the full statements and cases; it may sharpen rules
  but not change what a task stresses or its class.
