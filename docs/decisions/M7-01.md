# M7-01 · How the owner writes and approves examples and grant changes

Status: draft, awaiting the owner's approval.

Base: the recorded M7-01 page in DECISIONS.md. All seven points **stand** as recommended there. The
page was written before M2-06, M2-15, M4-03, M4-48 and M5-06 were approved; none of them changes a
point. Examples keep M2-06's form, grants stay M2-15's names, programs stay paths (M4-48), and the
pending items ride in edit replies as M4-03's optional field.

GENESIS 3.6: people own acceptance examples and grant lists, and the toolchain refuses merge and
release when one differs from the approved version. This record says how that approval is made so
no agent can make it.

## 1. Points

**1.1 An approval is a signature from the owner's key.** `paka approve` signs the store by running
the system's `ssh-keygen -Y sign` with a key only the owner can unlock; the gate checks it with
`ssh-keygen -Y verify`. No crate, no download, no hand-written cryptography.

```
$ paka approve examples/wc
...
Approve this item? yes / no: yes
Enter passphrase for ~/.config/paka/approval_key:
approvals: serial 8, signed
```

**1.2 One signed file at the repository root.** `approvals` holds a serial number and the approved
text of every item, keyed by program path; `approvals.sig` signs the whole file; `approvals.pub` is
the owner's public key. The same file is the list of gated programs.

```
serial 8
grants examples/wc wc [ReadFiles, Console]
grants examples/counter counter []
example examples/counter dec_stops_at_zero {
  var s = Counter {}
  update(&s, Dec)
  s.count == 0
}
file .github/workflows/gate.yml 31
  (the file's 31 lines follow, indented)
```

**1.3 The gate runs from the target branch.** The gate job uses `pull_request_target`, so the
workflow file comes from the branch merged into (`development` or `main`). It builds paka from that
branch and runs it, with a read-only token, on the pull request as merged, using that branch's key
and store as the old state. It is a required check on both branches.

```
# .github/workflows/gate.yml
# on: pull_request_target    permissions: contents: read
# base   = checkout of the target branch
# merged = checkout of the pull request merged into it
base/target/release/paka gate merged --base base
```

**1.4 An example becomes human-owned when the owner adopts it by name.** The owner says in words what
should hold, the agent writes an ordinary `example`, the owner reads it and signs. No new syntax; the
label lives only in the store.

```
$ paka examples examples/counter
dec_stops_at_zero   agent-written   pass
$ paka approve examples/counter --adopt dec_stops_at_zero
```

**1.5 An approval covers the example's own text.** Editing, renaming or deleting it needs approval;
editing what it calls does not. The approve screen lists what it uses as not covered.

**1.6 An agent's change is stopped at merge and release.** The edit is stored and runs in dev mode;
the edit result and the gate list each pending item; merge and release are refused until the owner
approves.

```
{"pending": [
  {"kind": "grants", "program": "examples/wc", "app": "wc",
   "approved": ["Console"], "found": ["Console", "ReadFiles"]},
  {"kind": "example", "program": "examples/counter",
   "name": "dec_stops_at_zero", "change": "edited"}],
 "blocks": ["merge", "release"],
 "next": "The owner runs: paka approve. Or revert the change."}
```

**1.7 The owner sees one item at a time, old and new,** each with its own yes or no, in words only the
toolchain writes. A grant change shows the approved list, the new list and a fixed one-line meaning
per grant. An example change shows the whole new body with changed lines marked, its status and the
names it uses.

```
[1/2] examples/wc, app wc, grants
  approved: [Console]      now: [Console, ReadFiles]
  + ReadFiles: may read any file you can read
Approve this item? yes / no: yes
[2/2] examples/counter, example dec_stops_at_zero, edited, now: pass
    var s = Counter {}
    update(&s, Dec)
  - s.count == 1
  + s.count == 0
  uses: update, Counter (not covered by this approval)
Approve this item? yes / no:
```

## 2. Rules that follow

**The store**

- Labels live only in the store. An example is human-owned when the store has a record for its
  program and name; otherwise it is agent-written. Source text carries no label.
- The store is the file `approvals` in the nearest directory at or above the program; record paths
  are relative to it. Listing, Edit result, approve, gate and release all use this one rule.
  `paka build` never reads it.
- Three record kinds: `grants` (one app's list), `example` (canonical text, comments included, M4-47
  layout), `file` (a path and the file's text). C files named by a `foreign` declaration are held as
  SHA-256 inside the grants record (M7-02).
- A program is gated once the store has a record for its path; the first approval of its grant list,
  even `[]`, puts it there. Test and conformance programs have no records. A program with no records
  can merge, but the shipping command (M7-03) refuses it.
- Every app in a gated program needs a grants record. Lists are compared as sets; an added and a
  removed grant are both pending items. A rename or deletion of a human-owned example is pending;
  the owner approves the removal or the agent puts it back.
- Owned files: every file under `.github/workflows/` and `TRUSTED` (M7-02). The gate refuses when one
  differs, is missing, or a workflow file has no record.
- The serial is a counter on the first line. When the merged store differs from the target branch's,
  its serial must be higher, so an old signed store cannot be put back. `paka approve` starts from the
  working tree's store, refuses if it does not verify, and adds one.

**The key and signing**

- The gate refuses any pull request that changes `approvals.pub`. To add or replace the key, the owner
  lifts the branch rule once by hand, commits the key and a store signed with it, and puts the rule
  back. The first key goes in this way, before the check is required.
- Verify uses the target branch's `approvals.pub`, one fixed signer name and the namespace
  `paka-approval`; never the mode that checks a signature without checking whose it is.
- `paka approve` runs `/usr/bin/ssh-keygen` by that fixed path with an empty environment, so no key
  agent or helper takes part. ssh-keygen asks for the passphrase itself; paka never sees it. The key
  path defaults to `~/.config/paka/approval_key`; `--key` names another.
- `paka approve` reads yes or no from a terminal only, else exits with usage status 2. No flag answers
  for the owner.
- The owner approves with a paka built from the branch the pull request targets, in a checkout no
  agent works in. The command rewrites `approvals` and `approvals.sig` on the pull request's branch;
  either side may commit them, since the signature is the proof.

**What each side sees**

- The screen shows every character outside printable ASCII in escaped form, so a comment or string
  cannot hide lines, move the cursor or pass one letter off as another.
- A refused agent: `paka gate` exits 1 and lists each pending or failing item in the edit result's
  shape, as text (one line per item) or JSON. The last line says: revert the change, or ask the owner
  to run `paka approve`.
- The Edit tool compares against the store to report and does not check the signature. Run loops
  never read the store.

**The gate**

- It checks the signature and serial, every record against the source, every workflow file, and that
  every human-owned example of every gated program passes in the interpreter. A failing, trapped or
  unfinished one refuses; agent-written examples never refuse. The CI job has a time limit.
- The job compiles no C, runs no script and runs no compiled code from the pull request: only Paka
  source in the interpreter, where code has no authority of its own (GENESIS 3.5).
- Approving an example that fails is allowed: approval says it is the right goal; the gate still
  refuses the merge until it passes. `paka approve <program> --drop <name>` gives up ownership after
  the same screen and signature.
- A pass is judged against the target branch as it was when the job ran; two passing pull requests
  can still break an example together. The shipping command runs the gate again. GitHub's 'branch
  must be up to date' setting is left off.
- On the owner's machine, gate and release use the working tree's `approvals.pub` and have no target
  serial to compare. This catches honest mistakes; the required check on GitHub is the one that
  cannot be bypassed, so a release counts only from a clean checkout of `main`.
- Not stopped: a program with the owner's rights that records the passphrase or swaps the tools; a
  change to the gate's own Rust code, which review and the owner's merge guard. The signature stops
  an agent that is wrong, misled or steered by hostile input.

**Owner must still**

- Create a key used for nothing else, with a passphrase, outside `~/.ssh`:
  `ssh-keygen -t ed25519 -f ~/.config/paka/approval_key`. Never add it to a key agent, never let the
  desktop remember the passphrase, never give it to an agent. Commit `approvals.pub` yourself before
  the gate becomes required and check by eye that it is yours. Confirm `ssh-keygen` exists on the CI
  image.
- Mark the check `gate` as required, for administrators too and with no bypass: on `development` once
  M7-10's workflow is there, on `main` after the M7 merge. Before the gate counts as proof, agents work
  under a GitHub account of their own with write access only.
- Approve each workflow file as an owned file in the first approval.
