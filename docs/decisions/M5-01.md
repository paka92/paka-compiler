# M5-01 · What a view is and what its body may contain

Status: approved by the owner on 2026-10-13.

Base: the recorded M5-01 page in DECISIONS.md. All seven points **stand** as recommended there.

## 1. Points

**1.1 Children: a child block after the element.** An element that holds children takes a brace
block after its arguments. Each element line in it adds one child, in order.

```
view counter_view(s: Counter) -> View<Msg> {
  Col(gap: 8) {
    Text("{s.count}")
    Row(gap: 8) {
      Button("-", on: Dec)
      Button("+", on: Inc)
    }
    ??reset
  }
}
```

**1.2 Child block contents: `let`, `if`, `for`, `match`.** Besides element lines, view calls and
holes, a child block may hold `let`, `if`/`else`, `for` and `match`; their bodies are child blocks
too. No `var`, assignment, `while`, `break`, `continue` or `return`. An arm that adds nothing is
written `Done => {}`.

```
view todo_view(s: Todos) -> View<Msg> {
  Col(gap: 8) {
    Input(s.draft, on_change: Draft, key: "new")
    Button("Add", on: Add)
    if len(s.items) == 0 { Text("Nothing to do") }
    for t in s.items {
      todo_row(t, key: t.id)
    }
  }
}
```

**1.3 Elements: only in views, only in place.** Elements, child blocks and view calls appear only in
a view, as its result or as a line of a child block. A `fn` cannot build one, and an element cannot
go in a `let`, a list, a state field or an argument. `View<Msg>` is only ever a view's result type.

**1.4 One root.** A view body is zero or more `let` lines and then one element expression: an
element, a view call, a hole, or an `if`/`else` or `match` whose every branch ends in one.

**1.5 View calls: plain call, same messages.** A view is called by its lower-case name wherever an
element may stand. The called view's result type must be the caller's `View<Msg>` exactly, so one
app has one message enum. A view may call itself.

**1.6 Launch: defaults, then optional start.** The first state is the state type built from its
field defaults, so a visual app's state type is a record with a default on every field. If the app
has a `start:` line, that message is handled next. Then the view runs and the window opens.

```
type Todos { draft: String = "", items: List<Todo> = [] }

app todo {
  state:  Todos
  update: update
  view:   todo_view
  grants: []
}
```

**1.7 Closing the window ends the app** with status 0. No message is sent; effects not yet performed
are dropped. An `Exit` effect also ends it.

## 2. Rules that follow

- `view` is a definition kind. It is pure: it reads its arguments, calls functions and views, and
  gives one element. It cannot change state or ask for effects.
- The signature is written in full: `view name(params) -> View<Msg>`.
- The app's view takes exactly one parameter, the state, read-only. Other views take read-only
  parameters under M2-02. No `inout` and no `&` in a view.
- The app's view takes the state type and gives `View<M>`, where M is `update`'s message type.
- An element call always writes its parentheses, and writes a child block if and only if it takes
  children; a container writes its block even when empty (`Col() {}`).
- A child block is read only where an element may stand, so `if len(xs) == 0 {` reads as before.
- An event argument takes a message value (`on: Dec`); an event that carries data takes a variant
  name. No closures.
- `??name` where an element may stand draws a labelled placeholder. A hole elsewhere in a view traps.
- A trap in a view keeps the last frame. If the first frame traps, the window shows one error node.
- Elements are Upper-case built-in names in the one pool, taken from every program once M5-12 adds
  them.
- `update` has either form: no result, or `-> List<Effect<Msg>>`.
- The view runs after launch, after every handler that did not trap, and after every code swap;
  never inside a handler.
- If the start handler traps, the state stays at its defaults and the first frame is drawn from them.
- The window title is the app's name. A view may recurse; running out of stack is a trap in the view.
