# M5-07 · How migrate and explicit reset are written and applied

Status: approved by the owner on 2026-10-13.

Base: the recorded M5-07 page in DECISIONS.md. All seven points **stand** as recommended there.

## 1. Points

**1.1 Carried by the edit.** The Edit call has one optional state field holding `reset` or the text
of one migrate. It belongs to the waiting change set, is used once at the swap and is then thrown
away. It is never written to the source. Field names are M4-03's.

```
replace: type Counter { count: Int = 0, step: Int = 1 }
state:   migrate(old: Counter) -> Counter {
           Counter { count: old.count }
         }
```

**1.2 Any change but defaults counts.** The stored types are the state type and every user type
reached from it through fields, list items, map keys and values, enum payloads, shared values and
pool items. The state has changed if the app names another state type or any stored type differs in
anything but defaults, comments and layout. Renames, reordered fields and added variants count.

**1.3 One migrate for the whole state.** It takes the old state value and gives the new one. A
changed type that contains itself cannot be converted and takes a reset.

```
migrate(old: Todos) -> Todos {
  var items: List<Todo> = []
  for t in old.items {
    append(&items, Todo { id: t.id, title: t.title, done: t.done, note: "" })
  }
  Todos { draft: old.draft, items: items }
}
```

**1.4 Parameter old, result new.** In `migrate(old: T) -> U` the parameter's type is read in the
running version and the result's in the new one. Anything read out of `old` has its old type; any
type name written in the body is new. An unchanged type is the same on both sides.

**1.5 Refused at the edit.** While a visual app runs, an edit that changes a stored type is refused,
source untouched, unless it carries a choice or the waiting change set has one. The refusal names
the changed types and how each differs. A later choice replaces an earlier one; a call may carry a
choice alone.

**1.6 A failed migrate keeps the old version running.** It is checked with the change set; an error
blocks the install. It runs on the old state at the swap. If it traps, nothing is installed, the
change set waits, and the trap is reported. It is not retried by itself.

**1.7 Reset is a launch again in the same window:** state from field defaults, the `start:`
message handled again if any, element state and focus dropped, then the view. It may come with any
edit or alone.

## 2. Rules that follow

- Old is the running version: the last one installed.
- A migrate is `migrate(name: OldState) -> NewState { body }`: no name, one read-only parameter,
  pure, ending in the new state. It may call the new version's functions on new or unchanged values.
- An old value of a changed type can only be taken apart: fields read, matched on every old variant,
  looped over or indexed. It cannot be passed to a function, compared or printed.
- Exit-check sample: from `Counter` without `step`, adding `step: Int = 1` bare is refused; with
  `state: reset` it installs and shows 0; with the migrate above the count stays.
- After a good migrate, code and state swap together between handlers and frames. The start message
  is not resent; element state and focus follow M5-02's matching.
- A hole in a migrate is allowed; reaching it is a trap. A migrate that does not finish is stopped as
  M4-04 rules and counts as trapped.
- A migrate with nothing changed is accepted and runs once.
- The edit-time rule applies only while a visual app runs in dev mode. With nothing running a state
  field is ignored and the result says so.
- A stored-type change that reaches the swap with no choice waits; the result says a choice is
  missing, and a call carrying only a choice releases it.
- A waiting choice is dropped when the app ends.
- Editing the app block's `state:` line is a state type change. Adding a first `view:` is not.
- The edit result says one of: state kept, migrated, reset, refused for a missing choice, not
  installed for a missing choice, or migrate trapped. A waiting migrate a later edit made wrong is
  listed among what that edit broke.
- Adding a message needs no choice unless the state holds messages. A queued input whose variant is
  gone or changed is dropped and reported. A reset empties the queue and drops later answers to old
  effects.
- Interpreter and dev mode follow the same rules. Release mode has no swap.
- The toolchain never migrates by itself, even for an added field with a default.
- An edit that changes a field's meaning without changing its type keeps the state; a reset can be
  sent with it.
