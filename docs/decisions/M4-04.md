# M4-04 · Where dev-mode code runs and how a run is stopped

Status: approved by the owner on 2026-10-15.

Base: no options page was recorded in DECISIONS.md. Section 1 states the three options and the
recommended pick, which **stands**; section 2 gives the rules that follow.

## 1. Choice

**One runner process per server** (recommended). `paka serve` starts a child process, the same
`paka` binary in a hidden runner mode, through `std::process`. The runner holds the Cranelift back
end and all compiled code. The server parses and checks; for each installed definition it sends the
checked core form down the runner's standard input, and the runner compiles it and swaps it in. Runs
happen in the runner; replies come back on its standard output.

- Why: A crash in generated code or in the runtime kills only the runner; the server answers the
  request with a trap or a `stopped` result and starts a new runner. Compiled code survives between
  runs, so a swap costs one compile (M4-01b: 2.1 ms warm p95 for the largest class) plus a pipe
  round trip.
- Not chosen: **In-process** (the server compiles and runs on its own thread). Fastest, with no pipe,
  but a wrong pointer in generated code or a runtime bug takes the server down, against the task's
  first rule. **Forked** (fork the server for each run). Clean memory per run and code inherited, but
  `fork` is not in the standard library, forking a threaded process is unsafe in general, and code
  compiled in a child is lost when it ends, so a visual app could not be swapped in place.
- Look again when: The pipe round trip shows up in M4-44's profile, or M5 needs two apps live at once.

## 2. Rules that follow

**Traps.** Generated code never faults on purpose. Every check (bounds, overflow, division, stack
depth, memory cap) is an explicit test that returns a trap status (M4-05). No signal handler is
installed. A fault that still happens is a bug: the runner dies, the server reports the run as
`stopped: "crash"` and restarts the runner.

**Stuck handlers.** Compiled code polls one interrupt flag at every loop head and function entry: a
load and a branch. The runner sets the flag itself at the run's `limit_ms`, from a watcher thread;
the run then ends with `stopped: "time"`. If the runner does not answer 100 ms after the deadline,
the server kills it with `Child::kill` and restarts it.

**Memory.** Each run allocates from the runner's heap and frees everything at its end, so nothing
leaks into the next run. A per-run cap is checked by the allocator and ends the run with a memory
trap. Compiled code lives until its definition is replaced; replaced code is freed when no run is
using it.

**Restart.** A new runner receives every installed definition's core form and compiles them all
before the next run. This is a cold start, paid only after a crash or a kill; the server reports it
in the reply that caused it.

**The 100 ms budget.** Edit to running: check in the server, one pipe write, one compile, one slot
swap, and the run. M4-44 measures it from request written to reply read; the pipe is part of the
measurement.

**Swaps.** Each definition is called through a slot table. A swap rewrites one slot between
messages, never during a handler, so a running handler always finishes on the code it started with.

**Visual apps (M5).** The app's state lives in the runner's heap and stays there while code is
swapped. If an edit changes the state's type, the state cannot be kept; M5 decides between a
migration and a fresh start.

**Unsafe.** Calling compiled code and the slot table need unsafe. It lives in one crate, the
installer, and only the runner uses it; the server has none.

**C libraries.** M7's separate process for C calls is a further child of the runner, not of the
server, so a crashing library ends one call, never the runner.
