# M2-15 · Headless apps: first message, effects, grants, ending, effect failure, standard input and handler traps: decision

Base: the recorded M2-15 page in DECISIONS.md, written out as one run loop with every line of
output fixed byte for byte, the reason texts tied to host errors, and the M1 cases that change
listed with their new expectations. All eight recorded picks stand. One settled line is amended
because two earlier records force it, marked **amends**: the status a program may choose is 0 or
5 to 255, not 0 or 4 to 255, since M1-14.6 and M2-06 §1.7 reserve 4 for internal errors. Four
settled lines are made exact where they were loose, marked **fixes**: the `ended without Exit`
line is bare; a `then:` or `or:` function is applied when its answer reaches the front of the
queue, not when the file effect is performed; `Print` writes to the process's own descriptor 1,
and SIGXFSZ is ignored next to SIGPIPE; a literal exit status outside the range is a check error.

The one idea under everything (paper lines 165 to 167): a handler returns effects as data, the
runtime performs the granted ones in order, and every answer is a message. There is one queue, one
handler, no callback that runs inside a handler, and nothing a program can observe but its own
messages, its standard output and its exit status.

## 1. Resolutions, point by point

### 1.1 The app form

```
app NAME {
  state:  S          // optional; a record type with a default on every field
  start:  Start      // required; a variant of the message enum
  update: update     // required; the handler
  grants: [Console]  // required; may be []
}
```

One key per line, each at most once, order without meaning. An app with no `view:` is headless
(paper line 126). After the duplicate-key and missing-key tests, the keys are checked in the order
`state`, `update`, `start`, `grants`, whatever the written order. `state:` names a record type built
from its field defaults (`Tally {}`, M5-01.6); no type reachable from it may hold a function type
(M2-09 §1.11, `type-mismatch` at the value). `start:` names a variant of the enum the handler takes;
its fields, if any, are all `String` (1.4). `update:` names a function of one of two shapes (1.2).
`grants:` lists names from 1.5.

A program with no app checks (`paka check` status 0, `paka examples` runs its examples); `paka run`
and `paka build` refuse it with `main.paka: error[no-app]`, status 1, after the program has been
checked. More than one app stays `multiple-apps` at the second app's name. This is the rule
spec/m1.md §8 already carries as decided.

### 1.2 The handler

```
fn update(s: inout S, m: Msg) -> List<Effect<Msg>>     // with state:
fn update(m: Msg) -> List<Effect<Msg>>                 // without state:
```

Checked at the `update:` value: the named function must have exactly this shape for the app's
`state:` and message enum, else `bad-update-signature` (M2-02 §4). The message enum is the type of
the last parameter; `start:` must name one of its variants, else `bad-start`. The name `update` is
not reserved and a function no app names is an ordinary function, so the paper's counter, whose
`update` returns nothing, checks in a program with no app.

The handler runs to its end before any of its effects is performed. A trap inside it performs
none of them (1.9).

### 1.3 Effects and grants

`Effect<Msg>` is a built-in enum with five variants, `Msg` being the app's message enum:

| effect | fields | needs | answer |
|---|---|---|---|
| `Print(text: String)` | bare | `Console` | none |
| `ReadFile(path: String; then: fn(String) -> Msg, or: fn(String) -> Msg)` | one bare, two labelled, both required | `ReadFiles` | `then(text)` or `or(reason)` |
| `WriteFile(path: String, text: String; then: Msg, or: fn(String) -> Msg)` | two bare, two labelled, both required | `WriteFiles` | `then` or `or(reason)` |
| `Exit` | none; `Exit()` is `wrong-argument-count` (M2-02 §1.9) | none | none |
| `ExitWith(status: Int)` | bare | none | none |

A field takes a function when the answer carries data: `then:` of `ReadFile` gets the text, every
`or:` gets the reason. `then:` of `WriteFile` is a message value, so it may carry context
(`then: Wrote(name)`). A function value here is a named `fn` or a variant with one `String` field,
passed by name (M2-09 §1.10, `then: Loaded` where `Loaded(text: String)`).

Effects are plain values: any function may build them, `==` compares them (M2-09 §1.4), and an
example may end in `update(&s, Start("a.txt")) == [ReadFile("a.txt", then: Loaded, or: Failed)]`.
Only the list the app's `update` returns is performed; examples perform nothing (M2-06).

Grants: `Console`, `ReadFiles`, `WriteFiles`. They take no arguments. A name outside the three is
`unknown-grant` at the name, a name listed twice is `duplicate-grant` at the later one (both in
spec/m1.md §11); a grant never used is accepted. A grant is checked when its effect is about to be
performed, in list order, never at check time: a program may carry `ReadFile` under `grants: []`
and ends only if it reaches that effect.

### 1.4 Command-line arguments and the first message

`paka run main.paka a b` and a built program run as `./wc a b` fill the start variant's fields by
position: `Start(path: String)` gets `"a"`. The count must match the field count exactly, else
the usage line on standard error and status 2, before the first state is built:

```
wc: expected 1 argument (path), got 0
copy: expected 2 arguments (src, dest), got 3
light: expected 0 arguments, got 1
```

An argument that is not valid UTF-8 is `wc: argument 2 is not text`, status 2. The tool's own
flags (`--paka-examples`) are taken off before counting. Status 2 is the tool's usage status in
M2-06 §1.7, which names this line. The start message is not written anywhere; the program sees it
only through `update`.

### 1.5 The run loop

```
queue = [Start(args)]
state = S {}                       // when there is a state:
loop:
  if queue is empty: stop "ended without Exit"
  m = pop front of queue; if it is a pending answer, m = f(text or reason)
  effects = update(&state, m)      // a trap here ends the program (1.9)
  for e in effects, in order:
    Print:     refused without Console; else write text + "\n" to descriptor 1; a failure stops
    ReadFile:  refused without ReadFiles; else read now; push (then, text) or (or, reason) to the back
    WriteFile: refused without WriteFiles; else write now; push then or (or, reason) to the back
    Exit:      end, status 0
    ExitWith:  end with status, or stop when the status is out of range
```

Every file effect is done before the next effect in the list is looked at; its answer joins the
back of the queue. The `then:` or `or:` function is applied when the answer reaches the front,
just before `update` is called with its result (**fixes** the recorded "when the answer's turn
comes" to one point). A trap inside that function ends the program like a trap in the handler; the
chain line of M2-06 §1.2 names the function as the outermost frame (`in Loaded`).

Consequences a program can rely on:

- Answers arrive in the order the effects were performed, across handlers. A program that asks for
  several files keeps the names it waits for in its state, in that order; answers carry no path.
- A `Print` after a `ReadFile` in one list is written before the file's answer is handled.
- A refused or failed effect stops at that effect: earlier effects in the list stay done, later
  ones are not performed, nothing queued is handled.
- `Exit` and `ExitWith` end the program at once: later effects in the list and every queued answer
  are dropped, a failure included. `[WriteFile(...), Print("done"), Exit]` ends with status 0 even
  when the write failed; a program that must know a write worked exits from its `then:` message.
- An effect after `Exit` is never reached, so it is never refused.

Sequencing other than this order and any concurrency are not decided (paper lines 355, 356): no
effect runs in the background, no two effects overlap, and no later decision may make a file
effect's answer arrive before an effect listed after it in the same handler.

### 1.6 Print, exactly

`Print(text)` writes the text's UTF-8 bytes and one line feed as one buffer to the process's file
descriptor 1 and reports the system's answer. Not the language's buffered standard output: a
descriptor closed at start (`>&-`) must be an error (M1-06.2), and a buffered stream reports
success on a closed descriptor. The runtime asks the system until the whole buffer is written or
it refuses; a short write is retried. There is nothing to flush, so a program never leaves output
unwritten when it ends by `Exit`, by a stop or by a trap. Standard error is never written by an
effect.

**Amends** the descriptor closed at start (`>&-`): `paka run` cannot see a descriptor 1 closed at
its start, because Rust's start-up reopens it on `/dev/null` and the crate forbids unsafe code. Only
a built program is held to `write error`, status 3. The same holds for the `>&-` row of section 2.
M2-36 also leaves out `run/no_app` of section 4: `check/no_app` and `paka/tests/build.rs` cover it.

A refusal is the stop `<app>: effect Print failed: <reason>` with the reason from this table:

| host error | reason |
|---|---|
| `EPIPE` | `broken pipe` |
| `ENOSPC`, `EDQUOT` | `no space left on device` |
| anything else (`EBADF`, `EFBIG`, `EIO`, ...) | `write error` |

The runtime sets SIGPIPE and SIGXFSZ to ignored before the first message, so a closed pipe and a
file-size limit are refusals, never a kill. SIGXFSZ joins the M1-14.5 rule, which named SIGPIPE
only; no other signal is touched.

### 1.7 ReadFile and WriteFile, exactly

`ReadFile(path, ...)` opens the path relative to the process's working directory, reads every byte
and gives them as a `String`. `WriteFile(path, text, ...)` creates or replaces the file with the
text's UTF-8 bytes, makes no directories, adds nothing; after a failure the file's content is not
promised. Neither follows a rule of its own for `~` or environment variables: the path is used as
written.

The reason is one of six texts, from the first row that matches:

| condition | reason |
|---|---|
| the path holds a NUL byte, or is empty | `failed` |
| `ENOENT`, `ENOTDIR` | `not found` |
| the path is not a regular file (from its metadata, before any open; read only) | `not a file` |
| `EACCES`, `EPERM` | `no permission` |
| `EISDIR` (write only) | `not a file` |
| the file is larger than the String limit of M2-06 §1.4 (read only) | `failed` |
| the bytes are not UTF-8 (read only) | `not text` |
| `ENOSPC`, `EDQUOT` (write only) | `no space` |
| anything else | `failed` |

The size is checked before the bytes are decoded, so a huge file is `failed` and never a `memory`
trap: an effect fails only through its `or:`, never through a trap. A file of zero bytes reads as
`""`. The read is done whole, so a file that changes while it is read gives some one of its
contents; not meaning.

The host reads the path's metadata before it opens it. A path that is not a regular file is
`not a file` unopened, even where its own permissions would refuse it, since opening a FIFO waits
for a writer. A regular file is then opened, so `no permission` still comes before the size, and
one larger than the limit is `failed` with no byte read. The open does not wait, and the kind and
size are then taken again from the opened file, so a path changed between the look and the open is
judged by what was opened.

### 1.8 Ending and the exit status

- `Exit` and `ExitWith(0)` end with status 0.
- `ExitWith(n)` with `n` in 5 to 255 ends with status `n`. **Amends** the recorded 4 to 255:
  M1-14.6 locks "M2-15 must keep 3 and 4 out of the statuses a program may choose for itself",
  and M2-06 §1.7 gives status 4 to an internal error of every command. 1 and 2 belong to the
  `paka` tool and the usage line, 3 to traps and stops. 101 is legal. The tasks of M2-01 write
  `ExitWith(20)`.
- `ExitWith(n)` with any other `n` (1, 2, 3, 4, 256, -1) is the stop
  `<app>: effect ExitWith failed: status <n> is not 0 or 5 to 255`, status 3. A stop, not a
  trap: it has no position and the value may have been computed.
- An Int literal as the argument, with or without the leading `-` M2-03 §1.12 folds, is refused at
  check time under the existing code `literal-out-of-range` at the literal:
  "3 is not an exit status a program may choose; write 0 or 5 to 255". A computed status is
  checked only at run time.
- When the queue is empty and no `Exit` was performed: the stop `<app>: ended without Exit`,
  status 3 (M2-15.7, already in spec/m1.md §9.3). **Fixes** the recorded "may name the last
  message handled": the line is bare, as M1's `run/no_exit` case holds it.
- A refused effect: `<app>: effect <E> refused: grant <G> is missing`, status 3 (M1-06.1 kept).
- A failed `Print`: `<app>: effect Print failed: <reason>`, status 3 (M1-06.2 kept).
- A trap in a handler or in a `then:`/`or:` function: the M2-06 report, status 3.
- Status 4 is never chosen by a program: it is the runtime's own internal error (M1-14.6).

The four stop lines are stops, not trap kinds (M2-06 §1.1): one line on standard error, no kind,
no position, no help lines. The process never ends by a signal on its own account; what a kill
from outside does is not meaning.

### 1.9 A trap inside a handler

The program ends: the trap report on standard error, status 3, standard output written so far
stays written (paper line 160, M2-06 §1.2). None of that handler's effects is performed, because a
trapped handler returns no list: `[Print("x"), Print("{1 / 0}")]` prints nothing. Effects of
earlier handlers stay done: a `Print("p")` in the handler before a trapping `Loaded` is on
standard output when the trap line is on standard error.

No state copy is taken and nothing is rolled back: the program ends, so nobody could see a
restored state. M2-36 tests no rollback; the copy and the restore of paper line 159 arrive with
M5-25b for visual apps, where the program lives on. In a headless app a held `&` place at the
trap (M2-05 item 17) is simply never seen.

### 1.10 Standard input

None. No effect reads it, no grant names it, the first message carries only the command-line
arguments. A task that needs input names a file (M2-01 §2). Adding a `ReadInput` effect later is a
free extension.

### 1.11 wc under the rules

```
type Tally { words: Int = 0 }

enum Msg { Start(path: String), Loaded(text: String), Failed(why: String) }

fn count_words(text: String) -> Int {
  len(words(text))
}

fn update(s: inout Tally, m: Msg) -> List<Effect<Msg>> {
  match m {
    Start(path) => [ReadFile(path, then: Loaded, or: Failed)]
    Loaded(text) => {
      s.words = count_words(text)
      [Print("{s.words} words"), Exit]
    }
    Failed(why) => [Print("cannot read file: {why}"), ExitWith(20)]
  }
}

app wc {
  state: Tally
  start: Start
  update: update
  grants: [ReadFiles, Console]
}
```

Each change from paper lines 242 to 260: the `start:` line (M1-06.3); `or: Failed` with its
variant and arm (1.3); `count_words` written out with `words` (M2-14); single spaces instead of
aligned arrows and keys (M4-47). `paka run wc.paka a.txt` prints the count; `paka run wc.paka`
prints `wc: expected 1 argument (path), got 0` and ends with status 2; a missing file prints
`cannot read file: not found` on standard output and ends with status 20.

## 2. Attacks tried against the rules

| program or host | outcome |
|---|---|
| `[Print("a"), Print("b")]` under `grants: []` | nothing printed; `effect Print refused: grant Console is missing`, 3 |
| `[Print("a"), ReadFile(p, ...)]` under `[Console]` | `a` printed; `effect ReadFile refused: grant ReadFiles is missing`, 3 |
| `[ReadFile(p, then: Loaded, or: Failed), Print("asked")]` | `asked` printed, then `Loaded` or `Failed` handled |
| `[ReadFile("a", ...), ReadFile("b", ...)]`, both missing | two `Failed` messages, in that order; the state tells them apart |
| `[WriteFile("/", "x", then: Done, or: Failed), Exit]` | status 0; the failure is dropped with the queue |
| `Failed(why) => [ExitWith(20)]` with another answer queued | status 20; the queued answer is dropped |
| `[Print("x"), Print("{1 / 0}")]` | nothing printed; `trap divide_by_zero`, 3 |
| `Start(_) => [Print("p"), ReadFile(p, then: Boom, or: Failed)]` where `Boom` traps | `p` printed; trap with `in Boom`, 3 |
| `[Exit, Print("never")]` | status 0, nothing printed, nothing refused |
| `[ExitWith(0)]`, `[ExitWith(101)]`, `[ExitWith(255)]` | status 0, 101, 255 |

| `ExitWith(n)` computed as 4 | `effect ExitWith failed: status 4 is not 0 or 5 to 255`, 3 |

## 5. New and reused diagnostic codes

| code | at | message | fix |
|---|---|---|---|
| `bad-state` (new) | the `state:` value | `state Msg is not a record type with a default on every field` | `give every field of Msg a default, or name a record type` |
| `bad-update-signature` (M2-02) | the `update:` value | `update must be fn(s: inout Tally, m: Msg) -> List<Effect<Msg>>` | shown by the message |
| `literal-out-of-range` (M2-03, reused) | the literal in `ExitWith` | `3 is not an exit status a program may choose` | `write 0 or 5 to 255` |
| `type-mismatch` (M2-09 §1.11) | the `state:` value | `state Later holds a function type in field after` | `keep a message value instead and match on it in update` |
| `unknown-grant`, `duplicate-grant`, `missing-start`, `bad-start`, `multiple-apps`, `no-app` | as spec/m1.md §11 | unchanged | unchanged |

Where the table is silent: a repair follows the message after `; `. `bad-update-signature` writes
`Msg` for the enum when the last parameter is not one, and ignores parameter names. `bad-start` also
covers a `start:` value that is not a variant name (a type, a function or any other definition;
a name not defined is `unknown-name`), and a variant with a field that is not a
`String`: "`Start` field `n` is not a String; the first message is filled from the arguments".

Four stop lines, all status 3, with no code:

```
<app>: effect <E> refused: grant <G> is missing
<app>: effect Print failed: <reason>
<app>: effect ExitWith failed: status <n> is not 0 or 5 to 255
<app>: ended without Exit
```

One usage line, status 2: `<app>: expected <n> argument(s) (<fields>), got <m>`, or
`<app>: argument <i> is not text`. `argument` is singular for 1, plural otherwise; the field list
is left out when there is none.

## 6. Alternatives considered and why rejected

- **A `Result` in the message instead of `or:`.** Keeps one failure mechanism, but patterns are
  flat (M2-02), so every answer needs a match inside a match, `?` cannot stand in `update` (M2-12
  §1.7), and a finished write has nothing to put in `Ok`.
- **`or:` optional, a failure then ending the program.** Saves a variant and an arm in every
  program, but a forgotten `or:` shows only when a test feeds a missing file, and every task of
  M2-01 must print its own message and choose its status.
- **A failed file effect always ends the program.** Nothing to handle, but M2-01 and M2-12 require
  the program to say what went wrong.
- **Answers carry the path.** Saves a state field in a program that reads several files, but
  doubles every answer type and the program already chose the names.
- **Applying `then:`/`or:` when the file effect is performed.** Simpler loop, but a trap in
  `Loaded` would then strike in the middle of another handler's effect list, and the chain line
  could not say which handler was running. Applying at the front of the queue keeps one place
  where user code runs.
- **Keeping the chosen range at 0 or 4 to 255.** Two earlier records lock 4 out; letting a
  program choose 4 would make an internal error indistinguishable from a chosen status in every
  harness that compares statuses.
- **A new code `bad-exit-status` for the literal.** One more code for one literal; the existing
  `literal-out-of-range` with an exact message gives the same repair.
- **No check-time refusal of the literal.** Fewer rules, but `ExitWith(1)` is what an agent writes
  first, and a hidden case would be the first to say so.
- **Writing `Print` through the language's buffered standard output with a flush per effect.**
  The M1 code does this; it reports success on a closed descriptor and so breaks M1-06.2.
- **Naming the last message in `ended without Exit`.** Helps a reader once, costs a value text in
  the runtime and a line that differs by program; the bare line is what M1's cases hold.
- **A rollback in headless apps.** Nothing could observe it; the copy would be paid on every
  message for nothing.
- **Standard input as an effect or as a start field.** No task of M2-01 reads it; a later effect
  can add it without touching this page.
- **Concurrent file effects.** The paper leaves it open (line 356); every task runs within the
  order above, and a later decision can add an effect that is explicitly unordered.
- **A `List<String>` field for the rest of the arguments.** The runtime checks the count, so no
  program carries usage code; a List field can be allowed later without breaking a program.

## 7. Accepted risks

- A program that asks for several files and forgets to keep the names in its state cannot tell
  the answers apart. The order rule makes this exact, not convenient.
- A failed `WriteFile` may leave a partly written file; the program is told it failed, not how
  much was written.
- `failed` covers every host error the six texts do not name, so two different causes can read
  the same. The texts are for a program to print, not to branch on.
- A `Print` of 16 MiB to a slow pipe blocks the program; there is no timeout and no partial
  success. The sandbox of M3 and `limit_ms` of M4-03 bound it from outside.
- `literal-out-of-range` now carries two messages. A reader who looks the code up finds both
  under one name.
- The String limit of M2-06 is checked by size before a read is decoded, so a file just under the
  limit that reads fine on one host may be `failed` on a host with a smaller cap. Both hosts are
  outside meaning (M2-06 §1.4).
- Nothing rolls back in a headless app, so a visual app under M5-25b behaves differently at a
  trap. The two are different programs with different observers; the reference says so in one
  line.
