# M7-03 · How human-owned examples run against the shipped release binary

Status: approved by the owner on 2026-11-02, with the review's nine changes.

Base: the recorded M7-03 page in DECISIONS.md. M7-03.2 (a new `paka release`) **stands** as
recommended there; it is 1.3 below. M7-03.1 is **amended** (1.1, 1.2): function examples stay
compiled in but each runs in a process of its own, and UI examples are replayed against the binary
as M5-26 already does for dev mode instead of being compiled in. M7-03.3 is **amended** (1.4) to

GENESIS 3.6, line 187: before release, the human-owned examples run against the release binary
itself. This record says how, which command ships, and how anyone can check that the binary that
ran them is the one shipped.

## 1. Points

**1.1 Function examples are compiled into the binary and run one per process.** An example body is
an ordinary function returning Bool, so the release back end lowers it like any other. Started with
`--paka-examples <name>`, the binary runs that one example at depth 1 with no app, no state and no
effects, prints one line and exits. A trap ends only that run, so no runner has to survive one.
Each run has a fixed time limit; one that passes it is `timed out`.

```
$ ./wc --paka-examples count_words_empty
count_words_empty pass
$ ./wc --paka-examples count_words_two_lines
count_words_two_lines fail
```

- Alternatives: all examples in one run (a trap ends the rest, or the runner must recover from it
  in compiled code) · driven from outside (impossible: a function example calls any function with
  any value, and nothing outside the binary can reach those).

**1.2 UI examples are replayed against the binary.** The interpreter runs the example and logs each
action and what it left (M5-26's `ui_log`): the tree text, the tree after `Exit`, a trap's first
line or an end line. Started with `--paka-replay`, a visual binary runs its app with no window and
no effects, takes those actions on standard input, one per line (`click PATH`, and a typed-text
action), and prints the same full result after each. Release compares the two, action by action;
any difference refuses, and so does a UI example compared on fewer actions than it has. A UI
example touches the app only through events in and trees out (M5-06 1.1 to 1.5), so equal results
at every action mean its reads and claims hold against the binary too.

```
$ paka release examples/counter -o dist/counter
...
ui examples replayed: inc_then_dec 4 of 4 actions agree, reset_clears 3 of 3 actions agree
```

- Why the action count: in a UI example a dropped effect sends no answer (M5-06). If replay
  delivered one, the app would go on differently, and a comparison cut short there would still read
  as agreeing. So no back end queues an answer for a dropped effect, as the foreign path already
  does, and every action is compared.
- Alternatives: compile UI examples in as well (one mechanism for both kinds, but `ui_start`,
  `ui_click` and the readers must be lowered for release and survive a handler trap there; the
  comparison gives the same evidence for less) · drive the binary through the Look protocol
  (every release binary would ship a Look port).

**1.3 A new `paka release` ships; `paka build` is never gated.** `paka release <program> -o <dir>`
reads the program once, runs the gate for it on that read, builds from the same read, runs the
examples against the binary and only then leaves the artefact. `paka build` keeps its current
behaviour and never reads the store, so conformance, fuzz and benchmark builds are untouched.

```
$ paka release examples/wc -o dist/wc
key: approvals.pub matches ~/.config/paka/approval_key.pub
gate: approvals serial 8, signature good, nothing pending
build: paka build examples/wc -o wc --examples count_words_empty count_words_two_lines
examples in binary: 2 of 2 pass
released: dist/wc  wc sha256 41c7...
```

- Why one read: the gate and the build reading the files each on their own would let an edit made
  between them be built under an approved name. One read, used by both, closes that, and `RELEASE`
  records the SHA-256 of every source file read.
- Alternatives: `paka build` gated by default with a flag to switch it off (every test, fuzz and
  benchmark call must add the flag) · `paka build` plus a later `paka stamp` (the file can change
  between the two steps, so the proof has a gap by design).

**1.4 Examples are compiled in only by name, under `paka build --examples <name>...`.** The flag
adds the named function examples of the program and no others, human-owned or not; it is the
switch M2-06 left to this task. A name that is not a function example of the program refuses the
build. A plain `paka build` compiles in none, and its binary answers the switch only with the
usage line of section 2. `paka release`
passes exactly the function examples the verified store names, and records the command line it
built with in `RELEASE`.

```
$ paka build examples/wc -o wc                                  # no examples, no switch
$ paka build examples/wc -o wc --examples count_words_empty     # one example in
```

- Why: the build stays a function of the source and its flags, with no tie to the store. An agent
  reproduces a release failure with the command line from `RELEASE` and the switch, and gets the
  build release tested. Benchmark binaries carry no example code, so no extra callers change
  inlining.
- Alternatives: every build carries its examples (one build path, but benchmark and conformance
  binaries change shape) · `--examples` adds every example (more code in the binary than release
  tests, and a release depends on examples no one approved) · release compiles in the store-named
  examples by itself (the binary then depends on a file outside the source).

**1.5 One build into a fresh directory, hashed before and after, renamed into place.** Release
refuses if `-o` exists. It builds the whole artefact once, under its final file names, into a new
directory beside `-o`: the binary, a freshly built host for each foreign declaration and the
notices file. It takes the SHA-256 of every file, runs every example against the binary, writes
`RELEASE`, renames the directory to `-o` and takes the hashes again there. It never builds twice; a
failed host or a changed hash refuses and leaves no artefact.

```
program    examples/wc
source     wc.paka  sha256:9e01...
build      paka build examples/wc -o wc --examples count_words_empty count_words_two_lines
binary     wc  sha256:41c7...
compiler   paka <version>, clang 21
approvals  serial 8  sha256:77aa...
example    count_words_empty      pass
example    count_words_two_lines  pass
```

- Why: a released program finds each host beside its binary under the binary's own name (M7-15),
  so binary and hosts must be built together under the names they ship with; renaming the binary
  alone would ship it without them. Hosts are built fresh, not taken from the host cache, so what
  ships is built from the files the gate checked. A rename moves the directory without copying or
  rebuilding it, so the bytes that ran the examples are the bytes shipped, and the hashes show
  nothing changed in between. Anyone holding the artefact can hash it, compare with `RELEASE` and
  run the switch again. Needs only M4-07's SHA-256.
- Alternatives: build into a temporary file and rename it (hosts are named after the output file,
  so the renamed binary finds none) · build twice and compare (needs builds identical to the last
  byte, which nothing in M6 promises) · the owner's key also signs `RELEASE` (a stranger could
  verify it, but a passphrase per release that no one has asked for yet).

## 2. Rules that follow

**The binary's switches**

- `--paka-examples` and `--paka-replay` are reserved in all three modes, with one outcome: an
  argument list whose first argument is either one never reaches the app. They are taken before the
  start message and the count check (M2-15). Where the switch is not served (the interpreter, dev
  mode, a binary built without that example, `--paka-replay` in a headless app) the run ends with
  one usage line naming the switch and status 2, and no handler runs; so does a served switch in
  any other shape than below. M2-15's flags sentence names both, and a conformance case checks the
  outcome in the three modes.
- `--paka-examples <name>` prints `<name> pass` or `<name> fail` and exits 0. A trap gives the usual
  trap line and status 3; release reports it as `trapped`. An unknown name gives a usage line,
  status 2. The memory ledger is checked as after a run; a leak is status 4. The reason a claim
  failed (its sides) is help: the gate already ran the example in the interpreter.
- `--paka-replay` is served by visual binaries only. Effects are dropped, no grant is used and no
  foreign host starts, as M5-06 rules for UI examples, and no dropped effect queues an answer. Each
  line of standard input is one action: `click PATH` (built in M6-18) or a typed-text action. After
  the launch and after each action it prints, on standard output, what M5-26 logs: the tree text,
  the tree after `Exit`, the first trap line or the end line. The action line form is shared with
  M5-26's log and the windowless test.
- Release trusts the printed lines, not the status alone. A function example passes only with
  status 0, standard output exactly `<name> pass` and an empty standard error, within the time
  limit; anything else is reported as what it was (`fail`, `trapped`, `timed out`, or the output
  seen) and refuses. Each replayed UI example must agree on every one of its actions.

**What release checks, in order**

- That `-o` does not exist, and that `approvals.pub` equals the public key beside the signing key
  (`~/.config/paka/approval_key.pub`, or beside the key `--key` names).
- One read of the program's files. The gate for this one program runs on that read: signature,
  records, owned files, human-owned examples in the interpreter. With no base at hand the serial is
  recorded, not compared (M7-01).
- That the program has records and at least one human-owned example; no owner evidence, no release.
- The build from the same read, with `--examples` and the store's function example names, which
  refuses a hole (GENESIS line 308) and anything the back end cannot lower yet. Then the hosts,
  built fresh; one that fails refuses.
- Hashes, function examples, UI replays, `RELEASE`, rename, hashes again at the final path. Any
  refusal removes the new directory, wherever it then is, leaves no artefact and exits 1.

**The artefact and where it is made**

- One directory: the binary, one host per granted `foreign` declaration under the binary's name
  (M7-02, M7-15), the third-party notices file (M7-16) and `RELEASE`. `RELEASE` holds the SHA-256
  of every source file read and of every artefact file, the build command line, the compiler and
  store, and each example's result. Examples perform no effects, so hosts are listed as built, not
  exercised.
- The owner runs `paka release` from a clean checkout of `main`. A release from any other tree proves
  nothing, since the local gate trusts the key in the working tree (M7-01); the key check above
  catches only an honest mistake. No CI release job yet.
- The pull-request gate never builds or runs a binary; binary examples run only inside
  `paka release`, so compiled code from a pull request stays out of the gate job (M7-01).
- Example runs against the binary are never cached; M7-09's cache serves the interpreter only.

**What is claimed**

- A function example runs real compiled code: it calls the program's functions out of line, so the
  optimizer cannot fold it away. A copy inlined into other callers is not what the example ran;
  three-mode conformance and fuzzing cover that code. `RELEASE` claims no more.
- A UI example's app part runs in the binary, on every one of its actions; its reads and claims run
  in the interpreter on results shown equal to the binary's.
- Conformance and the benchmarks run builds of their own (`paka build`, with `--examples` for the
  example-status cases), never the shipped binary. They speak for the compiler, not for one
  artefact.

**Owner must still**

- Run `paka release` yourself, from a clean checkout of `main`.

## Review (reviewer told to break it)

Verdict: approve with the changes below. Holding: `paka build` never reads the store, so
conformance, fuzz and benchmark builds are not gated; the interpreter gate takes no result from the
example cache; a trap or leak exits 3 or 4.

Required changes:

1. (high) UI replay: an answer is delivered as the failure `dropped`, so after the first file read
   the rest of a UI example is never compared yet reads as agreeing. In replay, queue no answer, as
   the foreign path does; release refuses a UI example compared on fewer actions than it has.
2. (high) Gate and build read the source separately (gate.rs, main.rs), so an edit between them is
   built under an approved name. Release reads and checks the program once; the gate and the build
   both use that result; `RELEASE` records the SHA-256 of every source file read.
3. (high) Foreign hosts are named after the output file and may come from the user cache, so a
   temporary-file rename ships a binary that finds no host. Replace 1.5's file rename: build the
   whole artefact into a fresh directory beside `-o` under final names, build hosts fresh (a failed
   host refuses the release), hash every file before and after the runs, write `RELEASE`, rename
   the directory into place, refuse if `-o` exists, and take the second hash at the final path.
4. (medium) `--paka-examples <name>` and `--paka-replay` collide with program arguments and behave
   differently per mode. Reserve both in all three modes with one outcome, written into M2-15, with
   a conformance case.
5. (medium) Compile only the named examples: `paka build --examples <name>...`; release passes the
   store's names and records the command line in `RELEASE`; `unfinished` conformance cases stay
   interpreter and dev only.
6. (medium) Replay prints, per action, M5-26's full result (tree, `Exit`, first trap line, end line)
   on standard output, and a typed-text action is added; §3's note that replay is unbuilt is out of
   date (M6-18 built `click PATH`).
7. (low) A fixed time limit per example run (`timed out`); require status 0, standard output exactly
   `<name> pass` and empty standard error.
8. (low) Release refuses unless `approvals.pub` equals the public key beside the signing key.
9. (low) Say under "What is claimed" that conformance and benchmarks use plain builds, not the
   shipped binary.
