# M7-03 · How human-owned examples run against the shipped release binary

Status: draft, awaiting the owner's approval.

Base: the recorded M7-03 page in DECISIONS.md. M7-03.2 (a new `paka release`) and M7-03.4 (one
build, hash, run, rename) **stand** as recommended there; they are 1.3 and 1.5 below. M7-03.1 is
**amended** (1.1, 1.2): function examples stay compiled in but each runs in a process of its own,
and UI examples are replayed against the binary as M5-26 already does for dev mode instead of being
compiled in. M7-03.3 is **amended** (1.4) to follow M2-06, which promised a switch on `paka build`
that keeps examples: `paka build --examples` compiles in every function example and never reads the
store. The page was written before M2-06, M5-06, M5-26, M6-17 and M7-07 were approved or built;
the amendments follow what they fixed.

GENESIS 3.6, line 187: before release, the human-owned examples run against the release binary
itself. This record says how, which command ships, and how anyone can check that the binary that
ran them is the one shipped.

## 1. Points

**1.1 Function examples are compiled into the binary and run one per process.** An example body is
an ordinary function returning Bool, so the release back end lowers it like any other. Started with
`--paka-examples <name>`, the binary runs that one example at depth 1 with no app, no state and no
effects, prints one line and exits. A trap ends only that run, so no runner has to survive one.

```
$ ./wc --paka-examples count_words_empty
count_words_empty pass
$ ./wc --paka-examples count_words_two_lines
count_words_two_lines fail
```

- Alternatives: all examples in one run (a trap ends the rest, or the runner must recover from it
  in compiled code) · driven from outside (impossible: a function example calls any function with
  any value, and nothing outside the binary can reach those).

**1.2 UI examples are replayed against the binary.** The interpreter runs the example and logs every
action's events and the tree text it left (M5-26's `ui_log`). Started with `--paka-replay`, a
visual binary runs its app with no window and no effects, takes those events on standard input and
prints the tree text after each action. Release compares the two, action by action; any difference
refuses. A UI example touches the app only through events in and trees out (M5-06 1.1 to 1.5), so
equal trees at every action mean its reads and claims hold against the binary too.

```
$ paka release examples/counter -o dist/counter
...
ui examples replayed: inc_then_dec 4 actions agree, reset_clears 3 actions agree
```

- Alternatives: compile UI examples in as well (one mechanism for both kinds, but `ui_start`,
  `ui_click` and the readers must be lowered for release and survive a handler trap there; the
  tree comparison gives the same evidence for less) · drive the binary through the Look protocol
  (every release binary would ship a Look port).

**1.3 A new `paka release` ships; `paka build` is never gated.** `paka release <program> -o <dir>`
runs the gate for that program, builds, runs the examples against the binary and only then leaves
the artefact. `paka build` keeps its current behaviour and never reads the store, so conformance,
fuzz and benchmark builds are untouched.

```
$ paka release examples/wc -o dist/wc
gate: approvals serial 8, signature good, nothing pending
build: sha256 41c7...
examples in binary: 2 of 2 pass
released: dist/wc/wc  sha256 41c7...
```

- Alternatives: `paka build` gated by default with a flag to switch it off (every test, fuzz and
  benchmark call must add the flag) · `paka build` plus a later `paka stamp` (the file can change
  between the two steps, so the proof has a gap by design).

**1.4 Examples are compiled in only under `paka build --examples`.** The flag adds every function
example of the program, human-owned or not; it is the switch M2-06 left to this task. A plain
`paka build` compiles in none and has no `--paka-examples` switch. `paka release` always builds
with the flag and runs only the examples the verified store names.

```
$ paka build examples/wc -o wc                # no examples, no switch
$ paka build examples/wc -o wc --examples     # what release builds
```

- Why: the build stays a function of the source and its flags, with no tie to the store. An agent
  reproduces a release failure with `paka build --examples` and the switch, and gets the same binary
  release tested. Benchmark binaries carry no example code, so no extra callers change inlining.
- Alternatives: every build carries its examples (one build path, but benchmark and conformance
  binaries change shape) · release compiles in only the store-named examples (the binary then
  depends on a file outside the source).

**1.5 One build, two hashes, one rename.** Release builds once into a temporary file in the output
directory, makes it read-only, takes its SHA-256, runs every example against it, takes the hash
again, renames that same file into place and writes the record `RELEASE` beside it. It never builds
twice; a changed hash refuses and leaves no artefact.

```
program    examples/wc
binary     wc  sha256:41c7...
compiler   paka <version>, clang 21
approvals  serial 8  sha256:77aa...
example    count_words_empty      pass
example    count_words_two_lines  pass
```

- Why: a rename moves the file without copying or rebuilding it, so the bytes that ran the examples
  are the bytes shipped, and the two hashes show nothing changed in between. Anyone holding the
  binary can hash it, compare with `RELEASE` and run the switch again. Needs only M4-07's SHA-256.
- Alternatives: build twice and compare (needs builds identical to the last byte, which nothing in
  M6 promises) · the owner's key also signs `RELEASE` (a stranger could verify it, but a passphrase
  per release that no one has asked for yet).

## 2. Rules that follow

**The binary's switches**

- `--paka-examples <name>` and `--paka-replay` are taken only as the whole argument list, before the
  start message and the count check (M2-15). Any other arguments go to the app as before.
- `--paka-examples <name>` prints `<name> pass` or `<name> fail` and exits 0. A trap gives the usual
  trap line and status 3; release reports it as `trapped`. An unknown name gives a usage line,
  status 2. The memory ledger is checked as after a run; a leak is status 4. The reason a claim
  failed (its sides) is help: the gate already ran the example in the interpreter.
- `--paka-replay` exists in visual binaries only. Effects are dropped, no grant is used and no
  foreign host starts, as M5-06 rules for UI examples. An action that queues an answer ends the
  comparison of that example, as in M5-26. The event text form is fixed by the task that builds it
  and shared with M6-18's windowless test.
- Release trusts the printed lines, not the status alone: each store-named example must appear
  once with `pass`, and each replayed one must agree on every action.

**What release checks, in order**

- The gate for this one program on the working tree: signature, records, owned files, human-owned
  examples in the interpreter. With no base at hand the serial is recorded, not compared (M7-01).
- That the program has records and at least one human-owned example; no owner evidence, no release.
- The build with `--examples`, which refuses a hole (GENESIS line 308) and anything the back end
  cannot lower yet.
- Hash, function examples, UI replays, hash, rename, `RELEASE`. Any refusal removes the temporary
  file, leaves no artefact and exits 1.

**The artefact and where it is made**

- One directory: the binary, one host per `foreign` declaration (M7-02), the third-party notices
  file (M7-16) and `RELEASE` with the SHA-256 of every file. Examples perform no effects, so hosts
  are listed as built, not exercised.
- The owner runs `paka release` from a clean checkout of `main`. A release from any other tree proves
  nothing, since the local gate trusts the key in the working tree (M7-01). No CI release job yet.
- The pull-request gate never builds or runs a binary; binary examples run only inside
  `paka release`, so compiled code from a pull request stays out of the gate job (M7-01).
- Example runs against the binary are never cached; M7-09's cache serves the interpreter only.

**What is claimed**

- A function example runs real compiled code: it calls the program's functions out of line, so the
  optimizer cannot fold it away. A copy inlined into other callers is not what the example ran;
  three-mode conformance and fuzzing cover that code. `RELEASE` claims no more.
- A UI example's app part runs in the binary; its reads and claims run in the interpreter on trees
  shown equal to the binary's.

**Owner must still**

- Run `paka release` yourself, from a clean checkout of `main`.

## 3. What this changes in TASKS.md

- M7-11: split as its note foresees. A new level 3 task adds `paka build --examples` and the
  binary's `--paka-examples <name>` switch: example bodies lowered as Bool functions, one run per
  process, the ledger check. `--paka-replay` belongs to M6-18 if its windowless test drives the
  binary by script, else to the same new task. M7-11 keeps the owner's approvals, the runs and the
  planted failure.
- M7-12: the release command is the new `paka release`: gate, refusal without records or a
  human-owned example, one build with `--examples`, read-only temporary file, two hashes, rename and
  `RELEASE`. Re-grade to level 3, since the hash-and-rename order is where a silent mistake lives.
- M7-07: the gate must be callable for one program from inside `paka release`, without a base tree.
- M6 notes: '`paka build` is the release command since M1; there is no second spelling' becomes:
  `paka build` is the optimizing build, `paka release` is the command that ships.
- M6-06 and the M6 exit check: the 'example-status cases in interpreter and dev only, until M7-11'
  exception ends; release builds those cases with `--examples` and reads the switch's line.
- M5-26: release joins as a third back end through `--paka-replay`.
- M2-06: '`paka build` drops them' stands; the switch that keeps them is `--examples`, and it keeps
  function examples only.
- M2-15: the tool's flags taken before counting are `--paka-examples <name>` and `--paka-replay`.
- M7-15, M7-16: hosts and the notices file are written by `paka release` into the artefact
  directory and listed in `RELEASE`.
