# M2-03 · Primitive types and the exact meaning of every operation

Base: the recorded M2-03 page in DECISIONS.md, written out as one table in which every row gives a
result or a named trap for every input, with the exact algorithms for `round`, `fixed`, literals and
`parse_float` so that no row depends on a library, a rounding mode or the CPU. Grafted: a precise
NaN rule that no back end has to pay for, a symmetric brace rule for string literals, a plain-scan
rule for interpolations, the UTF-8 source rules the M1 spec left open, and the back-end guard rules
every native target must follow. The six owner picks (M2-03.1 to .6) stand unchanged. Four
sentences of the recorded settled text change; each is marked "changes recorded text" below and
listed in section 6.

## 1. Resolutions

### 1.1 Types

Int, Float, Bool, String. No Char, no sized or unsigned integers, no byte, no tuple, no unit value.
A function without `->` has no value and cannot be used as one. Nothing converts implicitly
(GENESIS line 47); every conversion is a named function.

### 1.2 Int: 64-bit, trapping, truncating

One 64-bit two's-complement Int, -9223372036854775808 to 9223372036854775807. `+ - *` and unary `-`
trap `overflow` when the exact result does not fit (line 106). `/` truncates toward zero; `%` has
the sign of the dividend, so `a == (a / b) * b + a % b` always. `b == 0` traps `divide_by_zero`;
`MIN / -1` traps `overflow`; `MIN % -1` is `0`. Wrapping and bit work are the nine named functions
of M2-03.4 and never trap on the value; a shift count outside 0 to 63 traps `out_of_bounds`.

Why guards, not hardware traps: ARM64 does not trap on division, LLVM treats `MIN / -1` and `x / 0`
as undefined and may delete them, and a signal handler cannot name the source position M2-06
requires. Every native back end tests the operands and branches to the trap routine before the
instruction runs; the instruction then sees only inputs every target agrees on.

### 1.3 Float: IEEE binary64, no library

Round to nearest, ties to even; subnormals kept; no fused multiply-add (line 158); no flag, mode or
attribute that changes any of this. `+ - * /` and unary minus never trap. `sqrt` is the IEEE
correctly rounded root and is one instruction everywhere; `floor`, `ceil`, `trunc` are exact
everywhere. `round` and `min`/`max` are runtime routines, because hosts differ (Cranelift's
`nearest` ties to even, JavaScript's `Math.round` ties up, x86 `minsd` and LLVM `minnum` treat NaN
differently). Nothing links a maths library; sin, exp and pow do not exist (M2-01.4).

`round`, exactly: `t = trunc(a)`; if `abs(a - t) >= 0.5` (exact for every finite `a`) the result is
`t + 1.0` when `a > 0.0`, else `t - 1.0`; otherwise `t`. For `abs(a) >= 4503599627370496.0` (2^52),
inf and NaN the result is `a`. `round(0.49999999999999994)` is `0.0` (the naive `floor(a + 0.5)`
gives `1.0`); `round(-0.4)` is `-0.0`.

### 1.4 NaN: one value, bits unobservable (changes recorded text)

There is one NaN as far as any program can tell: `==` is false and `!=` true against everything,
NaN included; `< <= > >=` are false; `to_int` traps `bad_conversion`; `min` and `max` give NaN;
`fixed` prints `NaN` whatever the sign bit. No row of this table exposes the bits of a Float. So:
the interpreter and every runtime routine (`min`, `max`, the tools' value text) write
`0x7FF8000000000000` whenever they make a NaN themselves; a compiled back end emits nothing for
NaN; and a hand-written test vector compares a NaN result as a class (any NaN matches NaN) and
every other value bit for bit, the sign of zero included.

Why not the recorded "every operation gives exactly `0x7FF8000000000000`, unary minus and abs
included": it can be built (an unordered compare and a select after every `fadd fsub fmul fdiv
fsqrt fneg fabs`), but x86 makes NaNs with the sign bit set and ARM clear, so it costs two
instructions per Float operation on every native target, a real M4-28 and a real check in M6-08,
for a difference no program can observe. Line 161's "same behaviour both modes" holds because the
behaviour is the same. The day a built-in exposes Float bits, that one built-in canonicalises on
the way out, and the recorded guarantee is restored at one point.

### 1.5 Conversions and text to number

`to_float(n)` is the nearest Float, ties to even, never traps. `to_int(x)` is `trunc(x)` as an Int
and traps `bad_conversion` when `x` is NaN or `x < -9223372036854775808.0` or
`x >= 9223372036854775808.0` (both bounds are exact Floats; NaN fails both compares, so two
compares guard the instruction on every target). Int where a Float is expected, or the reverse, is
`type-mismatch`, and the message names the repair: `to_float`, `to_int`, or the literal written
with `.0`. In an operation that mixes the two the repair is `to_float(NAME)` or the literal with
`.0`, never `to_int`.

`parse_int` and `parse_float` (names from M2-14) accept exactly `-?` digits, and for Float
optionally `.` digits with at least one digit on each side; nothing is trimmed; anything else is
`None`. Leading zeros are accepted (`"007"` is `Some(7)`): input data is zero-padded in real files.
An Int that does not fit is `None`. A Float is the correctly rounded value, ties to even; too large
gives `Some(inf)` or `Some(-inf)`, too small gives a subnormal or `0.0`. Float literals use the
same routine, so a literal equals the parse of its own text.

### 1.6 `fixed`: exact decimal, ties away from zero (M2-03.6)

`fixed(x; digits:)` with `digits` 0 to 20, else `out_of_bounds`, checked before `x` is looked at. The result is the exact decimal
value of `x` rounded to `digits` places with an exact half going away from zero, printed as whole
digits, then `.` and exactly `digits` fraction digits (no point when `digits` is 0), with `-` first
whenever the sign bit is set. Never an exponent, never `+`, never padding. `NaN`, `inf`, `-inf`.
The algorithm is integer-only (section 2.6) and lives once in the runtime; no back end may use a
host formatter, because C's `printf`, Rust's `{:.n}` and JavaScript's `toFixed` disagree on ties
and none can be told to tie away.

### 1.7 String: code points, UTF-8 order (M2-03.2)

A String is a row of Unicode scalar values (0 to 1114111, none in 55296 to 57343). Positions,
`len` and slices count code points. `==` is code point by code point, no normalisation. `<` is
lexicographic by code point value, a proper prefix first. Code point order equals UTF-8 byte order,
so a back end that stores UTF-8 compares bytes and never decodes; this is meaning, so a UTF-16 host
(JavaScript) must compare by code point, not by unit. The representation is the back ends' (M4-22,
M6-10), with the ASCII fast path the recorded text asks of M4-32 and M6-11.

### 1.8 Source encoding

A source file is UTF-8. A byte sequence that is not valid UTF-8 (overlong forms and encoded
surrogates included) is `invalid-byte` at its first byte. Bytes 0x00 to 0x1F other than line feed,
and 0x7F, are `invalid-byte` wherever they stand, inside a string too (tab and carriage return stay
as M2-02 §1.9 recorded). A character above 0x7F is legal only inside a string literal or a comment;
anywhere else, a byte order mark at the file start included, it is `unexpected-character` at its
first byte: "only ASCII outside strings and comments". Columns keep M1's rule and count bytes.

Why not "a source that is not UTF-8 fails as not text": that is M2-15's rule for a file read at
run time. A source file is the lexer's, and the lexer reports a position.

### 1.9 Escapes: seven, no `\u{hex}` (changes recorded text)

`\n \r \t \\ \" \{ \}`. `\` followed by anything else, line feed and end of file included, is
`bad-escape` at the `\`. Why `\u{hex}` goes: the source is UTF-8, so a non-ASCII character is typed
as itself, and `\u{e9}` would be a second spelling of `é` (line 51: one spelling per construct;
M4-47 would have to pick one). A control character other than 9, 10 and 13 is written with
`from_code` (M2-14); no task class writes one (M2-01.5). Dropping it removes hex parsing and the
empty, over-long, surrogate and out-of-range cases from every lexer and from the vectors.

### 1.10 Braces in a string: symmetric (adds to recorded text)

`{` opens an interpolation; `}` closes one. A literal brace is written `\{` or `\}`. A bare `}`
outside an interpolation is `unexpected-character` at the `}`: "write \}". The recorded text named
only `\{`, which would make `"light}"` text while `"{light}"` is code; a stray `}` is nearly always
a broken interpolation, and one rule for both braces is the smaller lexer.

### 1.11 Interpolation: plain scan, no quotes or braces inside

`"{expr}"`: the expression text runs to the first `}` and may hold no `"`, `{` or `}` (`"` there is
`unexpected-character` at the quote; so no string literal, record literal, block, `if` or `match`
inside: put it in a `let`). The text is lexed and parsed as an ordinary expression at its real file
position, so an error inside points into the file. An empty `{}` is `unexpected-token` at the `}`.
The expression is an Int, Bool or String; a Float is `type-mismatch` at the expression: "a Float
has no text here: write {fixed(x, digits: 2)}"; any other type waits for M2-09 and is
`type-mismatch` in M2. The literal's value is its text parts and the expressions' texts joined in
written order, evaluated left to right. `"\{x\}"` is `{x}`; `"{"` alone is `unterminated-string`.

Why no brace counting: the string token then ends by one scan, the recorded "contains no string
literal" follows from "no quote", and M2-02 §1.7's level for the interpolation `{` is the only
level a string can add. The recorded sentence stays true; this fixes how it is enforced.

### 1.12 Literals: one spelling (changes recorded text)

Int: `0`, or a digit 1 to 9 then digits. Float: the same whole part, `.`, one or more digits
(`1.50` is legal and is `1.5`). No `+`, no `_`, no hex, no exponent, no `1.` or `.5`. A `0` followed
by a digit is `unexpected-character` at that digit: "no leading zero: write 7". A `-` directly
before a literal in operand position is part of the literal (M2-02's grammar `[ "-" ] INT`; the
parser folds, so `a -1` still subtracts and `-9223372036854775808` is a literal; `-(9223372036854775808)`
is not folded). A literal outside the Int range, or a Float literal whose nearest value is
infinite, is the check error `literal-out-of-range` at the literal. A Float literal too small is
`0.0` or a subnormal, never an error. The recorded text said "decimal digits only, one spelling";
`007` and `7` were two spellings of one value, which M4-47 would otherwise have to rewrite.
`parse_int` stays lenient (1.5).

### 1.13 Bool, precedence, ranges, order

As recorded. `&&` and `||` evaluate the right side only when needed; `!` negates; Bool has `==`
and `!=` and no order. Precedence from tightest: call, index, field, `?` (M2-12); unary `-` and
`!`; `* / %`; `+ -`; `..<`; comparisons; `&&`; `||`. Same level groups left; a comparison does not
chain, which M2-02's grammar enforces (`a < b < c` is `unexpected-token` at the second `<`: "write
a < b && b < c"). `%` on Float is `type-mismatch`: "no % on Float: write x - y * trunc(x / y)".
`a..b` and `a...b`: the lexer accepts `..<` only, so the first `.` not starting `..<` is
`unexpected-character`: "write a..<b". Evaluation is strictly left to right, as recorded and as
section 2.8 writes out; a check happens when its operation runs, never earlier (M2-06.2).

## 2. The table

Every row is meaning. The interpreter, the LLVM back end and every later one are tested against
the same vectors (M2-08). "MIN" is -9223372036854775808, "MAX" 9223372036854775807.

by its specification). With no exponent in the grammar the input is at most a sign, whole digits
and fraction digits; many digits cost time, never a different answer.

### 2.6 The `fixed` algorithm

Write finite `x` as `m * 2^e`, `m` an integer below 2^53, `e` from -1074 to 971. Let
`N = m * 10^digits`; `N < 2^120`, so 128-bit integers suffice.

- `e >= 0`: `x` is a whole number. Print the big integer `m * 2^e` (at most 309 digits; a digit
  array doubled `e` times, or any exact method), then `.` and `digits` zeros.
- `e < 0`: `k = -e`. If `k >= 121` then `q = 0` (`2N < 2^121`, so even an exact half cannot
  occur). Else `q = N >> k`, `r = N - (q << k)`; if `2r >= 2^k` then `q = q + 1`. Print `q` in
  decimal padded on the left with zeros to at least `digits + 1` digits, and insert the point
  `digits` from the right.
- `-` first whenever the sign bit is set, then the digits above.

No floating-point operation is used, so every back end gives the same bytes. About a hundred lines
of Rust once; a C port is the same; JavaScript uses BigInt.

### 2.7 Grammar

Additions to M2-02 §2. Tokens are built from bytes; a character above 0x7F is one or more bytes.

```
INT         = "0" | digit19 { digit }
FLOAT       = INT "." digit { digit }
STRING      = '"' { char | escape | interp } '"'
char        = any character of code point >= 0x20 other than '"' '\' '{' '}' and 0x7F
escape      = "\n" | "\r" | "\t" | "\\" | '\"' | "\{" | "\}"
interp      = "{" expr "}"            (* expr holds no '"' '{' '}'; one nesting level *)
```

Errors in a string literal, in scan order: line feed or end of file before the closing quote is
`unterminated-string` at the opening quote; a bad `\` is `bad-escape` at the `\`; a bare `}`, or a
`"` inside an interpolation, is `unexpected-character` at that byte; an empty interpolation is
`unexpected-token` at its `}`; an invalid byte is `invalid-byte` at the byte. The first found wins.

### 2.8 Evaluation order

Strictly left to right, one rule per form:

- Binary operator: left operand, right operand, then the operation and its check. `&&` and `||`
  evaluate the right side only when needed.
- Call: arguments in written order, each fully, then the call. An `&place` argument evaluates its
  index expressions in that position; the bounds check for the place happens at the call, after
  all arguments.
- Index and slice: the value, then the index (both range ends, start first), then the check and
  the read. On a chain of steps from a place, every index comes first, then the checks and reads
  step by step (M2-05 Rule D).
- List, Map and record literals and interpolated strings: parts in written order.
- `if` and `match`: the condition or subject, then only the chosen branch or arm.
- `place = expr` and `place op= expr`: the index expressions of the place in written order (outer
  first), then `expr`, then for `op=` the read of the place with its bounds check, the operation
  with its check, then the write with its bounds check. So `xs[i] = f(&xs)` runs `i`, then `f`,
  then checks and stores (M2-05); `xs[i] += g()` runs `i`, `g`, reads, adds, writes.
- `let` and `var`: the value, then the binding.
- Ranges: both ends evaluated once, start then end, before the first step; a `for` with
  `start >= end` runs zero times and its variable never overflows; a slice with `start > end`
  traps `out_of_bounds`.

The first trap in this order is the one reported (M2-06.2): `xs[5] + (1 / 0)` on three items traps
`out_of_bounds`; `(1 / 0) + xs[5]` traps `divide_by_zero`.

### 2.9 Runtime routines

Written once in Rust, called by the interpreter and linked into native builds; a C or JavaScript
target ports exactly these and nothing else: Int to text, `fixed`, `parse_int`, `parse_float`
(shape check plus correctly rounded conversion), `round`, Float `min` and `max`, String make, join,
compare, index, slice, `code_at`, `from_code`, and the trap entry (kind and position). Every other
row is one instruction with guards.

Lex (status 1, at the byte):

- `bad-escape` at the `\`: "escapes are \n \r \t \\ \" \{ \}".
- `unexpected-character` keeps its code; new messages: "write \}" (bare `}` in a string), "no
  string literal inside { }" (a `"` in an interpolation), "no leading zero: write 7", "write
  a..<b" (`..` or `...`), "only ASCII outside strings and comments".

Check (status 1, at the literal or expression):

- `literal-out-of-range` at the literal: "largest Int is 9223372036854775807" / "this Float is
  infinite; largest is about 1.8 followed by 308 digits".
- `type-mismatch` keeps its code; new messages: "a Float has no text here: write
  {fixed(x, digits: 2)}", "no % on Float: write x - y * trunc(x / y)", "write to_float(n)" /

Trap kinds used: `overflow`, `divide_by_zero`, `out_of_bounds`, `bad_conversion`; none added

## 6. What this page changes in recorded text

- DECISIONS.md M2-03, "Canonical NaN bits": replaced by 1.4. The bits are unobservable; the
  interpreter and runtime routines write `0x7FF8000000000000` when they make a NaN; compiled
  arithmetic does not canonicalise; vectors compare NaN as a class.
- DECISIONS.md M2-03, "String details": the escape list is `\n \r \t \\ \" \{ \}`; `\u{hex}` is
  gone; a bare `}` is an error.
- DECISIONS.md M2-03, "Int literals" and "Float": no leading zero in a source literal
  (`parse_int` still accepts them); the out-of-range code is `literal-out-of-range`.
- DECISIONS.md M2-03, "Interpolation": the expression holds no `"`, `{` or `}` (a refinement of
  "contains no string literal").
- TASKS.md M2-07: tokens INT and FLOAT as in 2.7 (no leading zero, no exponent, no hex, no
  underscore); STRING with seven escapes and interpolation spans; `..<` only; UTF-8 validation with
  the rules of 1.8; new code `bad-escape`.
- TASKS.md M2-08: implements `round`, `fixed` and decimal-to-binary by sections 1.3, 2.6 and 2.3 in
  a module shared with paka-rt; vectors hold every sample in this page plus signed-zero, subnormal,
  2^52, 2^53 and 2^63 cases; "float rows bit for bit" gains the clause "a NaN result matches as a
  class". The routines of 2.9 are the test surface.
- TASKS.md M2-08b and M4-29: stay dropped.
- TASKS.md M2-11: an interpolation's expression is parsed from its file span; a unary minus on a
