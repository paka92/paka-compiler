# M5-09 · The preview route on Wayland and the Look protocol

Status: approved by the owner on 2026-10-26.

Base: DECISIONS.md holds no recommended page for M5-09. The starting points were the paper's
sections 3.3 and 6, M4-03's envelope, M4-04's runner, M5-06's paths and tree text, and the M5-08
trial. Wayland allows no embedding of another program's window, no screen grab and no injected
input, so the route uses none of them. Where a choice had a smaller or safer option, that option
was taken; each point says why. No new trial was needed: the one fact the trial left open, how
often winit can start, was read from the vendored winit source.

## 1. Points

**1.1 The route: the app's own window, and no preview pane.** In dev mode a visual app opens one
top-level Wayland window of its own. The paper's preview pane is not built in M5.

- A pane inside an editor would need the editor to host Paka's drawing, which Wayland cannot do
  for another program's window. Look's screenshot already gives an agent the picture, and an
  editor can show that PNG later under its own ruling.
- With no Wayland display the app runs with no window, as M5-20 and M5-25 built it. The Look calls
  are the same either way.

**1.2 The window lives in the process that runs the app,** M4-04's runner in dev mode. The server
never opens one.

- A crash in drawing or in the platform libraries then ends the runner and closes the window, and
  the server answers and starts a new runner, as M4-04 rules for any crash.
- winit builds one event loop per process, ever: a second build fails. The runner builds it once,
  on a thread of its own, and keeps it; each launch opens a window in it and an ending app closes
  only its window. A new runner is a new process, so it may build its own.
- A Look call reaches the loop through winit's event-loop proxy, and its reply comes back over a
  channel.

**1.3 Look acts on the element tree, never on the screen.**

- A click names an element by M5-06's path and enters the app's input queue as the same event a
  pointer click on that element makes. It needs no coordinates or hit testing, so it works with
  no window.
- A keystroke enters the queue as the key event the window would make.
- The screenshot is drawn again from the current tree through vello_cpu (M5-33), not grabbed.
- Look input and the window's own input share one queue in arrival order (M5-03), so the two can
  never race.

**1.4 The four Look calls are new `call` values in M4-03's envelope,** with no new version, as
M4-03 rules. Section 2 gives their fields.

| Call | Does |
|---|---|
| `look_tree` | gives the current tree in M5-06's text form |
| `look_screenshot` | gives a PNG of the current tree, drawn at a scale of 1 or 2 |
| `look_click` | clicks the element at a path, then gives the tree |
| `look_key` | types text into the focused Input, or presses one named key, then gives the tree |

- Four calls, as the paper names them, keep each table small and each misuse a plain
  `bad_request`.
- One `look` call with a `do` field would put four sets of fields in one table, so it was not
  taken.

**1.5 The `run` call launches a visual app.** A run naming a visual app starts it and replies at
once, without waiting for it to end.

- It opens a window when the server has a Wayland display, and otherwise runs with no window.
- A run while an app is running ends that app and launches again.
- This is the smallest change: M4-03's run already names the app and its arguments, so no fifth
  Look call is needed to start one.

**1.6 The screenshot travels in the reply** as base64 text, drawn with the M5-08 standard-library
PNG encoder.

- At 480 by 360 units and scale 1 that is about 0.9 MB of text, which an agent tool can carry.
- Writing the PNG to a file was not taken: the server would then write outside the program's
  files, and the agent would need a path it cannot see.
- Scale is capped at 2, the largest the trial checked, so a reply stays near 3.7 MB at most.

## 2. Calls

Every reply carries M4-03's `v`, `id` and `ok`. A failure uses M4-03's error shape.

**`look_tree`.** No fields.

- Reply: `tree`, the M5-06 tree text, and `running`, which is true.

**`look_screenshot`.**

| Field | Type | Required | Meaning |
|---|---|---|---|
| `scale` | int | no | 1 or 2; default 1. Units are multiplied by it (M5-05). |

- Reply: `png`, the image as base64 with padding; `width` and `height`, in pixels.
- The size is the window's current size in units, or 480 by 360 with no window (M5-05).

**`look_click`.**

| Field | Type | Required | Meaning |
|---|---|---|---|
| `path` | string | yes | M5-06's path form; the root is `""`. |

- A click on a Button sends its message.
- A click on an Input moves focus there with the cursor at the end, as `ui_click` does.
- Any other click, a click on a placeholder included, does nothing.

**`look_key`.** Exactly one of `text` and `key` is given.

| Field | Type | Required | Meaning |
|---|---|---|---|
| `text` | string | no | Typed into the focused Input one code point at a time, as `ui_type` does. |
| `key` | string | no | One of `Tab`, `Shift+Tab`, `Enter`, `Space`, `Backspace`, `Delete`, `Left`, `Right`, `Home`, `End`, and `Shift+` with any of the last four. |

- Keys follow M5-08's focus rule. Tab and Shift+Tab move focus. Enter or Space on a focused
  Button clicks it. Space in an Input types a space. Enter in an Input does nothing.
- The rest go to the focused Input as M5-19 built them.

**Replies of `look_click` and `look_key`.**

- `tree`: the tree after the event's turn, its view run.
- `running`: false when that turn ended the app.
- `trap`: M2-06's fields when a handler or view trapped in that turn, else null. Rollback still
  follows M5-25b, so the tree is the old one.

**`run` on a visual app.** The reply's `run` holds:

- `tree`, the first tree;
- `window`, true when a window opened;
- `stdout`, `stderr` and `trap` as M4-03 has them;
- `status` and `stopped` null while the app runs.

**New error kinds.**

| Kind | When |
|---|---|
| `not_running` | A Look call with no visual app running: none was launched, or it ended by `Exit`, a trap at launch or a closed window. |
| `no_element` | `look_click`'s path names nothing in the current tree. |
| `no_focus` | `look_key` with `text` and no focused Input. |

A badly formed path, an unknown key name, a scale other than 1 or 2, or both or neither of `text`
and `key` is `bad_request`.

## 3. Rules that follow

- A focused Button shows `focus` in the tree text, in M5-06's form. UI examples never see one,
  since no `ui_` function sends Tab.
- A reply is sent after the event's own turn. Answers to effects that turn started arrive later
  and show in a later tree.
- With a window, the frame for each new tree is requested before the reply is sent (M5-38).
- Look cannot compose text through an input method. IME stays M5-37's hand check, and a preedit
  shows only in the tree text.
- Look calls are not held to a token budget. Find and view keep theirs.
- An edit that installs while an app runs swaps or resets it as M5-07 rules, and Look then reads
  the new tree.
- `paka run` on a visual app opens the same window. It still refuses one until M5-35 builds the
  window.
- The paper's preview pane stays open, with no milestone.
