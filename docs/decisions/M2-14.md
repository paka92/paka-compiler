# M2-14 · The built-in types and functions a headless program may call: decision

Base: the recorded M2-14 page in DECISIONS.md, written out as one closed table (9 types, 4
constructors, 63 functions) with the exact result of every row for every input, the trap kind or
Option on each, the Map rules, the sort as a procedure, the text rules, and one sample per task
class. All seven recorded picks stand. Six settled lines are made exact where they were loose,
marked **fixes**: the sort is given as a procedure over ranges, so sub-ranges split the same way
the whole does; `swap` checks both positions even when they are equal; the Map key-type error is
the existing `type-mismatch`; `lines` is defined through `split`; a width below zero in `pad_left`
and `pad_right` changes nothing; every row that grows a value checks M2-06's cap before growing.
One settled line is answered that the recorded page left open: native code may inline a row.

The one idea: a row is a claim or a question (M2-12). Square brackets and a position are claims
and trap; a lookup by name or a parse is a question and gives an Option. Every row has one result
that depends on its arguments alone, so every back end and every run agree.

## 1. Resolutions, point by point

No Set (write `Map<K, Bool>`), no tuple, no priority queue, no pool or shared type (M2-10), no

Upper-case built-in names: `Int`, `Float`, `Bool`, `String`, `List`, `Map`, `Option`, `Some`,

### 1.2 How a row reads

- Form: `name(params) -> result`, letters `T`, `K`, `V`, `E` for any type; a row with no arrow
  gives no value and may stand only as a statement (M2-09, M2-02).
- Argument order: the value worked on is the first parameter, every row is positional, and the
  only labels are `fixed(x; digits:)`, `insert(xs, item; at:)` and `list_of(item; count:)`, the
  rows where an Int item and an Int position or count could swap unseen. `join` takes the parts
  first, `split` and `replace` the text first, `get`, `has` and `remove` the Map first,
  `unwrap_or` and `ok_or` the Option first.
- In place: a row that changes a List or a Map takes it as its first parameter, `inout`, written
  `&place` at the call (M2-05 §1.4); no row takes two inout parameters. Every other row gives a
  fresh value and changes nothing. Results that come out of a collection (`pop`, `remove_at`,
  `get`, `keys`, `values`, `list_of`'s copies) are copies in meaning (M2-05 §1.1).
- Several types under one name (`len`, `is_empty`, `contains`, `find`, `min`, `max`, `abs`,
  `sort`): the first argument's type picks the row; `[]` picks the List row and `[:]` the Map row;
  letters then bind by M2-09 §1.3's walk. A type with no row is `type-mismatch` at that argument,
  listing the accepted types ("len takes a String, List or Map"). `contains([], 1)` binds `T` from `1`; `len([])` is
  `cannot-infer` at `[]`, as M2-09 has it.
- Not values: a built-in function cannot be passed or bound (`not-a-value`, M2-09). `sort_by`'s
  function is therefore a named user function.
- Names: all 63 are lower case, in M2-13's names table. A user definition of one is
  `duplicate-name`, fix "NAME is a built-in; rename it"; a local may hide one (M2-09).

### 1.11 Map: order, keys, literal, index, change (picks 1 and 2)

**Order and keys.** A Map holds its entries in rising key order: Int by signed number, String by
code point, which is UTF-8 byte order (M2-03 §2.5). Two equal Maps (M2-09 §1.4) walk alike, and
`keys`, `values` and the value text form need no second rule. Only `Int` and `String` are key
types. **fixes** any other key type is the existing `type-mismatch`, message "a Map key is an Int
or a String", at the key type's name in a signature or annotation (M2-16) and at the first key of a
literal (M2-20). `wrong-type-arguments` is not used: it means a wrong number of type arguments
(M1 spec §6), and `Map<Float, Int>` has the right number.

**Literal.** `[k1: v1, k2: v2]` evaluates `k1, v1, k2, v2` left to right as written and adds each
entry in turn; a later equal key replaces the earlier value, both values having been evaluated:
`["a": 1, "a": 2]` is `["a": 2]`. All keys share one type and all values one type; `K` and `V`
come from the first entry in M2-09's step 1 (a literal with entries is self-typed), so
`["a": 1, "b": 2.0]` is `type-mismatch` at `2.0`. `[:]` is typed from its position like `[]`;
`let m = [:]` is `cannot-infer`. A literal counts as a call in M2-05's rules. Layout: flat, one
space after each colon and comma (M4-47), `[:]` when empty.

**Index.** `m[key]` as a read claims the key is there and traps `out_of_bounds` at the `[`, detail
`key "x"` or `key 5` in the value text form. `m[key] = v` is the one form that adds: a missing key
is created, a present one replaced; it never traps (`memory` past the cap aside). Every other use
of a Map step needs the key present: `m[key] += 1`, `m[key].field = v`, `&m[key]`, and every step
but the last of an assignment, so `m[a][b] = v` needs `a` and may add `b` when `m[a]` is itself a
Map. Evaluation order is M2-03's for assignment: the target's key expressions, the right side, then
the lookup and store (M2-05 Rule D). The count idiom the reference shows is
`counts[w] = unwrap_or(get(counts, w), 0) + 1`; `counts[w] += 1` on a new key traps, and the
trap's help line names the idiom.

**Place.** `&m[key]` is a place (M2-05 §1.4) and may continue with field, List-index and Map-index
steps. In the overlap rule a Map step counts like a List step: two entries of one Map always
overlap, so `f(&m[a], m[b])` is `inout-overlap` unless `m[b]` is an Int, Float or Bool, and
`f(&m[a], &m[b])` is refused; the fix is `f(&m, a, b)`. `remove(&m, k)` inside `for k in keys(m)`
is accepted: `keys(m)` is a fresh List.

### 1.12 Walking a Map or a String (pick 3)

`for` walks a List or an Int range and nothing else (M2-02). `for c in text` and `for k in m` are
`type-mismatch` at the walked expression, fixes "write chars(text)" and "write keys(m)".
`keys(m)`, `values(m)` and `chars(text)` are fresh Lists, so the body may change the Map or the
String and M2-05 §1.7's frozen-place rule needs no extension. Key and value together:
`for k in keys(m) { let v = m[k] ... }`, one trap-free lookup per entry, accepted cost.

### 1.13 The sort, exactly (picks 4 and 5)

One procedure, in every back end, for `sort` and `sort_by`, over the positions `lo..<hi`:

```
sort_range(lo, hi):
  if hi - lo < 2 { return }
  mid = lo + (hi - lo) / 2             // Int division; at the top this is len / 2
  sort_range(lo, mid)                  // the left half, completely
  sort_range(mid, hi)                  // then the right half
  i = lo; j = mid; out = []
  while i < mid && j < hi {
    if before(xs[j], xs[i]) { take xs[j]; j += 1 } else { take xs[i]; i += 1 }
  }
  take the rest of the left, then the rest of the right     // no further calls
  write out back over lo..<hi
```

`sort_by(&xs, before)` is `sort_range(0, len(xs))`; `sort(&xs)` is the same with `<`. **fixes**
the recorded line named the top split only; `mid = lo + (hi - lo) / 2` says how every sub-range
splits. Fixed by this: the number of calls to `before`, their order, and which two items each sees,
as a function of nothing but `len` and the Bools returned so far. The right item is passed first:
the call asks "must the right one come before the left one?" and the left one is taken on `false`,
which is what makes the sort stable. So a `before` that contradicts itself still has one result: a
function that always answers `true` reverses the List (`[3, 1, 2]` becomes `[2, 1, 3]`), one that
always answers `false` leaves it as it is, and any other answers the same in every back end, since
a Paka function has no closure, no global and no effect (M2-09, M2-15). A trap inside `before` ends
the program at the first call that traps, in this order (M2-06 §1.3); nothing after it runs, and the
List's half-sorted state is never observed. Items are moved, not copied, through the scratch range,
so no copy the program could see happens; `before` receives its two items read-only (M2-05 §1.1).
`before` cannot reach `xs`, which is held by `&` for the whole call. Cost: at most
`len * ceil(log2 len)` calls and `len` extra slots; release code may not swap in a faster sort
(M6-14 keeps the call sequence), the one price of one meaning.

### 1.14 Text rules (pick 7)

- White space, exactly: the six characters with code points 9 to 13 and 32 (tab, line feed,
  vertical tab, form feed, carriage return, space). `trim`, `trim_start`, `trim_end` and `words`
  use this set; no other row does. On ASCII text this is what Rust's `trim` and `split_whitespace`
  and TypeScript's `trim` do.
- Case: `upper` and `lower` change `a` to `z` and `A` to `Z` only. No Unicode table, no length
  change, no version drift; the result is the same in every back end with no data to ship.
- Matching (`contains`, `find`, `starts_with`, `ends_with`, `split`, `replace`): exact code-point
  equality, left to right, earliest match, no overlap. No regex, no pattern, no case folding.
- Positions and lengths count code points (M2-03); String keys and `sort` on Strings order by code
  point. The experiment's inputs are ASCII (M2-01 §2); the non-ASCII results above exist so that
  M2-33's tests have one answer.

### 1.15 Growth, traps and the detail line

Trap kinds: none added. `out_of_bounds`: a bad position in `code_at`, `insert`, `remove_at`,
`swap`; `pop` on an empty List; a missing key at a Map `[`; a count below zero in `repeat` and
`list_of`; a shift count outside 0 to 63; `fixed` digits outside 0 to 20. `bad_conversion`:
`to_int`, `from_code`. `overflow`: `abs` of the smallest Int. `assert`: `assert`, `unreachable`.
`memory`: **fixes** every row that grows a List, Map or String (`append`, `extend`, `insert`,
`list_of`, `join`, `repeat`, `pad_left`, `pad_right`, `replace`, `m[key] = v` on a new key) checks
M2-06's cap of 16,777,216 items, entries or bytes before growing and traps there, before any part
of the result exists. Every other row never traps. A built-in's trap is reported at the user's call,
at the name token, with M2-06 §1.2's detail text; `sort_by`'s function traps where it traps.
`m[key] = v` on a new key traps `memory` at its last `[`.

### 1.16 Value text form, for the tools only

A Float prints as the shortest digits that read back as the same Float, with no exponent and at
least one digit on each side of the point: `1.0`, `0.1`, `-0.0`, `100.0`, `0.30000000000000004`;
NaN and the infinities print as `fixed` prints them. A Map prints as its literal in key order with
each key and value in this form, `[:]` when empty. Only the runtime's own code produces this text
(M2-27's failed comparisons, M5-16's tree text); no M2 program can reach it, since interpolation
takes Int, Bool and String only and there is no to-text row (M2-09).

### 1.17 Size of the table and what is left out (pick 6)

63 functions. Each replaces a loop a model would otherwise write by hand in at least one of the
seven task classes, and each is something Rust and TypeScript give for free. The signatures with
one-line results take about 2,000 of the reference's 8,000 tokens under M2-18's rule (bytes divided
by 3): 63 rows at some 90 bytes each, plus the constructors, the count idiom and the sort in one
sentence. The edge lists above are not in the reference; they become M2-39b's cases.

Left out on purpose: `map`, `filter`, `fold`, `reduce`, `any`, `all`, `sum`, `for_each` (without
closures a passed function cannot see a local, so most habitual uses would be errors anyway; loops
are the form, and M2-09's look-again does not fire); `sorted` and `reversed` (one rule: in place);
`Set`, priority queue, `entries(m)` (no tuple); regex and any text pattern; Unicode case and
white-space tables; `to_text` on Float (`fixed` is it); `unwrap`, `expect`, `panic`, `is_some`,
`is_ok` (M2-12); `index_of` (it is `find`); `clamp`, `pow`, random, dates. Each is a plain new row
later if practice runs demand it; adding a row breaks only a program that defined that name, and
the fix is a rename.

If M2-18 cannot fit the table, rows go in this order: `extend`, `pad_right`, `trim_start`,
`trim_end`, `is_empty`, `values`. Each is written in one line with the rows that stay, and each
dropped row is listed in that pull request as a change to this table. No row named by another
record (`is_empty`, `contains` in M2-09 §1.2; `extend` in M2-09's fix text; `repeat`, `insert` in
M2-12 §1.5 and M2-06 §1.1) goes before the ones that are only here.

## 2. Grammar

## 3. Implementation rule: interpreter and native code

- Every row is one routine in the runtime crate (M2-03 §2.9's list grows by the String, List and
  Map rows), driven for the generic rows by the per-type layout record (M2-09 §3, M4-22). The
  interpreter calls them with its values; dev native code calls them through private runtime names
  (M4-29, M4-32) with bounds checks inside the routine.
- Native code may inline a row. A row's meaning is its result, its trap kind and site, and for
  `sort` and `sort_by` the sequence of calls to `before`; a back end that keeps those may open any
  row in place (`len`, `is_empty`, `min`, `has`, an `append` under the cap) under M2-06 §1.3's two
  obligations and M6-11's bit-identical rule for Float. The alternatives considered included a rule
  that no row is ever inlined; it is not taken, because M2-09 §3 already allows per-type copies and
  the obligations above are what make a copy correct, not the call.
- Map is an ordered map keyed by Int or String with comparison and no hashing: the interpreter's
  standard ordered map (M2-26), the runtime's own sorted structure in native code (M4-38b).
- The sort is one routine over a scratch range of `len` slots, moving items; per-type copies
  (M6-14) make the same calls in the same order.
- The text rows share one left-to-right matcher on code points, one white-space test on the six
  code points and one ASCII case map. `tests/vectors/ops.vec` gains a String section for them and
  `rows.txt` their names; the List and Map rows are tested by M2-34's goldens.

## 4. Samples, one per task class

```
// 1 Text processing: word counts, most frequent first, ties by word
type Count { word: String, n: Int }
fn more(a: Count, b: Count) -> Bool { a.n > b.n || a.n == b.n && a.word < b.word }
fn top(text: String) -> List<String> {
  var counts: Map<String, Int> = [:]
  for w in words(lower(text)) { counts[w] = unwrap_or(get(counts, w), 0) + 1 }
  var rows: List<Count> = []
  for w in keys(counts) { append(&rows, Count { word: w, n: counts[w] }) }
  sort_by(&rows, more)
  var out: List<String> = []
  for r in rows {
    let n = "{r.n}"
    append(&out, "{pad_right(r.word, 12)}{pad_left(n, 5)}")
  }
  out
}

// 2 Parsing and small interpreters: sum the integers of "12 + 3 - 4"
fn eval(src: String) -> Result<Int, String> {
  var total = 0
  var sign = 1
  for t in words(src) {
    if t == "+" {
      sign = 1
    } else if t == "-" {
      sign = -1
    } else {
      total += sign * ok_or(parse_int(t), "bad number {t}")?
    }
  }
  Ok(total)
}

// 3 State machines and simulations: a light that cycles on ticks
enum Light { Red, Green, Amber }
fn step(l: Light) -> Light {
  match l {
    Red => Green
    Green => Amber
    Amber => Red
  }
}
fn after(ticks: Int) -> Light {
  var l = Red
  for i in 0..<ticks { l = step(l) }
  l
}

// 4 Grids and dynamic programming: minimum path sum, down or right
fn min_path(g: List<List<Int>>) -> Int {
  var best = list_of(list_of(0, count: len(g[0])), count: len(g))
  for r in 0..<len(g) {
    for c in 0..<len(g[0]) {
      var from = 0
      if r > 0 && c > 0 {
        from = min(best[r - 1][c], best[r][c - 1])
      } else if r > 0 {
        from = best[r - 1][c]
      } else if c > 0 {
        from = best[r][c - 1]
      }
      best[r][c] = g[r][c] + from
    }
  }
  best[len(g) - 1][len(g[0]) - 1]
}

// 5 Graph algorithms by list index: breadth-first order from a named node
fn bfs(adj: List<List<Int>>, index: Map<String, Int>, start: String) -> List<Int> {
  var seen = list_of(false, count: len(adj))
  var q = [index[start]]
  seen[q[0]] = true
  var i = 0
  while i < len(q) {
    for v in adj[q[i]] {
      if !seen[v] {
        seen[v] = true
        append(&q, v)
      }
    }
    i += 1
  }
  q
}

// 6 Integer and float reports: mean and extremes, two decimals, aligned
fn report(xs: List<Float>) -> String {
  var sum = 0.0
  var lo = xs[0]
  var hi = xs[0]
  for x in xs {
    sum += x
    lo = min(lo, x)
    hi = max(hi, x)
  }
  let mean = sum / to_float(len(xs))
  join([pad_left(fixed(lo, digits: 2), 8), pad_left(fixed(mean, digits: 2), 8),
        pad_left(fixed(hi, digits: 2), 8)], " ")
}

// 7 File tools: strip trailing white space from every line (effects are M2-15's)
fn clean(text: String) -> String {
  var out: List<String> = []
  for l in lines(text) { append(&out, trim_end(l)) }
  join(out, "\n") + "\n"
}
```

## 5. Alternatives considered

- **A table of 48 rows.** Drop `is_empty`, `contains`, `values`, `starts_with`, `ends_with`,
  `replace`, `extend`, `repeat`, `pad_right`, `reverse`, `trim_start`, `trim_end`, `insert`,
  `upper`, `lower`, each a short loop, to save about 500 reference tokens. Not taken: M2-09 §1.2
  lists `is_empty` and `contains` and names `extend` in a fix line; M2-12 §1.5 and M2-06 §1.1
  list `repeat` and `insert` among the trapping rows. Dropping them corrects four records for a
  saving the reference does not need, and every program then writes `trim_end` and `lower` by
  hand before the go/no-go. The recorded test is "replaces a loop", not "cannot be done without".
- **A wrong-name table in the check.** Some forty habit spellings (`push`, `length`, `indexOf`,
  `toUpperCase`, `splitlines`, `sorted`) folded to lower snake case and mapped to the row to name
  in an `unknown-name` fix. Not taken here: it is checker text, not language meaning, and a list
  written before any run guesses which names cost edits. M2-13 owns the `unknown-name` fix and
  already proposes the nearest known name; the practice runs (M3-03) count the wrong names that
  occur, and the ones that do can then be added to M2-13's fix text, a few lines each, with no
  reference cost and no conformance case.
- **`wrong-type-arguments` for a bad Map key type.** Rejected: that code means a wrong count.
- **`lines` by prose.** "Text after the last line feed is one more line only if not empty" gives
  the same results; the `split` definition is checkable in one line and is kept.
- **`sort` restricted to Int and String.** Rejected: M2-09 §1.5 already fixes Float `sort`.
- **Never inline a row.** Rejected in §3.
- **The options the recorded page weighed** (insertion order, any key type, a functions-only
  Map, `m[key]` as Option, a two-name `for`, an `Entry` record, `sorted` and `reversed`, a
  three-way or key-only sort function, a wide table, Unicode rules): the picks stand as recorded.

## 10. Accepted risks

- The names are locked and common (`find`, `get`, `insert`, `words`, `remove`, `keys`, `values`);
  a user function of that name costs one rename.
- `counts[w] += 1` on a new key traps at run time; the help line names the idiom, and a row that
  adds with a starting value stays a free later addition.
- Only `sort_by` takes a function; a habitual `map` or `filter` is an `unknown-name` with a fix,
  and `for c in text` is refused. Practice runs count both.
- The fixed merge sort bars a faster sort; a Map lookup is a search, not a hash; non-ASCII case
  and white space follow the ASCII rule; the value text form prints a huge Float with every digit.
- The table takes about 2,000 reference tokens; if M2-18 overflows, six rows go in a known order
  and this page is amended with them.
