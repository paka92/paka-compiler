# M5-02 · Key rules: who needs one, scope, tree-wide ids, duplicates

Status: approved by the owner on 2026-10-13.

Base: the recorded M5-02 page in DECISIONS.md. All eight points **stand** as recommended there.

## 1. Points

**1.1 Outside a loop: elements that hold state.** An element the table marks as holding state (the
text input now) must be given `key:`, the last labelled argument. Any other element may carry one.

**1.2 In a loop: every child keyed.** Every element or view call a `for` body adds carries a key,
including ones inside an `if` or `match` in that body. A hole is exempt.

```
for t in s.items {
  todo_row(t, key: t.id)
}
```

**1.3 Scope: siblings; the id is the path.** A key must differ only from its siblings' keys. An
element's tree-wide id is the list of steps from the root; a step is the key or, without one, the
place number.

```
Col                      id: (root)
  Input key="new"        id: "new"
  Button "Add"           id: #1
  Row key=7              id: 7
    Button "done"        id: 7 / #0
    Text "buy milk"      id: 7 / #1
```

**1.4 Unkeyed children: place in the source.** The step is the number of the line that wrote the
child, counted from 0 among the element lines of that child block, through `if`, `match` and `for`
bodies. It does not change while the code is the same.

**1.5 A key on a view call names the view's root.** Every view call accepts `key:` without
declaring it. Inside a view the root carries no key, and the root may not be an element that needs
one.

**1.6 Key values: Int or String.** `3` and `"3"` are different keys.

**1.7 Duplicates: one error node in place.** Siblings sharing a key are replaced by one error node
at the place of the first, naming the key and the count. Other siblings draw as usual. It is not a
trap; the element state under that key is dropped.

**1.8 Element state: gone from the tree, gone.** State is kept only for an element matched by step
and kind under a matched parent. Anything not matched loses its state with everything inside it.

## 2. Rules that follow

- `key:` is written last, on any element or view call, with any Int or String expression.
- The same literal key twice directly in one block is a check-time error. Lines in different
  branches of an `if` or `match` may share one. Other duplicates are found when the tree is built.
- A hole in a loop needs no key; the element that replaces it must carry one and starts fresh.
- The root has the empty path as its id and carries no key.
- Focus is one id held by the runtime. It stays while that element is matched and is dropped
  otherwise.
- After a code swap the same matching applies. An added line renumbers the unkeyed lines after it,
  so cursor or focus there can be lost; the text is not, since the app holds it.
- A reset drops all element state and focus; a migrate keeps them under the matching rule.
- A handler trap rolls back app state only; the view is not rerun and the tree stays.
- Two root screens with the same kind and an element of the same kind and key at the same path
  share its cursor. Use different keys when that is not wanted.
- Children of nested loops share one sibling list; a keyed container per outer round gives the
  inner loop its own scope.
- The text form of ids is M5-06's.
