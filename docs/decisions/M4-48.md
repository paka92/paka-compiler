# M4-48 · A definition's full name and the file it is stored in

Status: approved by the owner on 2026-10-15.

Base: the recorded M4-48 page in DECISIONS.md. Both points **stand** as recommended there.

## 1. Points

**1.1 Full name: the bare name.** The full name is the name as written, such as `count_words` or
`Tally`. All definitions of a program share one pool and a duplicate is an error (M2-02), so it is
unique. The stable id is this name; the kind is not part of it, and a rename makes a new id.

**1.2 File: one per definition.** In a directory program a new definition goes into its own file,
named after it:

```
wc/
  Tally.paka
  Msg.paka
  update.paka
  count_words.paka
  wc.paka
```

## 2. Rules that follow

- Packages stay undecided through M7. One program is one pool of bare names.
- A single-file program stays one file; a new definition is appended after one blank line.
- Files holding several definitions are allowed and left alone; an edit rewrites a definition where
  it is. No tool moves, splits or sorts.
- A definition added to an existing file goes at its end. If `foo.paka` already exists, a new `foo`
  is appended to it.
- The file name is the name plus `.paka`, directly in the program's directory. An add whose file name
  passes 255 bytes is refused.
- Delete removes the definition's text and its comments; a file left with no definition is deleted.
- There is no rename: it is an add under the new name and a delete of the old one, and the old name's
  users are reported as broken until edited.
- Variants, fields and labels are not definitions. A variant is found by its bare name and answered
  with its enum; fields show as part of their type.
- Built-in names share the pool, have no file, cannot be edited, and are found with kind `builtin`.
- Examples and apps are named and stored like any definition.
- A definition that changes kind under the same name keeps its id; its interface hash changes, so its
  users are rechecked.
