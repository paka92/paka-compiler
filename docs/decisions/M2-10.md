# M2-10 · Shared immutable data and pools with handles: decision

Base: the paper (GENESIS.md line 269) says shared data is immutable, cannot form cycles and is
reference-counted; that graph-shaped data is kept in a pool whose nodes refer to each other by handle;
and that a stale handle traps (also line 63). M2-01 put graphs in by list position and left pools out
(§3, §4). M2-05 §1.9 settled how trees are built and changed; M2-06 reserved `stale_handle` with
nothing able to raise it. This page rules on what is left: whether milestone 2 needs a shared immutable
type or a pool at all. It does not; every M2-01 task class is written under the rules already recorded,
nothing is added, and both picks on the M2-10 page of DECISIONS.md stand.

## 1. Resolutions, point by point

### 1.1 No shared immutable type in milestone 2

A value has one owner (M2-05 §1.1). A tree is an enum or record that holds itself behind a hidden
pointer (M2-05 §1.9). Using a subtree twice copies it in meaning; no type lets two owners read one
value. The tree sample, written under M2-02, M2-05 and M2-09:

```paka
enum Expr { Num(value: Int), Add(left: Expr, right: Expr) }
fn count_nums(e: Expr) -> Int {
  match e { Num(v) => 1, Add(l, r) => count_nums(l) + count_nums(r) }
}
fn double_nums(e: Expr) -> Expr {
  match e { Num(v) => Num(v * 2), Add(l, r) => Add(double_nums(l), double_nums(r)) }
}
fn double(e: Expr) -> Expr { Add(e, e) }
example tree_sample {
  let t = Add(Num(1), Add(Num(2), Num(3)))
  var u = t
  u = Add(Num(0), u)
  count_nums(t) == 3 && count_nums(u) == 4 && double_nums(t) == Add(Num(2), Add(Num(4), Num(6)))
}
example two_copies { double(Num(2)) == Add(Num(2), Num(2)) }
```

Every line is accepted. `e` is a read-only parameter, passed without copying (M2-05 §1.1). Patterns
are flat and `match` is the last expression, so no `return` (M2-02). `l` and `r` are read-only copies in
meaning (M2-05 §1.8). `var u = t` copies; `u = Add(Num(0), u)` is the accepted way to change an enum
tree: build the changed tree, assign the subject (M2-05 §1.9), and `t` keeps three leaves. `==` is
structural on every type (M2-09 §1.4). `Add(e, e)` holds two independent copies (M2-05 §1.1).
Refused: `u.left = Num(0)` is `bad-assignment-target`, because a variant field is not a place (M2-05
§1.6); a record tree may instead change in place through `&n.kids[i]` (M2-05 §1.9).

Why not a shared type now. No M2-01 task class needs a subtree with two parents (M2-01 §1, class 2);
the paper puts shared data in for cost, not meaning (lines 269, 360), and cost is measured in M6.

### 1.2 Graphs by list position; pools and handles not decided

A graph is a record over lists; a node is its position. Names map to positions through a
`Map<String, Int>` when a task needs them (M2-14). The graph sample:

```paka
type Graph { adj: List<List<Int>> = [] }
fn add_node(g: inout Graph) -> Int { append(&g.adj, []); len(g.adj) - 1 }
fn link(g: inout Graph, a: Int, b: Int) { append(&g.adj[a], b) }
fn unlink(g: inout Graph, a: Int, b: Int) {
  var i = 0
  while i < len(g.adj[a]) {
    if g.adj[a][i] == b { _ = remove_at(&g.adj[a], i) } else { i = i + 1 }
  }
}
fn reach(g: Graph, seen: inout List<Bool>, u: Int) {
  seen[u] = true
  for v in g.adj[u] { if !seen[v] { reach(g, &seen, v) } }
}
example graph_sample {
  var g = Graph {}
  let a = add_node(&g)
  let b = add_node(&g)
  link(&g, a, b)
  var seen: List<Bool> = list_of(false, count: 2)
  reach(g, &seen, a)
  unlink(&g, a, b)
  seen[b] && len(g.adj[a]) == 0
}
```

`reach` is the walk M2-05 §1.7 accepts: `g` read-only, `seen` through `&`, no write to `g` while
`g.adj[u]` is walked. `unlink` changes the graph during a walk, so it uses `while`, which freezes
nothing (M2-05 §1.7); `for v in g.adj[a] { _ = remove_at(&g.adj[a], i) }` would be
`changed-while-walked`, and the other accepted spelling is `let next = g.adj[a]` before the `for`.
`link(&g, g.adj[a][0], b)` is accepted: an `Int` argument is exempt from the overlap test (M2-05 §1.2).
`f(&g.adj[a], g.adj[b])` is `inout-overlap`, because two index steps on one list never part ways
(M2-05 §1.3, Rule A); bind `g.adj[b]` to a name first.

Removing a node is the program's business: mark it dead or rebuild the lists. A position out of range
traps `out_of_bounds`; a position in range that names the wrong node reads the wrong node, and nothing
catches that (M2-01 §7). That is the accepted risk. Cycles exist only as positions (M2-05 §1.9).

Why not pools now. Where the paper puts a pool (line 269), every M2-01 class 5 task already writes a
record over lists. A stale-handle rule needs a handle type, and that needs a pool no task has asked for.

### 1.3 Accepted cost, and what a back end may do

Cost in meaning: a subtree bound from a place, stored, or used twice is copied in full; a change to an
enum tree builds a new tree along the changed path and copies the unchanged siblings; a value held in
two places is two values, never one shared. Without changing meaning a back end may: skip any copy no write can observe (M2-05 §1.1, §3), with
M4-33 taking the copy at last use; pass a read-only tree by pointer; keep self-holding fields behind a
hidden pointer (M2-05 §1.9); reuse unchanged siblings by pointer when a tree is rebuilt, as long as the
result reads as a copy. The interpreter may copy on every bind. M6 measures the cost of copying owned
trees and of bounds checks on list-position graphs; the reference-count and handle-check rows of its
cost table (line 360) read 'not built'. Why not fix a number now: the paper lists this cost as a thing
to measure (line 360), not to set.

### 1.4 What stays not decided, and what reopens it

Not decided: a shared immutable type; pools; handles; the stale-handle rule; pool iteration order.
`stale_handle` stays reserved, nothing raises it (M2-06); `Shared`, `Pool` and `Handle` are not
reserved names. A graph's order is its lists' order; a Map's order is M2-14's.

Evidence that reopens it: a program after 'go' that removes graph nodes and gets a wrong answer from a
reused position, where a stale-handle trap would have caught it (M2-01 §7); an M6 measurement showing
copies of large unchanged values cost more than the pointer-heavy gap the paper allows (line 99), or a
program that holds one large value in many places; an M6 benchmark that cannot be written without a
pool (line 360). Owning task: none exists in TASKS.md. After 'go', one decision task for shared data
and pools is to be added, or M6 is confirmed to report copy cost in its place; the M2-10 page of
DECISIONS.md records that as the open item. Why not decide it now: a rule on stale handles without a
handle type is a rule on nothing.

## 3. Implementation rule: interpreter and native code

Both: a tree is a value; passing it read-only passes no copy; binding, storing or returning it from a
place copies it. The interpreter may copy on every bind; native code applies §1.3. Neither builds a
reference count, a pool or a handle check.

## 4. M1 cases that stop holding

None; M1 has no shared type, pool or handle.

## 5. New diagnostic codes

None. §1 uses `bad-assignment-target`, `changed-while-walked` and `inout-overlap` from M2-05 §5.
