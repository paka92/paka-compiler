# M2-01 · Task classes the headless language must cover

Judge's decision over three proposals: smallest scope (six classes, Int only, no file writes),
representative coverage (eight classes, an error path in every task) and backwards from the
experiment (seven classes, each tied to the Paka rule it stresses). The third is the base: its
seven classes are the ones already recorded in DECISIONS.md and that eight later decisions
(M2-03 to M2-15, M3-01 to M3-04) and the approved 30-task outline are built on. The other two
contribute the error-path rule, the "everyday glue program" coverage and most of the risk list.

## 1. The seven classes

Every class must admit tasks in the "many exact rules" style (M3-04.3) with hidden cases on the
edges, so that Rust and TypeScript fail some runs. Every class stresses at least one of the
parts of Paka a model must get right while writing: effects as data (E), ownership and in-place
change (O), failure as values and a chosen exit status (F), numbers with one meaning (N), the
closed vocabulary (V). Spelling habits are hit by every class and need nothing built.

### 1. Text processing (V)

- Types: String, List<String>, List<record> for rows, Map<String, Int>.
- Effects: ReadFile, Print, Exit, ExitWith. Grants: ReadFiles, Console.
- Data: flat lists; a record per row; a list sorted by a named order function. Also covers
  record-shaped work (delimited rows to an aligned table with totals), so "records and data
  transformation" needs no class of its own.
- Example: "Wrap each paragraph to width W, spreading extra spaces left first; a word longer
  than W is cut at W. Print the result. On W < 1 print `bad width` and exit with the error status."

### 2. Parsing and small interpreters (O, F, N)

- Types: an enum that contains itself (expression tree), records, Result<T, String>,
  Option<Int>, Map<String, Int> as an environment.
- Effects: ReadFile, Print, ExitWith.
- Data: owned trees, copied in meaning, stored indirectly; no subtree with two parents.
- Example: "Integer expressions with + - * / and parentheses, one assignment or expression per
  line, variables persist, division truncates toward zero, division by zero is an error. Print
  each result. On the first error print `line L col C: <reason>` and exit with the error status."

### 3. State machines and simulations (O, F)

- Types: records in a Map<String, record>, enums with payloads, exhaustive match.
- Effects: ReadFile, Print, ExitWith.
- Data: flat records changed in place through `&m[key]`; two entries changed in one step.
- Example: "Accounts in whole cents. Commands open, deposit, hold, capture, release, transfer.
  A rejected command prints its rule name; a transfer changes two accounts or neither. Print the
  final balances in name order."

### 4. Grids and dynamic programming (O, N)

- Types: List<List<Int>>, List<List<String>>; Int only; ranges.
- Effects: ReadFile, Print, ExitWith.
- Data: nested lists built with list_of and written through `g[r][c] = v`; swap; a table read
  back along a path.
- Example: "Diff two files by longest common subsequence; on ties prefer deletion before
  insertion; print hunks in the given format."

### 5. Graph algorithms by list index (O, V, F) — graphs are in

- Types: Map<String, Int> from name to position, List<List<Int>> adjacency, List<Bool>
  visited, a record per node at most.
- Effects: ReadFile, Print, ExitWith.
- Data: nodes in a List pointing at each other by Int position; at least one task changes the
  graph during the algorithm (remove a link, recount, restore). No pool, no handle.
- Example: "One `a needs b` per line. Print a build order; when several may come next print the
  first in ASCII order. On a cycle print `cycle: a -> b -> a` from its smallest name and exit
  with the error status."

### 6. Integer and float reports (N, F)

- Types: Int, Float, fixed(x, digits:), to_float, to_int, floor, round; Option from parse_int
  and parse_float; records per row.
- Effects: ReadFile, Print, ExitWith.
- Data: flat lists of records; running totals; money in cents.
- Example: "Lines of `group value`. Per group print mean, median and standard deviation to two
  decimals; an empty group prints `n/a`; a single value has deviation 0.00."

### 7. File tools (E, F)

- Types: a state record holding the names still awaited, enum Msg with Loaded, Failed and
  Saved variants, Map<String, String> from name to content.
- Effects: ReadFile with then: and or:, WriteFile with then: and or:, Print, ExitWith.
  Grants: ReadFiles, WriteFiles, Console.
- Data: a queue of pending names; the number of reads and writes and the file names are known
  only at run time; written files are compared by the harness.
- Example: "Resolve `include <name>` lines recursively, each file once, and write the merged
  text to the named output file. On a cycle print the chain and exit with the error status; on
  a missing file print `missing: <name>` and exit with the error status."

## 2. Rules that cut across the classes

- Error path: every counted task defines at least one error condition (malformed input, bad
  argument, rule violation) with an exact message on standard output and the one fixed error
  status; hidden cases hit it. This is the recorded "error cases" of M3-04.3 made explicit, not
  a new class. Not every task makes errors its main output.
- Missing files: tested in the file-tools class only (and the file practice task). Other
  classes read one file that always exists, so M2-15's or: path is measured where it matters
  and does not tax every program.
- One program shape: one file; input as files named in the arguments; output on standard
  output, an exit status and, in file tools, written files. No standard input.
- Inputs: ASCII, under 200 lines, values within plus or minus 2^53 - 1, no float result on a
  rounding tie, recursion under 200 deep. Statements name arguments, files, output and status
  only, never a language feature or a grant.

## 3. Graphs: in, by list index; pools not built

Dropping graphs would remove the class where ownership meets shared structure, the first thing
a sceptic asks about. Index lists cost nothing new: they are what the same model writes in Rust
and TypeScript for small graphs, so no language gets a free structure. Pools are not built: no
class removes a node, so the stale-handle trap would never fire and the reference would spend
tokens on spelling no run exercises. The TASKS.md note "if M2-01 rules graphs out, the pool
part is dropped" fires in this narrower sense: graphs in, pools not built, pools recorded as
not decided (as M2-10 already does).

## 4. Explicitly out

Records and data transformation as a separate class (covered by classes 1 and 6); standard
input; text patterns (regular expressions); Unicode beyond ASCII; wrapping and bit operations
and hash or checksum tasks; big integers; sin, exp, pow and any maths library (a task needing a
power takes it as input); closures and user-written generics or interfaces; pools, handles and
a shared type; clock, randomness, network, environment, directory listing, foreign code;
concurrency; GUI; speed or large-input tasks; line-by-line sessions.

## 5. Why not the other two proposals as base

- Smallest scope (Float out, file tools out, no missing-file tests): cheapest M2, but it removes
  the two classes where Paka is most exposed (explicit Int-to-Float steps, hand-chained
  effects), so a pass would flatter the language; it also contradicts M2-03, M2-14, M2-15 and
  M3-04 as recorded and would reopen all four. Its risk list is kept.
- Representative coverage (eighth class, error path in every task): the eighth class would
  change the even spread M3-04.5 already fixed and the 30-task outline, for tasks that classes
  1 and 6 already hold. Its error-path rule is kept in the form above; its "at least one task
  per class makes error reporting the main output" is not, because the approved grid and report
  outlines do not meet it and no stress is lost without it.

## 6. What this locks

- M2-03: one 64-bit Int that traps on overflow, truncating division, Float with + - * /,
  comparison, sqrt, floor/ceil/round/trunc, to_float/to_int and one fixed-digit text form with
  one tie rule; parse to a number gives Option; no sin, exp, pow; wrapping and bit spellings
  exist but no task uses them. Already recorded.
- M2-05: recursive types stored indirectly and owned whole; in-place change through nested
  index and field paths; the overlap rule checks `append(&g.next[a], b)` at the call; copies in
  meaning. Already recorded.
- M2-09: named functions and variant names as values; no closures; no user generics; structural
  equality; ordering on Int, Float and String only. Already recorded.
- M2-10: tree sample only; no shared type; a graph is List<List<Int>>; pools not decided.
  Already recorded.
- M2-12: Option and Result with the short pass-up form; bugs trap, outside data returns; a
  defined error must reach update so the program prints its text and chooses its status.
  Already recorded.
- M2-14: at least split, lines, words, join, trim, pad, chars, code_at, parse_int,
  parse_float, fixed, sort, sort_by with a named order, Map with Int and String keys and
  get/has/keys/remove and `&m[key]`, list_of, pop, remove_at, swap, unwrap_or, ok_or; no
  regex, Set, priority queue or closure-taking helpers. Already recorded.
- M2-15: ReadFile and WriteFile with then: and or:; a program-chosen exit status outside 0 to 3;
  reads and writes whose count and names are known only at run time; arguments as String
  fields of the start message; no standard input. Already recorded.
- M2-06: the call-depth limit sits well above the 200 the tasks need. Already recorded.
- M3-04: 22 counted tasks spread evenly over these seven classes; every task names one; every
  task defines at least one error condition; the eight Paka-cost tags fall in the classes
  stressing O, N, E and F. The approved outline stands unchanged.
- M3-11: full statements add the error condition where an outline lacks one, without changing
  the task's class or what it stresses.
- M3-22: the three metrics are also summed per class, so a loss can be located before stop is
  recorded.

## 7. Fairness risks the M3 report must state

- Fixed boilerplate: every Paka program carries app, Msg, update, or: and Exit, roughly 100 to
  150 output tokens Rust's main and TypeScript's top level do not; a forgotten or: or Exit costs
  a first try. The logged diagnostic codes show how many Paka edits were slips only.
- TypeScript has regular expressions; Paka and Rust's standard library do not. Class 1 tilts
  TypeScript up; Rust decides the stop rule, and the TypeScript gap is printed anyway.
- Values capped at 2^53 - 1 for TypeScript's sake mean checked overflow never fires in any
  language; class 6 measures writing, not safety. A kindness to the control languages, stated
  in advance.
- Index graphs give a silent wrong answer on an in-range wrong index in all three languages:
  equal footing, but no evidence on the paper's stale-handle rule.
- Per-class imbalance: O is stressed by four classes, E by one. The per-class sums in the
  report let a reader reweight.
- What the verdict is silent on: pools and handles, the float tie rule, Unicode text, user
  generics, closures, standard input, GUI, build and run speed, per-definition tools. A go is
  a go for this subset and the analysis lists these as unmeasured.
- Vocabulary gaps: a frequent hand-written helper in Paka solutions is a token cost outside the
  bet; the dry run counts such helpers and treats a frequent one as a reference gap.
- Recall: classic graph and table problems sit in every model's training in Rust and
  TypeScript; the "many exact rules" style and fresh statements are what keep them from being
  solved by recall, and a class whose tasks cannot be made rule-heavy is weighted down in M3-04.
- Reference budget: classes 6 and 7 cost the most reference tokens. If the reference overflows,
  rows are trimmed in M2-14's fallback order, never classes.
- Interpreter time: grid and graph tasks can be cubic on small inputs; the under-one-second
  check on reference solutions, not the 10-second case limit, bounds them.
