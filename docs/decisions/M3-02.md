# M3-02 · Formulas, margin, model, repetitions and usage cap: proposal

Status: proposal, awaiting the owner's approval.

Base: the recorded M3-02 page in DECISIONS.md. Points 1.1 to 1.3, 1.5 and 1.6 **stand**. Points 1.4
(repetitions), 1.7 (dropped-task limit) and 1.8 (usage cap) are **amended**, because the cap must fit a
usage limit that other work shares. Point 1.9 is **new**: it writes out the three formulas the
done-when asks for. The task count behind these numbers is M3-04 §1.1: 14 counted tasks.

## 1. Points

### 1.1 Which model writes the programs? (stands)

**Sonnet 5.5 at effort medium** (recommended).

```
model:    claude-sonnet-5-5   (checked in every reply)
effort:   medium, sent on every call
thinking: provider default, counted as output
sampling: provider default
```

- Why: the lightest model that is not the known worst case in the cited study. A stop then cannot be
  blamed on model size, and Rust and TypeScript still have room to fail.
- The model under test need not be the model that builds the toolchain. TASKS.md's levels pick the
  engineering model; they decide nothing here.
- Not chosen: Haiku 5.5 (about a twentieth of the usage, but the cited small model is the one that
  lost on a less-seen language; a stop would answer the wrong question) · Sonnet 5.5 at effort low
  (fewer thinking tokens, but less like real use, and more failures in all three languages) · Opus
  5.5 (twice the usage, and Rust and TypeScript would pass more first tries, so harder tasks would be
  needed).
- Look again when: calibration shows Rust above 85% first try after every swap. Then write harder
  tasks; do not change the model.

### 1.2 Which language does Paka have to match? (stands)

**Rust decides, TypeScript is reported** (recommended). The stop rule compares Paka with Rust only.
TypeScript is run and published the same way.

- Why: Rust is the language Paka would replace: compiled, owned values, native speed.
- Not chosen: the better of the two (Paka could stop for not matching a language that does none of
  what it is for) · the mean of the two (one number that stands for no real language).
- Against: a Paka that matches Rust but trails TypeScript by 25 points gets 'go'. The report shows
  that gap plainly.

### 1.3 How does a run that never passes count? (stands)

**Cap plus one, real tokens** (recommended). It counts as a failed first try, 8 edits, and the
output tokens it really spent.

- Not chosen: leave it out of edits and tokens (hard tasks drop out for the weaker language) · medians
  (the median edit count is likely 0 or 1 everywhere and separates nothing).

### 1.4 How many times is each task run in each language? (amends)

**Four** (recommended). 14 counted tasks x 3 languages x 4 = 168 counted runs, 56 per language.

```
chance movement of the first-try gap = square root of (0.5 / runs per language)
42 runs -> 10.9 points | 56 runs -> 9.4 | 70 runs -> 8.5 | 110 runs -> 6.7
```

At 56 runs per language, a true first-try gap of:

- 0 points is read as lost about 2 times in 100;
- 10 points is read as lost about 1 time in 7, and as held about 1 time in 2;
- 30 points is missed (read as held or close) about 1 time in 7.

Runs of one task tend to fail together, so the true movement is somewhat larger.

- Why: a clear signal at a modest size. A real gap of 30 points or more is caught 6 times in 7, and a
  Paka that matches Rust is almost never stopped. The middle ground is read as close, which goes to the
  owner.
- Fixed fallback: if the dry run projects the rest above the cap, drop to three per task before
  calibration. If that is still above the cap, the owner decides.
- Not chosen: three (126 counted runs; about 2.4 million tokens less, but a true 10-point gap is read
  as lost about 1 time in 5) · five (210 counted runs; about 2.4 million tokens more for 1 point less
  movement; one more task would buy more than one more repetition).

### 1.5 How far behind Rust has Paka lost a metric? (stands)

**Just beyond published gaps** (recommended). Lost if the first-try rate is more than 20 points below
Rust, or mean edits more than 1.0 above, or output tokens more than 2.0 times Rust's.

- Why: just past the worst main-setup figures in the cited study (19 points, 1.69 times).
- Not chosen: tight (10 points, 0.5, 1.5 times; at 56 runs per language this stops on noise) · loose
  (30 points, 2.0, 3.0 times; almost nothing stops the project).

### 1.6 How is chance kept from deciding? (stands; the noise text is amended)

**Fixed band, no statistics** (recommended).

```
first-try gap:  held <= 10 points < close <= 20 points < lost
edits gap:      held <= 0.5     < close <= 1.0      < lost
token ratio:    held <= 1.7     < close <= 2.0      < lost
```

- Amended text: at 56 runs per language the band is about one chance movement wide, not one and a
  half. A true gap at the held line is read as lost about 1 time in 7. That is the price of the smaller
  design, and the report says so.
- Not chosen: a bootstrap interval over tasks (sounder, but a random procedure M3-10 cannot match by
  hand) · a single line per metric (a 19-point and a 21-point gap get opposite verdicts on noise).

### 1.7 What gives stop, go or inconclusive? (amends the dropped-task limit)

**Any one metric lost gives stop** (recommended).

```
inconclusive  if more than 2 of the 14 tasks were dropped (M3-03)
stop          else if any metric is lost
go            else if all three are held
inconclusive  otherwise
```

- Amended: the limit falls from 3 of 22 to 2 of 14, the same share of about one in seven.
- Not chosen: two of three lost (Paka could lose a quarter of its first tries and pass) · first-try
  rate alone (ignores the finding that a less-seen language shows its cost in tokens).

### 1.8 What is the usage cap for all model calls in M3? (amends)

**16 million input and 9.5 million output tokens** (recommended), for dry run, calibration and
counted runs together. The harness stops when either counter reaches its cap. Going on needs the
owner's yes.

Estimate per call:

```
fixed text   1,500  (CLI text about 800 + run rules about 700)
reference    8,000  (Paka only)
statement    1,500  (with 2 visible cases)
reply        7,000  output (program about 3,000 + thinking about 4,000)
feedback       800
each later call resends the last program and its feedback: +3,800 per earlier call
```

Assumed: earlier thinking is not resent. If the dry run shows it is, input grows faster; the
recheck after the dry run catches that.

A run of n calls:

```
input(n)  = n x base + 3,800 x n(n-1)/2     base 3,000 (Rust, TS) or 11,000 (Paka)
output(n) = 7,000 x n

             Rust or TypeScript            Paka
n = 1        3.0k +  7k =  10.0k           11.0k +  7k =  18.0k
n = 3       20.4k + 21k =  41.4k           44.4k + 21k =  65.4k
n = 6       75.0k + 42k = 117.0k          123.0k + 42k = 165.0k
n = 8      130.4k + 56k = 186.4k          194.4k + 56k = 250.4k
```

Planning mix of runs: 45% pass at the first call, 35% at about 3 calls, 10% at about 6, 10% use all 8.
Mean calls 2.9. Mean per run:

```
Rust or TypeScript:  29.0k input + 20.3k output = 49.3k
Paka:                52.2k input + 20.3k output = 72.5k
```

Runs and expected tokens:

```
phase         runs                          Rust/TS  Paka  input   output  total
dry run       2 x 3 langs x 2, 3 passes       24      12    1.32M   0.73M   2.05M
calibration   14 x 2 langs x 3                84             2.44M   1.71M   4.15M
swap checks   up to 4 tasks x 6               24             0.70M   0.49M   1.18M
counted       14 x 3 langs x 4               112      56    6.18M   3.41M   9.59M
total         312 runs                       244      68   10.63M   6.33M  16.97M
```

Cap = about 1.5 x expected, rounded: 16M input, 9.5M output. If every run used all eight calls, the
same 312 runs would take about 45M input and 17.5M output, so the cap also stops a harness fault
that loops.

- Why: room for runs to be half again as costly as planned, with a hard ceiling well under the
  worst case.
- Pacing: counted runs go in batches of one task (12 runs, about 0.7 million tokens expected). The
  harness checks the usage limit between batches and pauses under rule 11 when it is near; the
  runs go on when it resets.
- Recheck after the dry run: if measured tokens per run differ from the estimate by more than a
  third, the cap and the projection are recomputed before calibration, and §1.4's fallback applies.
- Not chosen: the recorded 552 runs (22 counted tasks, 5 repetitions; about 30 million tokens under
  these estimates, so the recorded 20M/11M cap is about the expected use, not twice it) · a pilot
  (7 counted tasks x 3 repetitions, 153 runs, about 8.3 million tokens; its only firm answer is
  stop on a gross loss, and anything else is inconclusive and goes to the owner).
- Owner must still: a restart of counted runs is outside this cap and needs the owner's yes.

### 1.9 What are the exact formulas? (new; written out from the recorded page)

**Pooled over runs** (recommended). Per language, over all counted runs that are not dropped:

```
F = runs whose submission 1 passed / runs
E = mean over runs of edits(run)
      edits(run) = submissions - 1   if the run passed
                 = 8                 if it never passed
T = sum over runs of output tokens (thinking included)

first-try gap = F_rust - F_paka         (in points)
edits gap     = E_paka - E_rust
token ratio   = T_paka / T_rust
```

- Why: three numbers a person can redo by hand from the raw logs.
- Not chosen: the mean of per-task ratios (a single task where Rust is cheap can swing the token ratio
  a long way) · medians (separate nothing on edits, see §1.3).
- Also printed, labelled as not the verdict: solve rate within eight submissions; input tokens with
  and without the reference; the same metrics for TypeScript; the metrics with nothing dropped; one
  table with tagged runs removed (M3-03); cut-off and refused replies per language; each metric per
  task.

## 2. Settled without asking

- Calibration: three runs per counted task in Rust and in TypeScript, 84 runs, plus up to 24 for
  swapped-in reserve tasks.
- Dry run (amended): 2 practice tasks x 3 languages x 2 runs = 12 runs per pass, at most three
  passes (36 runs). A fourth pass needs the owner's yes.
- Rulings: void runs are rerun inside the cap. Dropped tasks leave all three languages before any
  formula is applied.
- Go means only that the rule did not stop the project. The owner records go or stop in M3-23.
