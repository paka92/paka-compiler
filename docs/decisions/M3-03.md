# M3-03 · Defects, swaps and late changes

Status: approved by the owner on 2026-10-14.

Base: the recorded M3-03 page in DECISIONS.md. All six recorded picks **stand**. Two limits are
**amended** to fit 14 counted tasks and 4 reserve tasks (M3-04 §1.1). The toolchain defect, settled
without asking on the recorded page, is written out as point 1.7 with its alternatives, because the
done-when names it. Section 2 says who rules on each kind of case.

## 1. Points

### 1.1 After the `run` tag, may anything be fixed and run again? (stands)

**Only harness faults rerun** (recommended). Nothing changes after the tag. A run broken by the harness
(provider error after retries, refused or empty reply, usage limit reached mid-run, sandbox failure,
crash, full disk, a failed first-call token guard or a compaction event, M3-01 §1.7) is void. It is
run again from the same commit, at most twice; a third fault on the same run pauses the experiment.

```
rulings file, one line per ruling:
run 0142  void     harness: provider error after 3 retries; rerun as 0331
task G2   dropped  tools and reference disagree, regression case cases/g2_slice
run 0207  tagged   reference gap: section 4.2 silent on empty list
```

- Why: a harness fault says nothing about any language.
- Not chosen: fix and rerun affected runs (decided by people who have seen the first results) · no
  reruns at all (a network fault would score as a language failure).

### 1.2 The Paka tools and the reference disagree in a counted run. What happens? (stands, limit amended)

**Drop the task in all three languages** (recommended). It applies when a small program shows the
tools doing something other than what a sentence of the reference says, and the mismatch changed the
outcome of any run of the task.

- Amended: more than 2 dropped tasks of 14 makes the verdict inconclusive (M3-02 §1.7).
- Why: like for like, and no new runs. The limit and a table with nothing dropped stop the rule from
  quietly removing Paka's bad tasks.
- Not chosen: count it as it fell (one interpreter bug could decide the project) · fix and rerun Paka
  (Paka alone gets a second attempt).

### 1.3 The reference was silent or unclear, and the tools do what it says. Does the run count? (stands)

**It counts as it fell** (recommended). M3-21 tags the run. The report adds one table with tagged runs
removed, marked as not the verdict.

- Why: the reference is part of what is tested.
- Not chosen: remove the run (a judgement made after the results, by a party that wants Paka to pass)
  · fix the reference and rerun (the reference would be tuned on the counted tasks).

### 1.4 When is a counted task too easy or too hard? (stands, limit amended)

**Swap at 6 of 6** (recommended). A task is swapped when all six calibration runs (3 Rust,
3 TypeScript) pass first try, or when none of the six passes at all. The replacement is the unused
reserve task of the same class, else the next in reserve order, calibrated the same way. The list may
be tagged `run` only if Rust's first-try rate on it is between 30% and 85% and TypeScript's is at most
85%.

```
task T2: rust 3/3 first try, ts 3/3 first try -> swap
task G1: rust 2/3 first try, ts 3/3 first try -> keep
task R3: rust 0/3 solved,    ts 0/3 solved    -> swap
kept list: rust first try 58% (30..85), ts 71% (<= 85) -> may tag `run`
```

- Amended: more than 4 swaps uses up the reserve. The list then cannot be repaired, and the owner
  decides whether to write new tasks under a new `protocol` tag.
- Not chosen: swap at 5 of 6 (one unlucky run counts as proof, and needs a larger reserve) · no swaps,
  window only (several tasks could separate nothing).

### 1.5 A task cannot be written in Paka at all. What happens? (stands)

**Fix bugs, swap gaps** (recommended). Found in M3-16, before the `protocol` tag. A tool bug is fixed
through M3-16's defect task. A task that cannot be written with the approved language and built-ins is
swapped for a reserve task and listed under 'Paka could not express'. Long or clumsy does not qualify.
More than two such swaps goes to the owner.

- Not chosen: keep it and let Paka fail (measures a known missing feature) · add the feature
  (reopens M2 under time pressure).

### 1.6 Between the `protocol` and `run` tags, what may change? (stands)

**Wording yes, rules no** (recommended). The reference may be reworded, corrected or trimmed to fit
8,000 real tokens, using evidence from practice tasks only, and only where the tools already behave
that way. No language rule, checker behaviour, counted task, test, counting rule or stop rule changes,
except harness fixes, calibration swaps and a tool bug fix with a regression case.

- Not chosen: frozen at `protocol` (a misleading sentence found on day one stays in every run) ·
  anything until `run` (language design steered by two practice tasks).

### 1.7 A Rust or TypeScript toolchain defect changes a counted run. What happens? (written out)

**Drop the task in all three languages** (recommended). It applies when a small program shows the
pinned compiler or runtime breaking its own documentation, and the defect changed the outcome of any
run of the task. It counts toward the same limit of 2 dropped tasks.

- Why: the same rule as a Paka mismatch, so no language is treated better.
- Not chosen: count it as it fell (the baseline would be scored on a tool bug, against the Paka rule)
  · pin another version and rerun that language (Rust or TypeScript alone gets a second attempt, after
  the results are known).

## 2. Who rules on each

```
case                         who flags                 who rules               when
harness fault                the harness, from logs    the rule; owner sees    during runs
                                                       the list
tool-reference mismatch      M3-21 ruling, from the    a blind second ruling   after counted runs
reference gap                transcript and the        of a sample; the owner
toolchain defect             reference text            approves
task Paka cannot express     the M3-16 author          the owner decides the   before `protocol`
                                                       swap
saturated task               M3-19b, mechanically      the 6-of-6 rule and     before `run`
                                                       the window
amendment                    the author of the change  the owner merges each   between the tags
```

- Runs sent to M3-21: every never-passing run in any language, every run in which a tool crashed or
  printed an internal error, and every run the harness flagged.
- Mismatch or gap: a mismatch only when a small program behaves differently from a sentence of the
  reference. Everything else is a gap, and the run counts as it fell.
- A wrong test found after the `run` tag: if the statement proves an expected result wrong, the task
  is dropped in all three languages and counts toward the limit of 2.
- Sandbox or counting fault found during counted runs: stop, fix the harness only, tag a new `run`
  commit and run all counted runs again, with the owner's yes, because it takes the usage again.
- Model id withdrawn mid-run: the experiment stops. A new id means a new `run` tag and all counted runs
  again, with the owner's yes.
- No rule fits: the run stands as it fell, and the case is written up for M3-23.
- Publication: all raw logs, void and dropped runs included, every ruling and every difference
  between the two tags.
