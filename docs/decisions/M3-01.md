# M3-01 · What one run is: proposal

Status: proposal, awaiting the owner's approval.

Base: the recorded M3-01 page in DECISIONS.md, written out with the one point it left to M3-08: how
the conversation with `claude -p` is kept and which flags every call carries. Points 1.1 to 1.6
**stand** as recorded. Point 1.7 is **new**. Nothing here changes a counting rule.

Every call goes through the installed `claude -p` with no key. No paid service and no extra usage is
used.

## 1. Points

### 1.1 What can the model do inside one run? (stands)

**No tools, whole file** (recommended). Each reply is one complete program in one code block. The
harness builds it, runs the cases and sends the result back as the next message.

```
system:  rules of the run (+ the Paka reference, Paka runs only)
user:    task statement with 2 visible cases
model:   ```paka ... whole file ... ```
user:    build and case results
model:   ```paka ... whole file again ... ```
```

- Why: the smallest loop that gives all three languages the same work. Edits and tokens are plain to
  count.
- Stated limit, in the protocol in these words: one edit replaces the whole file in all three
  languages; Paka's per-definition Find, View and Edit tools are not measured.
- Not chosen: shell tools in a loop (closer to real work, but an edit is no longer one reply and
  tool chatter counts as tokens) · Paka's own definition tools (not built before M4, and Paka would
  get a different loop from Rust and TypeScript).

### 1.2 How many submissions may one run make? (stands)

**Eight** (recommended). The first try plus at most seven edits. No pass after submission 8 means
never passing.

- Why: room for a few habit slips on top of real bugs, without letting a stuck run burn usage.
- Not chosen: four (cheapest, but two rounds of syntax habits push a run into never passing) ·
  sixteen (few runs cut off, but a failing run costs about three times as much, see M3-02 §1.8).

### 1.3 How much of the test results does the model see after a failure? (stands)

**Visible cases in full, hidden cases counted** (recommended). A failed build returns the
compiler's own text. A working build returns each failing visible case in full (arguments,
expected and actual output, exit status, standard error). For hidden cases it returns only how many
failed and in which way.

```
build: ok
visible case 2: FAIL
  args: in2.txt
  expected stdout: "3 words\n"   status 0
  got stdout:      "2 words\n"   status 0
  stderr: (empty)
hidden cases: 5 of 8 pass (2 wrong output, 1 wrong exit status)
submission 2 of 8
```

- Why: concrete evidence, the same in all three languages, and a pass still means the statement was
  met.
- Not chosen: all cases shown (the model can special-case expected outputs) · pass or fail only
  (runs end by guessing, which measures the statement, not the language).

### 1.4 Do the reference's tokens count toward the token metric? (stands)

**No: output tokens decide** (recommended). The token metric is output tokens only, thinking
included, summed over every call of the run. Only Paka runs carry the reference. Input tokens are
logged and reported per language twice: as sent, and with the reference taken out.

```
tokens(run) = sum over calls of usage.output_tokens
reported beside it: input tokens, and input tokens minus the reference
```

- Why: output is where an unfamiliar language shows its cost, and it is the measure the cited study
  uses. The reference adds a fixed, known amount per call (about 8,000 tokens). Counting it would
  measure the reference's size, not the writing.
- Not chosen: all tokens, reference included (strictest; Paka loses a constant known today) · all
  tokens, reference taken out (needs a subtraction rule, and input then mostly tracks how long each
  compiler's messages are).
- Against: a model writing Paka really pays for the reference on every task. The report prints that figure, so
  the stricter reading is visible.

### 1.5 Does a harmless Paka spelling slip cost an edit? (stands)

**Yes, counted like any error** (recommended). The checker rejects the file and names the fix. The
next reply is one edit. The harness logs the diagnostic codes of every failed check, so the report
can say how many Paka edits were spelling slips only.

- Not chosen: the harness applies the fix for free (Rust and TypeScript get no such help) · the
  checker accepts other spellings (reopens M2-02 on no evidence).

### 1.6 Is a TypeScript type error a failed submission? (stands)

**Yes, the strict check must pass** (recommended). The file must pass `tsc` in strict mode before
it runs, as Rust must compile and Paka must check.

- Not chosen: strip the types and run (the baseline would be JavaScript, not TypeScript).

### 1.7 How is the conversation kept, and which flags does every call carry? (new)

**One open process per run, stream-json in and out** (recommended). The harness starts one
`claude -p` process per run, in a fresh empty directory, and writes each user turn to it as one
JSON line. It reads each reply, with its `usage` block and model name, from the output stream. When
the run ends, the harness closes the process.

```
claude -p --model claude-sonnet-5-5 --effort medium \
  --system-prompt "<run rules, see §2>" \
  --tools "" --setting-sources "" --strict-mcp-config \
  --no-session-persistence --disable-slash-commands \
  --input-format stream-json --output-format stream-json --verbose
```

Never passed: `--bare` (it accepts only an API key), `--fallback-model`, `--max-budget-usd`,
`--resume`, `--continue`.

- Why: earlier turns stay exactly as they were, because the harness never resends them. Nothing is
  written to a session store. The CLI's own caching works across turns, which keeps input cheap.
- Guard: the input tokens of the first call must equal the system text, the statement and (Paka only)
  the reference, plus the fixed CLI text measured in the dry run, within 50 tokens. Anything more means
  outside text rode along, and the run is a harness fault (M3-03). A compaction event in the stream
  also voids the run. The longest conversation is about 45,000 tokens (a Paka run at submission 8),
  far below the point where the CLI compacts.
- Locks: M3-08's call layer and M3-09's trial loop. The harness checks every flag on the fake model
  before the first live call.
- Not chosen: resume a saved session per call (each call starts a new process and reloads the
  session from the CLI's store, which the harness does not control) · a fresh call per turn with
  the transcript pasted as one user message (full control, but the model sees its own earlier code as
  user text, which changes the conversation the paper describes).

## 2. Settled without asking

- System text, the same for all three languages except the parts in brackets:

```
You write one program in [language]. Reply with the whole file [main.ext] in one
code block. Any other text is allowed; only the code block is used.
The harness builds it with: [build line]
It runs the program on cases. Input comes as files named in the arguments.
Output is standard output, the exit status and, where the task says so, written files.
There is no standard input.
After each submission you get the build result or the case results.
You have 8 submissions.
Use [the standard library only | Node's built-in modules only | the built-ins only;
the app may list any grant the reference names].
[Paka only: the language reference follows.]
```

- User message: the task statement with its two visible cases. Later user messages: the feedback of
  §1.3 and nothing else.
- Pass: the build works and every visible and hidden case matches: standard output byte for byte,
  the exit status the statement names, and every file the statement says is written. Standard error
  is not compared.
- First try and edit: first try is submission 1; each later submission is an edit. A reply with no
  code block, more than one, or cut off at the reply limit is a failed submission and counts.
- Token count: from the `usage` block of each reply. Output tokens, thinking included, are counted.
  Input is reported as the sum of plain, cache-write and cache-read input. A call that failed and was
  retried is not counted.
- Budgets per run: eight submissions; 32,000 output tokens per reply, thinking included (a longer
  reply counts as cut off); 120 seconds per build; 10 seconds and 1 GB per case.
- Program shape: one file, `main.paka`, `main.rs` or `main.ts`. Rust uses the standard library only;
  TypeScript uses Node's built-in modules only; Paka uses its built-ins.
- Build lines, versions written into the protocol:
  - Paka: `paka check main.paka`, then `paka run main.paka <args>` in the interpreter.
  - Rust: `rustc --edition 2024 -C debug-assertions=on -C overflow-checks=on -o main main.rs`, then
    `./main <args>`, with the pinned toolchain.
  - TypeScript: `tsc --strict --noEmitOnError --target es2022 --module commonjs --types node --outDir
    out main.ts`, then `node out/main.js <args>`.
- Compiler feedback: each language's own text, unchanged, cut after 8,000 bytes with a note. A
  failing visible case shows standard output and standard error cut after 2,000 bytes each.
- Sandbox: every case runs in a fresh directory, with an empty environment except TZ=UTC and the C
  locale. Hidden cases cannot be read.
- Interpreter speed: every Paka reference solution finishes every case in under 1 second (M3-17), so
  the 10-second limit never decides a Paka run.
- Holes, examples and in-file tests: allowed in all three languages. Only the build line and the
  cases decide.
- Model settings: one model, one effort setting and the provider's default sampling on every call
  (M3-02). The harness checks the model name in every reply; a run answered by any other model is void.
