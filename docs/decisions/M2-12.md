# M2-12 · The one error-handling mechanism: decision

Base: the five recorded picks on the M2-12 page of DECISIONS.md: failure and absence are values
in the result; the two built-in enums `Option<T>` and `Result<T, E>`; bugs trap, outside data
returns; the postfix `?` that passes a failure up; `unreachable()` where a value is expected but
the place cannot be reached. Of the alternatives considered, the smallest one is the base: its
reading of the picks adds no grammar and no diagnostic code, and every rule below is checkable from
signatures alone (M2-09). Grafted onto it: the typing of an `if` or `match` whose value has no
expected type (§1.2), the lowering of `?` as one early return with an exact release rule (§3), and
fixed message texts for the places a program written by habit goes wrong (§5). All five picks
stand. Where this page differs from or adds to the recorded page it says so and §7 lists the lines.

The one rule, stated once: a function that can fail or have no answer says so in its result type,
the caller takes the value apart with `match` or passes it up with `?`, and nothing else in the
language jumps. A trap is for a claim the program itself made and broke (M2-06); a returned
failure is for a question whose answer depended on outside data.

## 1. Resolutions, point by point

### 1.1 The two types

`Option<T>` has the variants `Some(value: T)` and `None`. `Result<T, E>` has `Ok(value: T)` and
`Err(error: E)`. Both are built-in enums under M2-02's rules: the variant names are bare, in the
one pool of names, and no user type or variant may reuse `Option`, `Some`, `None`, `Result`, `Ok`
or `Err` (`duplicate-name`, M2-02 §1.3). `T` and `E` are any type, a function type included; no
default fills `E`, so a `Result` always names what its failure carries. There is no unit type:
a step that can fail and has nothing to give back is a trap or an `or:` message (M2-15).

Equality is M2-09 §1.4's: same variant, then fields equal. Interpolating one is `type-mismatch`
"match it first" (M2-09 §1.6); the tools print `Some(3)`, `None`, `Ok(4)`, `Err("no")`. A field
of `Some`, `Ok` or `Err` is not a place: no `&` through it, no assignment into it
(`bad-assignment-target`, M2-05 §1.6). The four constructors are rows of M2-14's table and are
the only new rows this page adds:

| row | signature |
|---|---|
| `Some` | `Some(value: T) -> Option<T>` |
| `None` | `None: Option<T>` |
| `Ok` | `Ok(value: T) -> Result<T, E>` |
| `Err` | `Err(error: E) -> Result<T, E>` |

`Some`, `Ok` and `Err` written bare, like any variant with fields, are `wrong-argument-count` where
the expected type is the variant's own type and `not-a-value` elsewhere (M2-09 §1.9); `None` is a
plain value.
The helpers `unwrap_or` and `ok_or` are M2-14's rows and are used here as it recorded them. There
is no `unwrap`, `expect`, `is_some`, `is_ok` or `panic` (§5).

### 1.2 Typing from position

`Some(x)`, `Ok(x)` and `Err(e)` carry the type of their argument and leave the other letter free;
`None` carries nothing. The free letter takes its binding from the position, by the same path
M2-06 §1.5 fixed for a hole: an argument takes the parameter's type; a field in a record or
variant literal; the right side of `let x: T =`, `var x: T =` or an assignment to a place; the
last expression of a function body or a `return`; an item of a list or map literal whose type is
known; an `if` branch, `match` arm or block end that itself has an expected type; the other side
of `==` or `!=` when that side's type is known on its own. With nothing to take it from:
`cannot-infer` at the expression (M2-02 §1.8), message "cannot infer the type of None; write it:
`let x: Option<T> = None`".

Added to the recorded page: an `if` or `match` used as a value with no expected type takes the
type of its first branch that carries its own type (M2-09 §1.3's test: a name, a literal other
than `[]`, `[:]` or `None`, or a call with no free letter), and that type is then the expected
type of every other branch. With no such branch the first branch's `None`, `Ok` or `Err` is
`cannot-infer`. This keeps M2-02 §1.8 as written (a local's type is the type of its initial
value; the initial value's type is now defined for this shape) and costs the checker one pass over
the branches before the second.

```
let a: Option<Int> = None                       // accepted
let b = if ok { Some(n) } else { None }         // accepted: Option<Int> from the first branch
let c = if ok { None } else { Some(n) }         // accepted: the second branch carries the type
let d = None                                    // rejected: cannot-infer at None
let e = Err("no")                               // rejected: cannot-infer at Err, "write the type: let e: Result<T, String> = ..."
fn f(n: Int) -> Result<Int, String> {
  if n < 0 { Err("negative") } else { Ok(n) }   // accepted: both branches take the result type
}
```

### 1.3 Matching

Patterns are M2-02's flat patterns: `Some(v)`, `None`, `Ok(v)`, `Err(e)`, and `Some(_)` or
`Err(_)` where the payload is unused. A match on an `Option` or `Result` subject must name both
variants; a `_` arm on an enum subject is rejected as M2-02 §1.9 fixes it (a `_` arm is for
`Int`, `String` and `Bool` subjects), and a missing one is `missing-arm` "no arm for variant
None". An arm that leaves early is a block: `None => { return Err("missing") }` written over
three lines (M2-02 §2 arm forms; M4-47's layout). A block that ends in `return`, `break` or
`continue`, and `unreachable()` itself, give no value and fit any expected type.

### 1.4 The pass-up form `?`

Written postfix, tightest with call, index and field (M2-03 §1.13), already in M2-02 §2's grammar
as the fourth postfix step. The operand must be an `Option<T>` or a `Result<T, E>`; the value of
`e?` is `T`, a fresh value (M2-05 §1.2). What `?` does is fixed by its rewrite:

```
e?  on Result<T, E>  is     e?  on Option<T>  is
match e {                   match e {
  Ok(v) => v                  Some(v) => v
  Err(x) => {                 None => {
    return Err(x)               return None
  }                           }
}                           }
```

So `?` may stand only where that `return` is legal: in a function whose result type is
`Result<U, E>` for a `Result<T, E>` operand with the same `E`, or `Option<U>` for an `Option<T>`
operand. It may not stand in a function with no result or any other result type, in `update`
(its result is `List<Effect<Msg>>`), or in an example (`Bool`; M2-06 §1.6). An `Option` passed up
in a `Result` function goes through `ok_or(opt, error)?`; a `Result` passed up in an `Option`
function has no short form and is matched, because dropping the error text is a choice the program
should write out. Both errors are `type-mismatch` at the `?` with the messages in §5.

`?` may stand on any postfix expression: `parse_int(s)?`, `get(m, k)?`, `xs[i]?` when the item
is an `Option`, `f(x)?.field`, `g(h(x)?)?`. `e?` as a whole statement whose `T` is not used is
`unused-result` like any value (M2-02 §1.4): "the value of parse_int is not used; write
`_ = parse_int(s)?`". At the end of a line `?` ends the statement, since it is not a two-sided
operator (M2-02 §1.5); `?` where a primary is expected is `unexpected-token` (M2-02 §4,
`lex/lone_question`). A payload bound by `?` from a place that the same statement writes is copied
out first (M2-05 §1.8); when `?` leaves early mid-expression the operands already evaluated are
released and no `&` place has yet been resolved (M2-05 §1.10 item 15). Writes to an `inout`
parameter made before the `?` stay made: there is no rollback inside a function, and the rewrite
makes that plain.

```
fn ratio(a: Int, b: Int) -> Result<Int, String> {
  if b == 0 {
    return Err("divide by zero")
  }
  Ok(a / b)
}

fn half_ratio(a: Int, b: Int) -> Result<Int, String> {
  let r = ratio(a, b)?                  // accepted: r is Int
  Ok(r / 2)
}

fn ratio_or_zero(a: Int, b: Int) -> Int {
  ratio(a, b)?                          // rejected: type-mismatch at ?
}

fn first_digit(s: String) -> Result<Int, String> {
  let d = parse_int(s[0])?              // rejected: type-mismatch at ?: ? passes None up, but first_digit returns Result<Int, String>; write ok_or(parse_int(s[0]), "...")? or match it
  Ok(d)
}

fn total(fields: List<String>) -> Result<Int, String> {
  var sum = 0
  for f in fields {
    sum += ok_or(parse_int(f), "not a number: {f}")?
  }
  Ok(sum)
}
```

### 1.5 The line between a trap and a return

A built-in traps when the program made a claim it could have checked and the claim is false; it
returns an `Option` when the program asked a question whose answer depends on the data. Square
brackets are a claim; a named lookup is a question. The rows this page fixes, taken from M2-03,
M2-09, M2-14 and M2-15 as recorded (M2-14 keeps the right to rename a row, not to move it across
the line):

| built-in | on failure | kind or type |
|---|---|---|
| `+` `-` `*` on Int, `abs` of the smallest Int | trap | `overflow` |
| `/` `%` by zero | trap | `divide_by_zero` |
| `x[i]`, `x[a..<b]`, `&xs[i]` outside the List or String | trap | `out_of_bounds` |
| `m[key]` with a missing key (read, `op=`, `&m[k]`, any step but the last of an assignment) | trap | `out_of_bounds` |
| `pop` on an empty List; a bad position in `code_at`, `insert`, `remove_at`, `swap`; a count below zero in `repeat`, `list_of`; a shift outside 0 to 63; `fixed` digits outside 0 to 20 | trap | `out_of_bounds` |
| `to_int` of a Float outside Int, `from_code` of a bad code point | trap | `bad_conversion` |
| `assert(false)`; `unreachable()` reached | trap | `assert` |
| `??name` reached | trap | `hole` |
| `parse_int`, `parse_float` of text that is not a number | return | `Option<Int>`, `Option<Float>` |
| `find` with nothing found | return | `Option<Int>` |
| `get(m, key)` with a missing key | return | `Option<V>` |
| `ReadFile`, `WriteFile` that fail | message | the `or:` function's message (M2-15) |
| `ExitWith(n)` outside 0 and 5 to 255 | stop | status 3 (M2-15) |

Every other row never fails. No trap kind is added: M2-06's eight stand, and `unreachable()`
reuses `assert` as M2-06 §1.1 already records. `m[key] = v` adds the key and never traps.

### 1.6 `unreachable()`

A call with no arguments and no fields, a row of M2-14's table. Typed like a hole: from its
position by the §1.2 path, and standing alone as a statement it has no type and needs none
(M2-02 §1.4, M2-06 §2). Reached, it traps `assert` at the function name with the report
`<app>: trap assert at <file>:<line>:<col>` and no detail line (M2-06 §1.2). Unlike a hole it is
not listed by `paka check` and does not stop `paka build` (line 308): a hole is unfinished work,
`unreachable()` is a finished claim. `paka check` accepts `unreachable()` with no argument form;
`unreachable("why")` is `wrong-argument-count` "unreachable takes no arguments". Code after it on
the same block is `unreachable-code` (M2-02 §5), since it leaves like a `return`.

```
fn sign_name(n: Int) -> String {
  assert(n >= -1 && n <= 1)
  match n {
    -1 => "minus"
    0 => "zero"
    1 => "plus"
    _ => unreachable()                  // accepted: fits String; never reached after the assert
  }
}
```

### 1.7 How a failure becomes the task's message and status

`?` cannot stand in `update`, so every `Result` that reaches the app is matched there, once: the
`Err` arm prints the text and chooses the status (M2-01 §2's one message on standard output and
one fixed error status; M3-11 writes `ExitWith(20)`). The pure part of the program passes
failures up with `?`; `update` is where they stop. A file that cannot be read is not a `Result`
but M2-15's `or:` message, and takes the same arm shape. A trap, by contrast, never reaches
`update`: it ends the program with status 3 and M2-06's report on standard error.

```
enum Msg { Start(path: String), Loaded(text: String), Failed(why: String) }

fn update(m: Msg) -> List<Effect<Msg>> {
  match m {
    Start(path) => [ReadFile(path, then: Loaded, or: Failed)]
    Loaded(text) => match total(records(text)) {
      Ok(sum) => [Print("{sum}"), Exit]
      Err(why) => [Print(why), ExitWith(20)]
    }
    Failed(why) => [Print("cannot read: {why}"), ExitWith(20)]
  }
}
```

`records`, not shown, splits the text into lines of fields with M2-14's string rows.

### 1.8 Unused results

M2-02 §1.4's rule, unchanged: a call whose value is dropped is `unused-result`, whatever the type.
What this page fixes is the message when the type is an `Option` or `Result`, so that the error
M2-31 must reject ("an unhandled failure") comes with its three repairs: "the value of ratio is
not used; it is Result<Int, String>: match it, pass it up with ratio(a, b)?, or write
`_ = ratio(a, b)`". The accepted gap stands: `let r = ratio(a, b)` with `r` never read is only
the `unused-name` warning, because the program said it wanted the value.

### 1.9 Habit spellings

As M2-02 §1.2 and M2-09 §2 fix for every other habit: an error with a fix, never accepted, under
the code the spelling already falls under. No new code and no new grammar. `if let`, `try`,
`catch`, `throw`, `guard` are names in an unexpected place or unknown names, except `let` directly
after `if` or `while`, which is `unexpected-token` at `let` ("Paka has no `if let` or `while let`;
match it"). `??` directly followed by the start of a value (a literal, a name, a hole, `(`, `[`,
`-`, `!`, `if`, `match`) is refused with the `??` text, `unexpected-token` at `??` ("`??` starts a
hole; write `unwrap_or(e, d)`"); a double try followed by a call, an item or a minus is written
with brackets: `(a??)(x)`. `null` and `nil` are `unknown-name` ("Paka has no null; write None and a
match"); `unwrap`, `expect` are `unknown-name` ("write a match, `?` or unwrap_or"); `is_some`,
`is_none`, `is_ok`, `is_err` are `unknown-name` ("match it"); `panic` is `unknown-name` ("write
unreachable() or assert(false)"); `e?.field` with `e` a plain record is `type-mismatch` at `?`
by §1.4. `=> return Err(..)` with no block is `unexpected-token` at `return` by M2-02 §2's arm
forms, message "an arm that returns is a block: write `=> { return Err(...) }` over three lines";
`=> break` and `=> continue` likewise, at `break` or `continue`, with the same message.

## 2. Grammar

Nothing is added. The forms this page uses are already in M2-02 §2: `postfix = primary { "(" args
")" | "[" expr "]" | "." LOWER | "?" }`; `type = UPPER [ "<" type { "," type } ">" ]`, so
`Option<T>` and `Result<T, E>` parse as `List<T>` does; `arm = pattern { "|" pattern } "=>"
( block | place assign_op expr | expr )`; `statement` includes `"return" [ expr ]`. `unreachable()`
is a call. M2-11 (parse) and M2-17 (parse generics, function values and error-handling forms) find
no new production here, and M2-17's share is the checking order below.

## 3. Implementation rule

Checking (M2-20, M2-22, M2-31), in the order M2-02 §8 fixes, with these additions in the body
pass: a `?` is checked after its operand's type is known; the operand must be `Option` or
`Result`, else `type-mismatch` at `?`; then the enclosing definition's result type must be
`Option<_>` for an `Option` operand or `Result<_, E>` with the operand's `E`, else
`type-mismatch` at `?`; the `?` has type `T`. An `if` or `match` with no expected type is typed
by §1.2 before its branches are checked against it. A match on `Option` or `Result` is checked
like a match on any two-variant enum. `unreachable()` with an expected type takes it; with none it
is accepted only as a whole statement.

Lowering, both back ends: `?` is the match of §1.4 and nothing more. In the interpreter it is one
tag test and a return. In native code (M4-30, M4-31b) `Option` and `Result` are the ordinary
two-variant enums of M4-31; `e?` tests the tag, on failure moves the operand into the result slot
unchanged (no new allocation: `Err(x)` passed up is the same value), releases every temporary
evaluated so far in the statement, and returns; on success the payload is moved out or copied by
M2-05 §1.8 and the wrapper's count is dropped. `unreachable()` is compiled like a hole minus the
release check and is kept in release builds (M2-06 §3, M4-30). A reached `unreachable()` and a
failed `assert` share one trap path.

## 4. M1 cases that stop holding

None. The only M1 case with a `?` outside a string is `lex/lone_question`, where `?` stands where
a primary is expected, and M2-02 §4 already re-expected it as `unexpected-token` 4:33; this page
keeps that result. No M1 case names `Option`, `Result`, `Some`, `None`, `Ok`, `Err` or
`unreachable`.

## 5. New diagnostic codes

None. The forms are refused under codes M2-02 kept; the fixed messages are:

- `type-mismatch` at `?`, operand not `Option` or `Result`: "? needs an Option or Result; NAME is
  T; drop the ?".
- `type-mismatch` at `?`, wrong enclosing result: "? passes Err(E) up, but NAME returns R; make it
  Result<T, E> or match it" / "? passes None up, but NAME returns R; make it Option<T>, write
  ok_or(..., error)? or match it" / "? passes None up, but NAME has no result; match it". In
  `update` the text names `update` and offers only the match.
  In an example (M2-06 §1.6): "an example has no ?; match it".
- `unused-result` on an `Option` or `Result` value: the three-repair text of §1.8.
- `cannot-infer` at `None`, `Ok`, `Err` or `unreachable`: M2-02 §1.8's text with the type written
  as `Option<T>` or `Result<T, E>`, the known letter filled in.
- `missing-arm` at `match`: "no arm for variant None" (`Some`, `Ok`, `Err` likewise).
- `wrong-argument-count` at `unreachable`: "unreachable takes no arguments".
- `unknown-name` and `unexpected-token` fix texts for the habit spellings of §1.9.

## 6. Samples

From the M2-01 classes: parsing (2), text processing (1) and file tools (7). Every sample is in
M4-47's layout and checks under the rules above.

**Failure: a record file with a line number in the error.** Each line is `name,score`; a bad
score names the line.

```
fn score_of(fields: List<String>, line: Int) -> Result<Int, String> {
  if len(fields) != 2 {
    return Err("line {line}: expected name,score")
  }
  let text = fields[1]
  ok_or(parse_int(text), "line {line}: bad score {text}")
}

fn total(records: List<List<String>>) -> Result<Int, String> {
  var sum = 0
  var line = 1
  for fields in records {
    sum += score_of(fields, line)?
    line += 1
  }
  Ok(sum)
}

example total_rejects_bad_score {
  total([["a", "3"], ["b", "x"]]) == Err("line 2: bad score x")
}
```

**Absence: a lookup that may find nothing.** `find` and `get` answer with an `Option`; square
brackets would claim.

```
fn rank(names: List<String>, who: String) -> String {
  match find(names, who) {
    Some(i) => {
      let place = i + 1
      "{who} is number {place}"
    }
    None => "{who} is not listed"
  }
}

fn count_words(words: List<String>) -> Map<String, Int> {
  var counts: Map<String, Int> = [:]
  for w in words {
    counts[w] = unwrap_or(get(counts, w), 0) + 1
  }
  counts
}

fn first_word(words: List<String>) -> Option<String> {
  if is_empty(words) {
    return None
  }
  Some(words[0])
}

fn first_two(words: List<String>) -> Option<String> {
  let a = first_word(words)?
  let b = first_word(words[1..<len(words)])?
  Some("{a} {b}")
}
```

**The app, end to end** is the `update` of §1.7 with `total` above, under
`app scores { start: Start  update: update  grants: [Console, ReadFiles] }` laid out over
lines. Run on a file whose second line is `b,x`, it prints `line 2: bad score x` and exits 20;
on a missing file it prints `cannot read: not found` and exits 20; a bug in `total` that indexed
past a list would trap `out_of_bounds` with status 3 and nothing on standard output.

**Refused, with the fix each message gives:**

```
let n = parse_int(s)                    // accepted, Option<Int>; n unread is a warning
parse_int(s)                            // rejected: unused-result at parse_int: match it, parse_int(s)?, or _ =
let n: Int = parse_int(s)               // rejected: type-mismatch at parse_int: expected Int, found Option<Int>
fn f(s: String) -> Int { parse_int(s)? }       // rejected: type-mismatch at ?: ? passes None up, but f returns Int
fn g(s: String) -> Result<Int, String> { Ok(parse_int(s)?) }   // rejected: type-mismatch at ?: write ok_or(parse_int(s), "...")?
None => return Err("missing")           // rejected: unexpected-token at return: write => { return Err(...) }
if let Some(v) = get(m, k) { .. }       // rejected: unexpected-token at let: Paka has no `if let` or `while let`; match it
x.unwrap()                              // rejected: unknown-name unwrap: write a match, ? or unwrap_or
let v = get(m, k) ?? 0                  // rejected: unexpected-token at ??: write unwrap_or(get(m, k), 0)
```

```
match get(m, k) {
  Some(v) => v                          // rejected: missing-arm at match: no arm for variant None
}
match get(m, k) {
  Some(v) => v
  _ => 0                                // rejected: M2-02 §1.9, a _ arm is for Int, String and Bool subjects
}
```

## 7. Alternatives considered and rejected

- A dedicated code for each `?` misuse (`?` on a plain value; `?` in the wrong function). The
  position and the message already give the repair; two codes would split one check. Rejected.
- A parse-time table of habit forms with its own code (`if let`, `?? default`, `try`, `throw`,
  `null`), and a code for `=> return expr` in an arm. M2-02 §1.2 and its arm grammar already
  refuse these under the codes they fall under; only the fix texts are fixed here (§1.9).
- `?` converting `Option` to `Result` on its own, with a fixed error text. The text would be
  invented by the compiler and would be the one the task prints; `ok_or` makes the program write
  it. Rejected.
- `?` allowed in `update`, returning `[Print(e), ExitWith(n)]` for a fixed `n`. It hides the
  status the task must choose (M2-01 §2) and makes `update` the one function with a different
  `?`. Rejected.
- A `_` arm allowed on `Option` and `Result`. M2-02 §1.9 forbids it on every enum; two variants
  is not a reason to break the rule, and the second arm is the one the task tests. Rejected.
- Exceptions, `catch`, a null value, a `defer`, a trap that the program can resume. All make a
  failure jump past the reader's view (line 136); line 357 asked for one mechanism. Rejected.
- Typing an unannotated `let` from a later use. Nothing is inferred backwards (§1.2). Rejected.

## 9. Accepted risks

- `ok_or(parse_int(f), "...")?` is longer than a `?` that converts on its own; the price is paid
  once per parse and buys an error text the task controls. Look again if practice runs show the
  conversion costing counted edits.
- A `let`-bound `Result` that is never read is only a warning. A program can lose a failure this
  way; the paper's rule that an unread name is a warning (M2-02 §5) is kept over a special case.
- The first-carrying-branch rule of §1.2 means `if ok { None } else { Some(n) }` is typed by its
  second branch; a reader scanning the first branch learns nothing there. The annotation
  `let x: Option<Int> =` is always available and the reference shows it.
- Writes to an `inout` parameter before a `?` stay made when the `?` leaves. This is what the
  rewrite says and what the reader sees; a function that must leave its parameter untouched on
  failure checks first.
