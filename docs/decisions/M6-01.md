# M6-01 · What release IR may promise the optimizer and what proves it

Status: approved by the owner on 2026-10-26.

Base: the recorded M6-01 page in DECISIONS.md. All six points **stand** as recommended there. One
settled line is **amended** because a later approved record fixes it: the status a place that cannot
be reached returns is 3, since M4-05 §5 gives compiled code the statuses 0, 1 and 2 and calls any
other one internal. What a trap shows and which trap wins are taken from M2-06 as given.

Today `paka build` writes M1's IR and runs `clang -O2`; a test keeps twelve banned words out of that
IR. This record replaces both: M6-04 takes the flags from M6-02, M6-05 turns the test into the
allow-list below.

## 1. Points

**1.1 Proof is the emitter alone.** A promise is allowed only when the way the compiler writes the
IR makes it true for every program, with nothing resting on an analysis of the user's code, and
where possible in a shape the linter can see. Facts the checker proves (such as inout arguments not
overlapping, GENESIS 3.2) come in only through a signed decision of their own (M6-23).

```
  %ok = icmp ult i64 %i, %len
  br i1 %ok, label %in, label %trap7, !prof !0
in:
  %p = getelementptr inbounds double, ptr %data, i64 %i
  %x = load double, ptr %p, align 8   ; inbounds: every use is a load or store
```

**1.2 Only the optimizer removes a check.** Paka writes every bounds and overflow check the source
has, and LLVM removes the ones it proves never fire. Paka's own part (M6-19) is to write loops in a
shape LLVM can see through. Each trap site returns its own position, so LLVM cannot merge traps that
differ.

```
fn total(xs: List<Int>) -> Int {
  var sum = 0
  // bounds check on xs[i]: written, then proven away by LLVM
  // overflow check on +=: written, and it stays
  for i in 0..<len(xs) {
    sum += xs[i]
  }
  sum
}
```

**1.3 A small first table, grown by measurement.** It holds the rows array loops need (section 2). A
row is added later only with a by-construction proof, a linter rule, a measured gain on an M6-02
benchmark and a reviewer told to break it.

```
allowed:  nounwind | inbounds (use is load/store) | natural align
          hints: !prof, cold, inline marks | internal, private, constant
never:    nsw nuw exact | fast-math | undef poison unreachable
          assume | mustprogress willreturn | tail musttail | noalias
```

**1.4 Tail calls: never written, never promised.** Paka never marks a call `tail` or `musttail`;
LLVM may still turn a call into a jump where it proves that safe. A program that needs a bounded
stack uses a loop.

```
fn count_down(n: Int) -> Int {
  if n == 0 {
    0
  } else {
    count_down(n - 1)
  }
}
// interpreter: count_down(1000000) traps stack
// release: may run as a loop and give 0
```

**1.5 A place the checker proved unreachable returns status 3.** The runtime reports it as an
internal error: M1-14's line and exit status 4. It costs one compare and branch per match that LLVM
cannot remove. **Amends** the page's 255, left there for M4-05 to number.

```
  switch i64 %tag, label %bad [ i64 0, label %arm0
                                i64 1, label %arm1 ]
bad:
  ret i32 3          ; not finished, trapped or stopped: internal
```

**1.6 Runtime functions promise only `nounwind`.** It holds for any Rust code behind a C-convention
entry, so it cannot go stale. Hot paths such as item access are written inline in the IR (M6-11).

```
declare i32 @paka_rt1_list_grow(ptr, i64) nounwind
```

## 2. The table

| Row | Allowed where | Proof |
|---|---|---|
| `nounwind` | every function Paka defines, every runtime declaration | No `invoke`, `landingpad` or `resume` is ever written (linted); a trap is a status return; each runtime entry catches panics, so the user sees status 4, not an abort. |
| `inbounds` | a getelementptr whose every use is the address of a load, a store or another such getelementptr | Written only by the one helper that writes bounds check, address and access together. An address passed to a call has no `inbounds`. |
| alignment | every load and store, at the type's natural alignment from M4-22's layout table | The compiler lays out every value; the runtime allocates at 8 bytes or more (M6-10 tests both sides). |
| hints | `!prof`, `llvm.expect`, `cold`, `hot`, `noinline`, `inlinehint`, `alwaysinline` | A wrong hint costs only speed. |
| linkage and constants | `internal`, `private`, `unnamed_addr`, `constant` on globals | Release IR defines no changeable global; no store targets a global (linted); bytes in a constant are copied before their first write (M6-11 tests it). |

## 3. Rules that follow

- Plain words that promise nothing sit on the linter's allow-list beside the rows: integer and float
  arithmetic and comparison, `select`, `phi`, `br`, `switch`, `ret`, getelementptr without flags,
  `extractvalue`, `insertvalue`, `zext`, `sext`, `trunc`, `sitofp`, `ptrtoint`, the
  overflow-reporting intrinsics and `llvm.memset`, plus `load`, `store`, `call` and `alloca` under
  the rules here. A lowering task adds a word it needs in its own pull request, with a note that no
  input makes LLVM call its result undefined or poison.
- Instructions undefined on bad input are written only behind their check, by the helper that writes
  it: `sdiv`, `srem` after the zero and smallest-Int-by-minus-one checks; `shl`, `ashr` after the 0
  to 63 check; `fptosi` after the range and NaN check. Any other such word follows the same rule or
  takes a constant operand in range.
- Checked `+ - *` use the overflow-reporting intrinsics; `wrap_add`, `wrap_sub`, `wrap_mul` are
  plain `add`, `sub`, `mul`.
- Copies use `llvm.memmove`; `llvm.memcpy` only when the destination was allocated in the same
  function.
- Never allowed: `nsw`, `nuw`, `exact`, `disjoint`, `nneg`, `samesign`, `nusw`; `undef` and `poison`
  as written values; `unreachable`; `llvm.assume`; `mustprogress`, `willreturn` (an endless loop is a
  legal program, M2-06); `tail`, `musttail`; `invoke`; inline assembly; type-based alias metadata;
  `noalias`, value ranges, `nonnull`, `noundef`, `dereferenceable`, `readonly`, `readnone`,
  `memory(...)`, `captures` and lifetime marks until a row is added for them.
- Float: no fast-math flag (`fast`, `nnan`, `ninf`, `nsz`, `arcp`, `contract`, `afn`, `reassoc`), no
  `llvm.fmuladd` or `llvm.fma`. Allowed float intrinsics: `sqrt`, `floor`, `ceil`, `trunc`,
  `round`, `fabs`. Where NaN bits are made canonical is M6-08's; every place a program or test sees
  them shows the canonical ones.
- `noalias` appears nowhere until M6-23 signs it for inout parameters, at the places it signs.
- `alloca` only with a constant size and only in a function's first block. M6-16 may read the stack
  position as a plain word and mark a large-frame function `noinline`; nothing relies on a guard page.
- What a trap shows and which trap wins: M2-06 as given, kind and position, first in evaluation
  order. Stack and memory traps are compared on kind only.
- The linter reads the IR Paka writes, before clang optimizes it. Any keyword, attribute, metadata
  name or intrinsic that is neither a row nor a plain word fails. What LLVM adds itself is not linted.
- The clang command adds no flag that loosens meaning: no `-ffast-math`, no contraction flag.
  Optimization level and target CPU are M6-02's one constant.
- Adding a promise row takes one pull request with its proof, its linter rule, a measured gain on an
  M6-02 benchmark, a level 4 reviewer told to break it, and the owner's approval. A plain word needs
  its note and the normal review.
- A measurement-only build (M6-30) stands outside the table; its numbers count only under M6-02's
  clean-run rule.
- Not a row: that every address is live and written. That rests on the language (bounds checks, one
  owner, borrows that cannot be stored) and the layouts of M6-10 and M6-11, and is tested by
  three-mode conformance and the fuzz.
- Shared stack-trap cases already use the call's result in a checked operation
  (`down(n + 1) + 1`), so LLVM cannot turn them into loops and they still trap in release.

## 4. What this changes in TASKS.md

- M6-04: the one constant replaces M1's `-O2` (value from M6-02).
- M6-05: the allow-list has two parts, rows and plain words, plus two whole-line checks: every use of
  an `inbounds` result is a load or store address, and no store targets a global. Its level 2 reason
  ('token scan') is looked at again.
- M6-07: checked arithmetic through the overflow intrinsics; division and shifts through the helpers
  that check first; a match's fall-through returns status 3.
- M6-08: no `fmuladd`, `fma` or float flags; only the six exact float intrinsics.
- M6-09: field addresses passed to a call carry no `inbounds`.
- M6-10: its test covers 8-byte runtime alignment and the constant-buffer mark.
- M6-11: item access through one helper; `memmove` unless the destination is fresh; constant bytes
  copied before the first write, with a test; runtime declarations carry `nounwind` only.
- M6-16: constant-size slots in the first block; no `tail` marks; the stack-position read is a plain
  word; no guard-page attribute.
- M6-19: shapes loops and removes no check.
- M6-20: when the interpreter ends in a stack trap, release may finish or run on, so such runs are
  cut by a time limit and not filed as a divergence.
- M6-21: planted 'wrongly removed check' bugs are emitter bugs that leave a check out.
- M6-24: adds the `noalias` row and its linter rule together, only as M6-23 signs.
- M6-30: a measurement build keeps the promises that rested on the dropped checks, so it is valid only
  on inputs the normal build ran without a trap.
