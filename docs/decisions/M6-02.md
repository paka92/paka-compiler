# M6-02 · Benchmark set, fairness rules and cost-measurement method

Status: approved by the owner on 2026-10-26.

Base: the recorded M6-02 page in DECISIONS.md. All eight points **stand** as recommended there. One
part is **amended** because M2-10 is approved since: the language has no shared type and no pools,
so `expr_parse` has no shared-subtree form, `bfs` no pool form, the reference-count and handle-check
rows read 'not built', and the measurement-only build omits one family, bounds checks. In their
place the table carries the cost of copying owned trees (M2-10 §1.3), isolated as in 3.4.

This page is approved before any measurement. Nothing here is timed yet.

## 1. Points

**1.1 Baseline x86-64 at -O3, for all three.** No CPU flag, which is each compiler's own default,
so no language gets an instruction set the others lack and the binary runs on any 64-bit PC. It
replaces M1's `-O2` as M6-04's one constant.

```
paka:  clang -O3 prog.ll libpaka_rt.a ...
rust:  rustc --edition 2024 -C opt-level=3 -C codegen-units=1 -C panic=abort prog.rs
c++:   clang++ -O3 -std=c++20 -fno-exceptions -fno-rtti -ffp-contract=off prog.cpp
```

**1.2 Idiomatic safe code, tuned once.** Same algorithm, input and checksum in all three, standard
library only, one thread. Safe Rust with iterators; C++ with `std::vector` and plain indexing; no
vector intrinsics, pragmas or `restrict`. One tuning pass per version by a second agent, then all
sources are frozen by commit before any timing.

```
fn dot(a: &[f64], b: &[f64]) -> f64 {
    a.iter().zip(b).map(|(x, y)| x * y).sum()
}
```

**1.3 Eleven small own programs,** each under about 150 lines per language.

```
float/array: saxpy_dot, matmul, stencil, nbody
integer:     sieve, collatz (each checked and wrapping), mix (wrapping only)
pointer:     expr_parse, binary_trees, bfs, word_count
```

**1.4 Integer kernels against both checked and default Rust.** Paka checked stands beside Rust with
overflow checks on (like for like) and beside default Rust and C++ (what their users get). Paka
wrapping stands beside Rust's wrapping operations and C++ unsigned arithmetic. Inputs never
overflow, so all checksums agree.

```
x = 3 * x + 1                       // checked: traps if x leaves Int
x = wrap_add(wrap_mul(3, x), 1)     // wrapping twin: same result here
```

**1.5 Measurement-only builds are accepted, after a clean run.** Only a compiler built with the
`measure` feature takes the switch; the binary prints a banner on standard error and is never
shipped. A measured run counts only if the normal build ran the same program and input first,
without a trap and with the same checksum. **Amended:** the one family it omits is bounds checks.

```
$ paka build stencil.paka --omit bounds -o stencil_nb     (measure feature only)
$ ./stencil_nb
MEASUREMENT BUILD: bounds checks omitted, not a Paka program   (standard error)
4183902771
```

**1.6 Whole process, timed from outside.** From start to exit, pinned to one core, inputs sized so a
run takes 1 to 3 seconds and start-up is well under one percent.

```
$ paka-bench run stencil
stencil  paka 1.412 s  rust 1.398 s  c++ 1.371 s   (median of 10, spread 1.9%)
stencil  paka/rust 1.01   paka/c++ 1.03   expected: parity
```

**1.7 The LLVM gap is stated; C++ is the control.** Each column header names its compiler and LLVM
version. A note says the C++ column, built by the same clang as Paka, is the same-optimizer
comparison, and a small gap to Rust may be the optimizer's.

```
            paka             rust             c++
            clang 21.1.8     rustc 1.96.1     clang++ 21.1.8
            (LLVM 21)        (LLVM 22)        (LLVM 21)
Note: Rust is optimized by a newer LLVM. The C++ column is the like-for-like one.
```

**1.8 Parity means within 10%.** The table prints the raw ratio and one word fixed now: 'parity' at
most 1.10; 'as expected' on a pointer-heavy row up to 1.30; 'worse than expected' above the row's
line; 'measured' where the paper names no amount.

```
matmul   paka/c++ 1.04            expected: parity         -> parity
bfs      paka/rust 1.22           expected: behind 10-30%  -> as expected
bfs      paka/c++ 1.36            expected: behind 10-30%  -> worse than expected
collatz  paka/rust(checked) 1.06  expected: none stated    -> measured
```

## 2. The programs

- saxpy_dot: scale-and-add over two lists, then a dot product (the two-list kernel M6-24 names).
- matmul: plain matrix product on flat lists. stencil: five-point average over a grid, many sweeps.
  nbody: five bodies as records of Floats, with `sqrt`.
- sieve: primes below N in a `List<Bool>`. collatz: longest chain below N. Each has a checked form
  and a wrapping twin. mix: a 64-bit mixing generator and running hash, wrapping only, built from
  operations Paka has (wrapping multiply, xor, sign-copying right shift).
- expr_parse: parse an ASCII arithmetic text into a tree of a self-containing enum, then evaluate.
  binary_trees: build and walk many trees. bfs: shortest paths on a `List<List<Int>>` graph (M2-01).
  word_count: count words of an ASCII text in a `Map<String, Int>`.
- Numeric inputs come from a fixed seed through the same wrapping generator in all three; expr_parse
  and word_count read one ASCII file the runner makes. Each program prints one Int checksum line; a
  Float result is scaled to Int by a rule in the program list. The runner refuses a row whose three
  checksums differ.
- Paka sources are written from the language reference as an agent would write them: no switch, no
  benchmark-only built-in. Each is a headless app whose first handler computes, prints the checksum
  and exits, built with plain `paka build`.

## 3. Rules that follow

**Flags and libraries**

- Paka: `clang -O3`, no CPU flag, from M6-04's constant; the runner adds none. Rust: the line in 1.1,
  single file, no crates, plus `-C overflow-checks=on` for the checked column. C++: the line in 1.1.
  No fast-math, profile-guided or link-time optimization anywhere.
- Compiler versions are checked by the runner before each run; C++ uses the system's libstdc++,
  whose version the results file records. No download is needed.
- Standard library only, default allocator: `Vec`, `HashMap` with its default hasher,
  `std::vector`, `std::unordered_map`, `Box` and `std::unique_ptr` for tree nodes. 64-bit signed
  integers and 64-bit floats only. C++ sieve flags in `std::vector<char>`. No checksum depends on map
  order. The table names the containers used.

**Run protocol**

- The runner (M6-27) is plain Rust with the standard library, started as `paka-bench run`. It pins
  with `taskset` and times with Rust's monotonic clock. Nothing is installed.
- One fixed logical CPU, single thread. Per benchmark: one unrecorded warm-up of each binary, then 10
  rounds, each running the three languages one after another. Reported: median, and spread as
  (slowest - fastest) / median.
- Spread above 5% reruns once; still noisy, the row is published with a noise mark. The runner
  refuses to start when the one-minute load average is above 1.
- Input sizes are set by a Rust-only calibration run (default build 1 to 3 seconds, input building
  under 5%) and committed before any Paka binary is timed.
- Recorded: every raw time, checksums, compiler versions, flags, CPU model, kernel, governor, boost
  setting, the pinned CPU and the commit of the sources. Build time and memory use are not measured.
- Order: program list, sources, sizes, flags, protocol and the parity line are committed first. No
  Paka timing is looked at before that commit; the runner publishes only from it.
- After the first timing a program changes only for a logged reason, and then all three are re-run.
  A program is never dropped after its number is seen. Adding one is free.

**Expectation per row (GENESIS 3.2)**

- Float and array: parity with Rust; parity with C++ only where no trap branch is left in the inner
  loop, else 'none stated'.
- Wrapping integer: parity with both. Checked integer: 'behind' with no amount against default Rust
  and C++, 'none stated' against checked Rust. Pointer-heavy: behind by 10 to 30%.

**How each section 8 cost is isolated**

1. Overflow checks: the checked kernel's time over its wrapping twin, for sieve and collatz. No
   special build.
2. Bounds checks: the normal build's time over the measurement build without bounds checks, for
   saxpy_dot, matmul, stencil and sieve, plus a yes or no from M6-19's check: is a trap branch left
   in the inner loop.
3. Reference counting and handle checks: 'not built', with the reason (M2-10: no shared type, no
   pools). No number is invented.
4. Copying owned trees (in their place): a runtime built with the `measure` feature times its copy
   routine during expr_parse, binary_trees and bfs, and the table shows copy time as a share of the
   run. The programs are the ones in the set, unchanged.
5. State copy per handler: a visual app run with no window handles 10,000 messages on a state holding
   a `List<Int>` of 1,000, 100,000 and 10,000,000 items, once with a handler that writes one small
   field and once with one that writes one list item. A `measure` runtime times the copy itself;
   the figure is time per handler at each size. It must be a visual app: a headless program ends on
   a trap, so its runtime keeps no copy.
6. Dev-mode slowdown: the to-do sample run with no window through one committed script (add 1,000
   items, then tick each), in dev and in release. A `measure` runtime replays it and times each
   frame. Two ratios: time in Paka code (update and view) and whole-frame time including layout;
   drawing to a screen is not timed and the table says so. The numeric kernels also run once in dev
   mode to place Paka beside the 2-3x and 10-100x of GENESIS 3.1.

**What the table does not claim**

- Single-threaded code on one machine at the baseline CPU level; nothing about vector code, threads
  or memory use (GENESIS 3.2's last row).
- The pointer-heavy rows are measured without pools, so they do not test the cause the paper gives
  for that gap, handle checks.

**Owner must still**

- Leave the machine idle while the published run is made. Setting the CPU governor or frequency
  boost is optional and is the owner's; the runner records whatever is set.
