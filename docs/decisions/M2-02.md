# M2-02 · Statement, definition and comment syntax: decision

Base: the paper-literal proposal. Grafted from the checker-first proposal: the exact newline rule,
comment ownership inside bodies, the diagnostic code list, the strict discard rule and the 64 limit.
Grafted from the first-try proposal: the fix text on every habit-spelling error, the "one name bound
once per scope chain" wording, and the file-order rule. Every rule below agrees with the M2-02 entries
already in DECISIONS.md unless marked **overturns**; none are overturned. Where another milestone owns
a rule, this page says so and marks the grammar gap.

## 1. Resolutions, point by point

### 1.1 Argument labels: keep the `;` mark

A parameter list is bare parameters, then optionally `;` and labelled parameters. A bare parameter is
passed by position; a labelled one is passed as `name: value`, in the declared order. Built-in rows
and record building use the same spelling. Calls through a function value are positional (M2-09).
A label in a record literal that is not a field of the type, or stands out of declared order, is
`wrong-label` at the label, as in a call; the checker finds it, not the name pass.

```
fn clamp(x: Int; lo: Int, hi: Int) -> Int { max(lo, min(x, hi)) }
clamp(5, lo: 0, hi: 9)        // accepted
clamp(5, 0, 9)                // rejected: wrong-label at 0, "write lo: 0"
clamp(x: 5, lo: 0, hi: 9)     // rejected: wrong-label at x, "x is bare: write 5"
clamp(5, hi: 9, lo: 0)        // rejected: wrong-label at hi, "labels come in declared order"
```

Why not positional-only user functions: M2-02.4 is owner-accepted, and M2-14, M2-15 and M4-47 already
write rows and samples with `;`. Dropping it now reopens three rulings for a saving of one token per
labelled signature. Why not Swift's rule: every bare parameter costs a `_` and the paper's signatures
change. Confirmed: `;` is the final spelling, no longer provisional.

### 1.2 Habit spellings: errors with a fix, never accepted

`return` on the last line, a `;` anywhere, a trailing comma, a comma after a match arm and `else` on
the line after `}` are errors. Each message carries the fix. This is M2-02 as settled and M4-47.5.

```
fn double(n: Int) -> Int {
  return n * 2          // return-last: "drop return: the last line is the value"
}
let xs = [1, 2,]        // unexpected-token at ]: "remove the comma before ]"
let y = 1;              // unexpected-token at ;: "remove the ;: a line break ends the statement"
match m { Inc => 1,     // unexpected-token at ,: "remove the comma: one arm per line"
```

Why not accept-and-rewrite ("bends"): two spellings on input (line 51), and every whole-file tool and
the M3 experiment would have to apply the same rewrite to be fair. The cost is one counted edit per
habit slip; M4-47.5 chose the same side after seeing that cost.

### 1.3 Names and shadowing

- A local name is bound once per scope chain: a `let`, `var`, parameter, `for` name or pattern name
  may not reuse a name visible at that point (`duplicate-local`, at the name of the second binding (after `let`, `var` or `for`, or the
  parameter name), "already bound
  at line N"). Sibling blocks may reuse a name; a block may not rebind one from an enclosing block.
- A `let` or `var` name is visible from the next statement on, not in its own initial value:
  `let total = total + 1` uses an earlier `total` or is `unknown-name`.
- A local may hide a lower-case top-level function or built-in function; inside that scope the name
  is the local, and calling it is `not-a-function`.
- Unused local or parameter: warning `unused-name`. Warnings are printed by `paka check` only, on
  standard error, and only when there is no error; they never change the status. `paka run`,
  `paka examples` and `paka build` print none. (So the M1 light program, whose `m` is unused, runs
  silently as before.)
- A field name written twice in one type or variant is `duplicate-name` at the later one.
- Nearest name. The fix of an unknown name, type or grant (`unknown-name`, `unknown-type`,
  `unknown-grant`) is the visible name of the same kind and the same first-letter case with the
  smallest byte edit distance, when that distance is at most a third of the unknown name's length,
  rounded down; a tie goes to the first in byte order. Otherwise there is no fix, and no fallback
  such as `Console` stands in for one. Of the same kind: for an expression the locals, functions
  and variants in sight; for a type the types; for a grant the grants; for a pattern the variants;
  after `update:` the program's functions.
- Order of the name tests. Errors are found per definition in source order (spec/m1.md section 8)
  and a type is tested from the outside in: its name, then its argument count
  (`wrong-type-arguments`), then its arguments. Declaration errors come first; after that a name
  error in one definition never hides or changes the result of another. An app's name errors are
  held per entry, so the checker can report them after the app's duplicate-key, missing-key and
  duplicate-grant tests.
- Variants are bare and unique per program, built-ins included (M2-02.2). Case carries meaning
  (M2-02.3). One pool for all definitions, variants and built-ins (M1 §6 kept).
- Which files make one program: one `.paka` file, or every `.paka` file directly in the given
  directory (no subdirectories). Declarations are read in byte order of file names, then source
  order, so `duplicate-name` points at the later one deterministically. Where a tool puts a new
  definition is M4-48's.

### 1.4 Discard: strict both ways

An expression statement whose value is not used is `unused-result`; `_ = expr` discards; `_ = expr`
where `expr` has no value is `nothing-to-discard` (an `if` without `else` is `if-needs-else`). Calls with no result, holes and `unreachable()`
stand alone. The last line of a block whose value is used is the value; in a block whose value is
not used (a no-result function, a loop body, a value-less `if`, a value-less arm) the last line is an
ordinary statement and falls under the same rule.

```
fn step(s: inout Counter) {
  s.count += 1          // accepted
  pop(&q)               // rejected: unused-result at pop, "write _ = pop(&q)"
  _ = step(&s)          // rejected: nothing-to-discard at _, "step has no value: drop _ ="
}
```

Why not a silent drop of unused values: a pure call whose result is dropped is a bug (line 151);
one rule for Result (M2-12) and everything else.

### 1.5 Newline rule (lexer, exact)

The lexer turns a line feed into a NEWLINE token, except:

1. when the innermost unclosed bracket is `(` or `[`;
2. when the previous significant token is `,` `=` `->` `=>` `|` `{` or a two-sided operator
   (`+ - * / % == != < > <= >= && || ..<` and `+= -= *= /= %=`);
3. when the next significant token is `}` `)` or `]`.

Several NEWLINEs in a row collapse to one. A line holding only a comment, or nothing, yields no
NEWLINE of its own. End of input acts as one NEWLINE. `?` and `&` are not two-sided operators, so a
`?` at a line end ends the statement (M2-12). `<` and `>` in a type are the comparison tokens (M2-03:
no `>>`). Inside an open `{` a line feed is a NEWLINE, so a block is
statements separated by NEWLINEs; `{}` and `{ x }` on one line also parse.

```
let total = a +          // continues: trailing operator
  b
let xs = [1,
  2]                     // continues: inside [
if c {
}
else { }                 // rejected: unexpected-token at else, "put else on the line of the }"
```

### 1.6 Comments

`//` to the end of the line, anywhere outside a string, kept in the tree, never a token for the
grammar. Ownership, by position (M2-02.8 and M4-47.3): a comment on its own line belongs to the next
definition, statement, match arm, field, variant or app key; the last comment lines of a block
before its `}` belong to the block; a trailing comment belongs to the construct that starts on its
line; a comment inside a flat list (arguments, items, parameters) belongs to the statement or
definition holding the list; a comment after the last definition joins that definition. Blank lines
do not break ownership. No block comments.

### 1.7 Nesting limit: 64

A level is an unclosed `(` `[` `{` or type `<`, and the `{` of a string interpolation. `else if`
chains, operator chains, call chains and prefix-operator chains are parsed by loops and add no level
beyond their brackets. The 65th level is `nesting-too-deep` at its opening token: "nesting deeper
than 64 levels; move the inner part into a named function or local". Applies to types too.

Two forms nest with no bracket and count a level each all the same: an `if` or `match` standing in
the condition or subject of another, and a `fn` type standing as the result of another. A chain
(operators, calls, fields, `?`, prefix operators) adds no level but is at most 1,000 links long; the
link after that is `nesting-too-deep` at its token: "chain longer than 1,000 links; split it with a
local". A link is a binary operator, a call `(`, an index `[`, a field `.`, a `?` or a prefix
operator; the 1,001st link is reported at that token. The `if` or `match` standing in a header
counts a level; the one holding it adds none. Without these two rules a tree could be deeper than any walker's stack with no bracket at all.

Every walker over the tree takes a chain (binary, unary, call, field, index, `?`) by a loop, never
by recursion, so its recursion depth is bounded by the 64 levels. Why 64, not 256: every back end's
parser, checker, printer and tool walk the same tree; 64 is far above any readable program and fits
the 8 MiB stack of a program's main thread, where the tool runs. A debug test thread has 2 MiB, so
the tests that go 64 levels deep with 1,000-link chains run on a thread of 8 MiB. 256 buys nothing a
program needs and makes each walker prove its own stack margin.

### 1.8 Local type inference

A local's type is its written annotation, else the type of its initial value. A value that needs
its position to fix its type (`[]`, `[:]`, `None`, `Ok(x)`, `Err(e)`, `??name`, `unreachable()`)
takes it from an annotation, parameter, field, result, condition or the other side of an operator
(M2-06, M2-09, M2-12). With nothing to take it from: `cannot-infer` at that expression, not at the local,
with the text of §5. Nothing is inferred across definitions (line 140).

### 1.9 Other grammar calls

- `()` is grammatical: zero-parameter functions and calls exist. Calling a fieldless variant
  (`Exit()`, `Exit("now")`) is `wrong-argument-count` at the name: "Exit has no fields: write Exit".
- `view` definitions and the `view:` app key stay `unsupported-view` in M2 (gap for M5-01/M5-11).
  `migrate` is reserved (gap for M5). `state:` is parsed; its checks are M2-15's.
- An empty enum and an empty match are `unexpected-token` at the `}`; `type Empty {}` and an empty block `{}`
  parse. `{}` has no value.
- In an `if` or `while` condition, a `for` list and a `match` subject, an Upper name followed by `{`
  ends the header; write `(Counter {})` to build a record there. The `{` then opens the body, so
  `if Counter { count: 1 } == c` is `unexpected-token` at the `:`.
- Patterns are flat: `V`, `V(a, _)`, an Int (with optional `-`), a String, `true`, `false`, `_`.
  Alternatives joined by `|` bind no names: a name in a pattern of an arm with more than one pattern
  is `unexpected-token` at the first such name, "alternatives bind no names; write one arm per
  variant". `_` is allowed only on Int, String and Bool subjects and inside a variant pattern; on an
  enum subject (a user enum, `Option`, `Result`) it is `wildcard-on-enum` at the `_` (§5).
- A field default is a `constant` of the grammar in §2: a literal (`-` on a number included), `[]`,
  `[:]`, or a variant or record with constant arguments. `[1, 2]` and `["a": 1]` are not constants.
  Anything else is `unexpected-token` at its first token that is not part of a constant, reported
  by the parser: the name of a call, the operator of a sum, the first item of a non-empty list.
  A bare variant that has fields is left to the expression checker
  (`wrong-argument-count`, M2-09 §1.9).
- Names start with a letter; `_` alone is a token; `_m` is still `unexpected-character` at `_`
  ("names start with a letter; `_` alone discards").
- Tab and carriage return stay `invalid-byte` (M4-47: no tabs). Other bytes: M2-03 (UTF-8).

## 2. Grammar (EBNF)

Tokens: NL (newline, §1.5), UPPER, LOWER, INT, FLOAT, STRING (with `{expr}` parts, M2-03), `_`, and
keywords `app break continue else enum example false fn for if in inout let match migrate return
true type var view while`, reserved everywhere. App keys are not keywords. Comments are not tokens.
`[ ]` optional, `{ }` repetition, `|` choice; the literal braces are quoted.

```
program     = { NL } [ definition { NL definition } ] { NL }
definition  = type_def | enum_def | fn_def | example_def | app_def | view_def
type_def    = "type" UPPER "{" [ field { "," field } ] "}"
field       = LOWER ":" type [ "=" constant ]
enum_def    = "enum" UPPER "{" variant { "," variant } "}"
variant     = UPPER [ "(" field { "," field } ")" ]            (* no defaults in variants *)
fn_def      = "fn" LOWER "(" params ")" [ "->" type ] block
params      = [ param { "," param } ] [ ";" param { "," param } ]
param       = LOWER ":" [ "inout" ] type
example_def = "example" LOWER block
app_def     = "app" LOWER "{" { NL } [ entry { NL entry } ] { NL } "}"
entry       = "state" ":" UPPER                                 (* checks: M2-15 *)
            | "start" ":" expr                                  (* checks: M2-15 *)
            | "update" ":" LOWER                                (* checks: M2-15 *)
            | "grants" ":" "[" [ UPPER { "," UPPER } ] "]"      (* checks: M2-15 *)
            (* "view" ":" LOWER and "migrate" entries: gap, M5-01 / M5 *)
view_def    = "view" ...                                        (* gap: M5-01, M5-11; unsupported-view in M2 *)

type        = UPPER [ "<" type { "," type } ">" ]
            | "fn" "(" [ type { "," type } ] ")" [ "->" type ]
constant    = [ "-" ] INT | [ "-" ] FLOAT | STRING | "true" | "false" | "[" "]" | "[" ":" "]"
            | UPPER [ "(" args ")" ] | UPPER "{" [ labelled { "," labelled } ] "}"   (* constants inside *)

block       = "{" { NL } [ statement { NL statement } ] { NL } "}"
statement   = "let" LOWER [ ":" type ] "=" expr
            | "var" LOWER [ ":" type ] "=" expr
            | "_" "=" expr
            | place assign_op expr
            | "return" [ expr ]
            | "break" | "continue"
            | "for" LOWER "in" expr block
            | "while" expr block
            | expr                                              (* if, match and calls included *)
assign_op   = "=" | "+=" | "-=" | "*=" | "/=" | "%="
place       = LOWER { "." LOWER | "[" expr "]" }                (* a var local or inout parameter *)

expr        = or_expr
or_expr     = and_expr { "||" and_expr }
and_expr    = cmp_expr { "&&" cmp_expr }
cmp_expr    = range_expr [ ( "==" | "!=" | "<" | "<=" | ">" | ">=" ) range_expr ]
range_expr  = add_expr [ "..<" add_expr ]
add_expr    = mul_expr { ( "+" | "-" ) mul_expr }
mul_expr    = unary { ( "*" | "/" | "%" ) unary }
unary       = { "-" | "!" } postfix
postfix     = primary { "(" args ")" | "[" expr "]" | "." LOWER | "?" }
primary     = INT | FLOAT | STRING | "true" | "false" | "??" LOWER
            | LOWER | UPPER | "&" place
            | UPPER "{" [ labelled { "," labelled } ] "}"       (* record; not in a header position *)
            | "(" expr ")" | list | map | if_expr | match_expr
args        = [ expr { "," expr } ] [ [ "," ] labelled { "," labelled } ]   (* bare first, then labels *)
labelled    = LOWER ":" expr
list        = "[" [ expr { "," expr } ] "]"
map         = "[" ":" "]" | "[" expr ":" expr { "," expr ":" expr } "]"      (* M2-14 *)
if_expr     = "if" expr block { "else" "if" expr block } [ "else" block ]
match_expr  = "match" expr "{" { NL } arm { NL arm } { NL } "}"
arm         = pattern { "|" pattern } "=>" ( block | place assign_op expr | expr )
pattern     = "_" | [ "-" ] INT | STRING | "true" | "false"
            | UPPER [ "(" ( LOWER | "_" ) { "," ( LOWER | "_" ) } ")" ]
```

Notes for a hand-written recursive-descent parser: every choice is decided by the current token
(`let`, `var`, `_`, keywords) or by one token of lookahead after a LOWER (`=` or an assign_op means
assignment; `(` `[` `.` continue a place or an expression; after the place is parsed, an assign_op
means assignment, else the expression continues). `UPPER "{"` is a record except in a header
position. `[` then `:` or `expr ":"` is a map. `??` followed directly by a lower-case letter is one
hole token. Comparisons do not chain (grammar: one comparison per level);
`a < b < c` is `unexpected-token` at the second operator. `if` without `else`, or
whose branches have no value, has no value; a value needs `else` (`if-needs-else`). The `else`
keyword must sit on the line of the closing `}` (no NL before it). Type arguments appear only in
type positions, so `<` in an expression is always a comparison.

Owned elsewhere, not fixed here: operator meanings and precedence (M2-03, used as given); `&`
targets and overlap (M2-05); hole typing and example statuses (M2-06); function values (M2-09);
`?` placement (M2-12); map rows (M2-14); every app check, start, end and grants (M2-15); view
bodies and trailing blocks (M5-01, M5-11).

Within one definition the diagnostic is the earliest in source order among all its errors: name,
signature and body alike. Inside one call the order is: the count, then labels left to right, then
arguments left to right; a Map key type is tested right after the key argument, before the value
argument. The body is checked even when the names or the signature of its definition have an
error; a name or type that error left unknown is silent in the body, so nothing cascades.
`return 1 + "a"` on the last line is `return-last`, which stands first.

## 5. New diagnostic codes

Parse (status 1, first offending token):

- `nesting-too-deep` at the 65th opener: "nesting deeper than 64 levels; move the inner part into a
  named function or local".
- `unexpected-token` keeps its code; the message names the token and, for these, the repair: a binding
  name in a pattern of an arm with several patterns ("alternatives bind no names; write one arm per
  variant"), `;`
  ("remove the ;: a line break ends the statement"), a comma before `]` `)` `}` ("remove the comma
  before ]"), a comma after a match arm ("remove the comma: one arm per line"), `else` after a NL
  ("put else on the line of the }"), a wrong-case name ("type names start with an upper-case
  letter: write Msg" / "function names start with a lower-case letter: write update").

Check (status 1, at the named token):

- `return-last` at `return`: "return on the last line; drop return: the last line is the value".
  It applies to any `return` in tail position of the body, through the branches of an `if`/`else`
  and the arms of a `match`, with a value or bare.
- `unused-result` at the expression's first token: "the value of NAME is not used; write _ = ...".
- `nothing-to-discard` at `_`: "NAME has no value: drop _ =".
- `missing-value` at the block's `}`: "this block must end in a value of type T"; at a bare `return`
  in a function with a result: "return needs a value of type T".
- `unreachable-code` at the first statement after `return`, `break`, `continue` or a call of
  `unreachable()` (M2-12).
- `break-outside-loop` at `break` or `continue`.
- `if-needs-else` at `if`: "an if used as a value needs an else".
- `duplicate-local` at the name of the second binding (after `let`, `var` or `for`, or the
  parameter name): "NAME is already bound at line N".
- `unknown-name`, `unknown-type` and `unknown-grant` at the name: "NAME is WHAT; did you mean Y?",
  where WHAT is "not defined here", "not a variant", "not a function of the program", "not a type",
  "not a record type" or "not a grant"; without a nearest name (section 1.3) the message ends at WHAT
  and there is no fix.
- `duplicate-name` for a field written twice, at the later name: "NAME is already a field here".
- `wrong-type-arguments` at the type name: "NAME takes N type arguments".
- `assign-to-let` at the name: "NAME is a let (or a parameter, for name, pattern name); declare it
  with var"; a `for` name that walks a place with no slice step, rooted at a `var` or inout parameter, takes
  the walk by position instead (M2-05 §5); otherwise the plain text.
- `bad-assignment-target` at the first token: "only a var local, an inout parameter or their fields
  and items can be assigned"; for a variant's field: "FIELD is a field of the variant V; build V(..)
  and assign SUBJECT", SUBJECT as written (M2-05).
- `cannot-infer` at the expression that needs the type (`None`, `Ok`, `Err`, `[]`, `[:]`, the hole,
  `unreachable`), not at the local. A hole names itself (M2-06 §1.5). Otherwise the text names the
  local when the open value is the whole initializer of a `let` or `var` without a type: "cannot
  infer the type of NAME; write it: let NAME: T = ...", and else that expression: "cannot infer the
  type of None; write it: let x: Option<T> = ...". T is the open type with its known letters filled
  in (M2-22). A call is named by its function or variant name; an operator is never named.
- `wrong-label` at the argument: "write lo: 0" / "x is bare: write 5" / "labels come in declared
  order".
- `not-a-function` at the name: "NAME is a local here, not a function". **amends**: the text is
  "NAME is a TYPE, not a function", TYPE the local's type with the article a or an by the first
  sound of the type name as written (M2-09 §1.7); M2-09 amends this line.
- `wrong-argument-count` at the name (through a value, at the callee expression): "NAME takes 2
  arguments (a, b), got 1" ("takes 1 argument", "takes no arguments"); a fieldless variant called
  with `()`: "Exit has no fields: write Exit"; a record literal missing a field that has no default,
  at the type name: "T needs FIELD: write FIELD: ...".
- `unknown-name` at the field name on a record: "T has no field NAME", with "did you mean Y?" by
  the nearest-name rule of section 1.3.
- `type-mismatch` at the field name when the value is not a record: "T has no fields"; when the
  field is a variant's: "text is a field of the variant Line; match on the value to read it".
- `type-mismatch` at an expression with no value used as one: "NAME has no result" for a call of a
  named function, else expected the wanted type (or "a value"), found "no value". At the value of
  `return value` in a function with no result: "NAME has no result; drop the value or write -> T".
  The text reads "expected `T`, found `U`", the types in backticks as in M1.
- A repair named in a message is part of its text. The machine-readable fix field stays with
  `unknown-name`, `unknown-type` and `unknown-grant`.
- `missing-arm` at `match`: "no arm for variant A; add A => ..." for one variant, "no arm for
  variants A, B; add A => ... and B(_) => ..." for several. Variants come in declaration order and
  one with fields is written with one `_` per field; at most 5 are named, then "and N more". A
  Bool subject: "no arm for false; add false => ..." (or `true`); an Int or String subject: "no arm
  for other Int values; add _ => ..." (String likewise). The kind has no fix field. It is
  reported only when every pattern fits the subject type; otherwise the first pattern that does not
  fit is the match's error (`type-mismatch`). A `_` counts as covering, so `missing-arm` is not added to a
  `wildcard-on-enum`. A match subject is an Int, String, Bool or enum value; any other type, an
  `Effect` included, is `type-mismatch` at the subject, expected "Int, String, Bool or an enum". A
  subject whose type is still free (`match None {..}`, `match Ok(1) {..}`) is `cannot-infer` at the
  open part it needs, and the text names that part.
- `wildcard-on-enum` at the `_` of an arm whose subject is an enum: "_ is for Int, String and
  Bool; name each variant of T".
- `duplicate-arm` at the later pattern: "X is already matched above; drop it". It applies to any
  arm after a `_` and to a `_` after both `true` and `false`. A pattern with the wrong number of
  fields is `wrong-argument-count` at the variant name in the pattern, whether or not an earlier arm
  matched it.
- `missing-value` at the first token of a single-line arm (its pattern) that gives no value where one is needed: "this arm must give
  a value".
- `assign-to-let` on a pattern name: "NAME is a pattern name; declare it with var". Passing one
  with `&` is `bad-inout-target`: "NAME is a pattern name; it is a copy".
- Branch types do not depend on order. In an `if`/`else`, a `match` or a list literal the first
  branch (arm, item) that carries its own type gives the expected type of every other one, and the
  type recorded for each branch is the concrete one (`None` beside `Some(n)` is `Option<Int>`).
  When every branch is open, the branches are joined into one type (`[None, None, Some([])]` is
  `List<Option<List<T>>>`); branches that cannot be joined are `type-mismatch`, and a joined type
  that is still open is `cannot-infer` at the open part, with the joined type in the text.
  `Ok` and `Err` in different branches do not join; that is `cannot-infer` (M2-12 §1.2).
  `cannot-infer` reports at the expression inside parentheses. A bare hole, `None`, `[]`, `[:]` and `unreachable()`
  are open; `Ok(v)` and `Err(e)` are open too, since each leaves the other letter free (M2-12
  §1.2).
- `return ??x` in a function with no result is `type-mismatch` at the value, with the text above
  without the type: "NAME has no result; drop the value" (a hole has no type to write).
