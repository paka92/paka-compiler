# M2-06 · Traps, holes and what an example means: decision

Base: the recorded M2-06 page in DECISIONS.md, written out as one mechanism (a trap is a status
return from a numbered trap site) with the report text fixed byte for byte, the limits, the hole
rules, the example rules and the `paka examples` output. All five recorded picks stand. Three
settled lines are made exact where they were loose, marked **fixes**: the two sides of a failed
comparison print on two lines, not one; the call-chain line is printed the same way by every back
end instead of being left to differ; `stack` and `memory` reports carry no help lines. One M2-02
line is corrected: the M1 `parse/example` case stays a reject, because its body ends in a `Msg`.

The one idea under everything: a trap never faults, never signals and never panics. Every back end
numbers the places a program can trap, keeps one record, returns a status up the call chain and
prints the report once at the top. That is what makes "the same program gives the same result in
dev and release" (paper lines 156 to 161) hold for stops (line 63) without the optimiser keeping
frames.

## 1. Resolutions, point by point

### 1.1 The eight kinds and what raises each

| kind | raised by | position |
|---|---|---|
| `overflow` | an Int result outside the Int range: `+ - * / %`, the `op=` forms, unary `-`, `MIN / -1` (M2-03); `abs` of the smallest Int (M2-14). The wrapping forms never raise it | the operator; `abs` |
| `divide_by_zero` | Int `/`, `%`, `/=`, `%=` with a right side of 0 (M2-03). Float never traps | the operator |
| `out_of_bounds` | an index or slice outside a List or String, a slice with `start > end`; a missing Map key at `[` (read, `op=`, `&m[k]`, or any step but the last of an assignment); `pop` on an empty List; a bad position in `code_at`, `insert`, `remove_at`, `swap`; a count below zero in `repeat` or `list_of`; a shift count outside 0 to 63; `fixed` digits outside 0 to 20 (M2-03, M2-12, M2-14) | the `[`, also inside `&xs[i]`; the operator for a shift; the function name otherwise |
| `bad_conversion` | `to_int` of NaN, an infinity or a Float outside the Int range; `from_code` of a number that is no code point (M2-14) | the function name |
| `assert` | `assert(false)`; `unreachable()` reached (M2-12); the UI example failures M5-06 lists | the function name |
| `hole` | `??name` reached anywhere but a UI element position (line 75). Carries the name | the `??` |
| `stack` | the 10,001st nested call; a value nested too deep to copy or compare (M2-05) | the called function's name at the call site; the operator |
| `memory` | a List, Map or String that would pass 16,777,216 items, entries or bytes; an allocation the host refuses (M4-25, M6-11) | the operator or function name that grows the value |

`stale_handle` (line 63) is reserved: nothing can raise it, because there are no pools (M2-01).
Later decisions may add a kind for a new built-in; none may rename or merge one.

The three stop lines of M2-15 (`effect X refused`, `effect X failed`, `ended without Exit`) are
stops, not traps: one line, status 3, no kind, no position. The usage line of M2-15 is status 2.

A built-in's own check is reported at the user's call, at the name token. User code that a
built-in calls back (`sort_by`'s function) traps where it traps, like any user code.

### 1.2 The trap report, byte for byte

A headless program that traps writes this to standard error and ends with status 3:

```
<app>: trap <kind> at <file>:<line>:<col>
  <detail>
  in <frame>, called from <frame>, called from <frame>
```

- `<app>` is the name after `app`, as in M1's stop lines. `<file>` is the file's own name without
  its directory. `<line>:<col>` are 1-based; columns count bytes (M1 spec §2), the position is the
  start of the token §1.1 names.
- The detail line is present for every kind but `assert`, `stack` and `memory`, and reads, with
  values in the value text form of M2-09 and M2-14:
  `overflow`: `9223372036854775807 + 1`, `-(-9223372036854775808)`, `abs(-9223372036854775808)`,
  the `op=` forms as their operator;
  `divide_by_zero`: `7 / 0`, `7 % 0`;
  `out_of_bounds`: `index 5, length 5`; `slice 2..<9, length 3`; `key "x"`; `pop on an empty
  List`; `count -1`; `shift 64`; `digits 21`;
  `bad_conversion`: `to_int(NaN)`, `from_code(1114112)`;
  `hole`: `??scan`.
  A detail line longer than 256 bytes is cut at 256 bytes.
- The chain line is present whenever the detail line is. It names the function frames from the
  innermost out: the function the trap happened in, then each caller, the outermost being what the
  runtime called (`update`, a `then:` or `or:` function, or `example NAME`). A trap directly in the
  handler prints `  in update`. At most eight names are printed; when there were more the line
  ends in `, ...`. Built-ins are not frames.
- `stack` and `memory` print the first line only.
- Standard output written before the trap stays written. Nothing else is written to standard
  error. The trapping handler's effects are not performed (M2-15).

Meaning, compared by every harness (M2-41, M4-40, M6-06): the stream, status 3, the first line's
shape, the kind, the position, and for `hole` the name. For `stack` and `memory` only the kind and
the status: where they strike differs by mode (line 161). Not meaning: the help lines. Their text
is still fixed above, so a conformance case can hold the whole standard error by hand and every
back end prints the same bytes; the cross-back-end harnesses compare the meaning fields only.

```
avg: trap divide_by_zero at avg.paka:14:11
  0 / 0
  in mean, called from update
```

M4-03's `trap` object carries kind, line, column and the hole name (null otherwise); M4-03 rules
the key names.

### 1.3 Which trap wins

The first check that fails in M2-03 §2.8's order, which is strictly left to right. Nothing after
it is evaluated, so there is never a second trap to choose from. The points that needed naming:

- Arguments are evaluated left to right, then the `&place` bounds checks (M2-05), then the depth
  check, then the body. `f(xs[9], 1 / 0)` traps `out_of_bounds`; `deep(1 / 0)` traps
  `divide_by_zero` even at the depth limit.
- `xs[9] = 1 / 0` traps `divide_by_zero`: the right side runs before the store's check.
- `false && xs[9] == 0` traps nothing; `&&` and `||` evaluate the right side only when needed.
- A `memory` trap fires at the operation that would cross the cap, before any part of the result
  exists.

What the optimiser owes (M6-01, M6-19). Inside a handler nothing is observable but the result or
the trap: effects are values performed after the handler returns, and a trapped handler performs
none (M2-15). So release code has exactly two obligations: when no path traps, the result is the
one the order gives; when some path traps, the kind and site recorded are those of the first trap
in that order. A check proved never to fire may go. A check may be hoisted or merged only if, when
it fires, the code falls back to an exact path that reruns the operations in order with per-site
checks and lets that path record the site. Each trap site returns its own constant, so sites that
differ cannot be merged by accident. `stack` and `memory` are exempt: the optimiser may inline
and reorder freely, since only the kind is compared.

### 1.4 Limits

Three numbers, all the toolchain's own, none meaning. A program may not depend on them and no
conformance case tests them (M2-41); each has one defined outcome and a unit test in M2-26.

- **Call depth: 10,000.** The handler call or the example body is depth 1; each call of a
  user-defined function adds one; built-ins add nothing, a user function called back from a
  built-in counts. The call that would make depth 10,001 traps `stack` at the callee's name token
  at the call site, after the arguments are evaluated and before the body runs. The interpreter
  counts calls and runs on a thread whose stack holds 10,000 of its own frames (M2-26). Dev native
  and release only promise a clean `stack` trap, never a signal: M4-05 and M6-16 choose between
  the same counter and a stack-position check. The interpreter's number sits far above M3's
  tasks, which recurse about 200 deep.
- **Collection size: 16,777,216.** Items of a List, entries of a Map, bytes of a String. Checked
  before every growth (`append`, `insert`, `+` on String, `repeat`, `list_of`, interpolation, a
  slice that copies); past it, `memory` at that operation. Checking before the growth is what lets
  the record be written with no new allocation.
- **Host refusal.** In dev native and release an allocation the host refuses traps `memory` at the
  operation (M4-25, M6-11). The interpreter promises nothing about it: the cap is meant to keep it
  out of reach, and a refusal under the cap ends the process as the host does. Accepted gap.
- **No step or time limit.** An endless loop is a legal program that never ends; whoever started
  it stops it (the M3 sandbox, M4-03's `limit_ms`). Not a trap, not an example status.

### 1.5 Holes

**Written.** `??name`: `??` directly followed by a lower-case name, one token (M2-02, M2-12). The
name is required and need not be unique. A hole is a primary expression or a statement on its own
line. There is no `??name: T` form and no hole for a pattern, a type or a definition.

**Typed.** From its position only, through the expected-type path M2-12 fixed for `None`, `Ok` and
`Err`: an argument takes the parameter's type; a field in a record or variant literal; the right
side of `let x: T =`, `var x: T =` or an assignment to a place; the last expression of a function
body, of an example (`Bool`) or a `return`; a condition (`Bool`); an operand of `&&`, `||` or `!`
(`Bool`, so `??a && ??b` is accepted); either side of a range, from the other side (`??lo..<n` is
Int); an item of a list or map literal
whose type is known; an `if` branch, `match` arm or block end that itself has an expected type;
and the other side of a two-sided operator or comparison when that side's type is known without
the hole (`s.count + ??delta` is Int). A statement hole has no type and needs none. Every other
position is `cannot-infer` at the `??` (M2-02 §1.8), message
`cannot infer the type of ??NAME; write it: let NAME: T = ??NAME`; so is a hole as the base of a
field read, an index, a call or `?`, and as the first argument of a built-in. No new code: this is the error
the recorded pick asked for.

**Checked.** `paka check` accepts a program with holes and exits 0. When there is no error it
lists each hole as a note, together with warnings, in position order, on standard error, in the
form M2-04 gives every diagnostic (the one-line form, then the field lines that are present):

```
main.paka:4:33: note[hole]: ??rest takes Effect<Msg>
  definition: update
  bytes: 93..99
  text: "??rest"
```

A statement hole reads `??NAME takes no value`. With `--json` each note is one object with the
same keys as an error, `"kind"` being `hole`. A note never changes the exit status, so M3 judges
by `paka check` alone and a hole costs no counted edit. Like warnings, notes are printed by
`paka check` only.

**Run.** `paka run` and `paka examples` run the program. Reaching a hole traps `hole` at the `??`
with the detail line `??NAME`; in an example the status is `unfinished` (§1.6). A hole never
reached changes nothing: a program with a hole in a cold branch runs to `Exit` with status 0. The
one exception is the paper's: a hole in a UI element position draws a placeholder (line 75),
which is M5-06's and happens only in a view.

**Built.** `paka build` refuses a program with a hole (line 308): one line per hole, in position
order, exit 1, nothing written. This is the one command that prints more than one diagnostic.

```
main.paka:4:33: error[hole-in-build]: a release build has no holes; finish ??rest
```

### 1.6 Examples

**What one is.** `example NAME BLOCK` (M2-02's grammar), a top-level definition. It is checked
exactly as a function with no parameters and result `Bool` that nothing can call: statements, then
one `Bool` expression; `return` allowed; `?` not allowed (M2-12): `type-mismatch` at the `?`,
"an example has no ?; match it". Its name is in the one pool of
definition names (`duplicate-name` on a clash, M2-02) but not in scope in any expression: using it
there is `unknown-name` at the name. A body whose last expression is not `Bool` is `type-mismatch`
at that expression's first token with `expected: Bool`; a body that ends in a statement or is
empty is `missing-value` at the `}`. Both codes exist; the example brings none.

**What it may do.** Call functions, build values, call an update on a `var` state and look at the
state, compare effect lists with `==` (M2-15), drop a result with `_ =`. It takes no arguments,
has no grants and performs no effect: nothing in it can hand an effect list to the runtime. It
shares nothing with other examples. `paka examples` runs them in name order; a program may not
rely on that.

**When it runs.** Only under `paka examples FILE`. `paka check`, `paka run` and `paka build` check
examples like every definition and never run them; a wrong example therefore stops the whole
program at check time. `paka build` drops them (M7-03 adds the switch that keeps them). Each
example starts at depth 1 with a fresh world: no app, no state, no arguments.

**Statuses.** Four, computed by the toolchain only (line 185):

| status | when |
|---|---|
| `pass` | the body finished and its Bool is `true` |
| `fail` | the body finished and its Bool is `false` |
| `trapped` | the first trap in the body is any kind but `hole` |
| `unfinished` | the first trap in the body is `hole` (line 185) |

A false `assert` inside the body is `trapped`, not `fail`: `fail` is only the final Bool. One
example's trap does not stop the others. An example that never ends has no status and
`paka examples` never returns (§1.4).

**Output.** On standard output, one entry per example in byte order of name, nothing else; then
exit 0 when every example passed (also when there are none), 3 when any is `fail`, `trapped` or
`unfinished`. Standard error is empty. When the program does not check, the errors are printed as
`paka run` prints them (one line, no notes), exit 1, and no example runs. Usage is status 2, an
internal error 4, as for every command.

```
NAME pass
NAME fail at FILE:LINE:COL
  left: VALUE
  right: VALUE
NAME trapped at FILE:LINE:COL
  trap KIND
  DETAIL
  in FRAME, called from example NAME
NAME unfinished at FILE:LINE:COL
  ??NAME
  in FRAME, called from example NAME
```

- `fail`: the reported expression is the body's final expression; when that is an `&&` chain, it
  is the operand evaluated last, which is the one that was `false`. When the reported expression
  is a comparison (`==`, `!=`, `<`, `<=`, `>`, `>=`) the position is its operator and the two
  help lines show both sides in the value text form (M2-09, M2-14); otherwise the position is its
  first token and there are no help lines. **fixes**: two lines, not `left: -1  right: 0` on one,
  so a value that holds spaces or runs long stays readable and parseable.
- `trapped` and `unfinished`: the trap's position, then the trap's help lines exactly as §1.2
  prints them for `paka run`, with `trap KIND` first for `trapped`. A `stack` or `memory` trap
  shows its position and no help lines; the position is not compared across back ends.

### 1.7 Exit statuses, all commands

| status | `paka check` | `paka run` | `paka examples` | `paka build` |
|---|---|---|---|---|
| 0 | checks (notes and warnings may be printed) | `Exit` performed | every example passed | executable written |
| 1 | one error | one error | one error | one error, or one line per hole |
| 2 | bad usage | bad usage, or the app's usage line | bad usage | bad usage |
| 3 | — | trap or stop | some example did not pass | — |
| 4 | internal error | internal error | internal error | internal error |

No status is new; the numbers are M1's and M2-15's.

## 2. Grammar

Nothing beyond M2-02 §2: `example_def = "example" LOWER block`; `??` LOWER is one token and a
primary expression; a hole or `unreachable()` may stand alone as a statement (M2-02 §1.4, M2-12).

## 3. Implementation rule: interpreter and native code

**Trap sites (M2-23).** Lowering numbers every node that can trap and builds one table per
program: site number, file, line, column, and for `hole` the name; the kind travels with the
trap, since one site may raise several kinds. A built-in call takes the
site of its name token; `&xs[i]` takes the site of its `[`. The interpreter keeps the table in
memory; native back ends emit it as read-only data.

**One record, filled at the site, printed at the top.** The trap entry (M2-03 §2.9's runtime
routine) takes the site and the operand values the detail line needs. It writes the kind, the site
and the formatted detail into one static record, with no allocation, and returns. The function
then returns the trap status, and each caller that sees it appends its own name to the record's
frame list (eight slots and an overflow flag) and returns the status at once. The top (`paka run`'s
loop, `paka_rt1_run`, the `paka examples` driver) reads the record: the run loop prints §1.2's
report to standard error and exits 3; the examples driver prints §1.6's entry to standard output.
Because the frame list is appended while unwinding, inlining keeps it exact: the code that appends
moves with the body. A memory trap can be reported with no free heap: the record and the table
are static.

**Interpreter (M2-26).** Every evaluate function returns `Result<Value, Trap>` and `?` propagates
it; a call frame maps the error to append its name. A call-depth counter; a size check before
every growth; copy and compare count their depth on the same counter (M2-05); the run loop and the
examples driver own the printing.

**Dev native (M4-05, M4-27, M4-30).** Every compiled function returns a status: 0 finished, 1
trapped, through the convention M4-05 fixes; the result travels through the out pointer as in M1.
On a trap the code calls the trap entry, appends its name and returns 1; every call site tests the
status. Any status but 0 or 1 at the top stays an internal error (status 4), and `catch_unwind`
stays for real bugs only. Renaming the entry on this ABI change (`paka_rt2_run`) is M4-05's. A
hole compiles to its site: the trap entry, then `ret 1`; no value is ever made for it. An example
compiles to a status function with one `Bool` out; the driver maps status 0 and the Bool to
`pass` or `fail`, status 1 and the record's kind to `trapped` or `unfinished`.

**Release (M6).** The same convention and the same record. No `llvm.trap`, no `unreachable`, no
signal handler, no instruction that can fault (M6-01's allow-list, M4-26's banned-operation scan).
§1.3's two obligations bound every hoist, merge and removal.

## 4. M1 cases that stop holding

- `lex/hole` was deleted by M2-07 under M2-02 §4. Its program returns as an M2-41 case with the
  exact expectations of §1.5's samples: `paka check` prints the one note above and exits 0;
  `paka run` writes nothing to standard output, the report `light: trap hole at main.paka:4:33` /
  `  ??rest` / `  in update` to standard error, status 3, because the list is built before any
  `Print` is performed; `paka build` prints the one `hole-in-build` line and exits 1.
- `parse/example` parses (M2-02) but its body is `Start`, a `Msg`, so it stays a reject with the
  new line `main.paka:4:3: error[type-mismatch]` and status 1. M2-02 §4's "runs; `paka run` does
  not run examples" is corrected: that expectation needs a body ending in a Bool and belongs to an
  M2-41 case. `run/string_symbols` holds `??rest` inside a string and is untouched.

No other M1 case can reach a trap, a hole or an example.

## 5. New diagnostic codes

Note (printed by `paka check` only, when there is no error; status unchanged):

- `hole` at the `??`: "??NAME takes T" / "??NAME takes no value". Carries no types and no fix.

Build (status 1, `paka build` only, every hole in position order):

- `hole-in-build` at the `??`: "a release build has no holes; finish ??NAME". No types, no fix.

Kept and reused: `cannot-infer` (a hole with no typed position, M2-02 §1.8), `type-mismatch` and
`missing-value` (an example body not ending in a Bool), `duplicate-name` (two definitions of one
name, examples included), `unknown-name` (an example's name in an expression),
`wrong-argument-count` (`assert` with a message argument). The diagnostic line gains the level
`note` beside `error` and `warning`: `path:line:col: note[code]: message`. `unsupported-hole` and
`unsupported-example` are already retired (M2-02 §5).

## 6. Samples

The paper's counter under the rules, with one example per status:

```
type Counter { count: Int = 0 }
enum Msg { Inc, Dec }

fn dec(n: Int) -> Int { if n > 0 { n - 1 } else { 0 } }

fn update(s: inout Counter, m: Msg) -> List<Effect<Msg>> {
  s.count = match m {
    Inc => s.count + ??step
    Dec => dec(s.count)
  }
  []
}

example dec_stops_at_zero {
  var s = Counter {}
  _ = update(&s, Dec)
  s.count == 0
}

example dec_from_two {
  var s = Counter { count: 2 }
  _ = update(&s, Dec)
  s.count == 2
}

example inc_once {
  var s = Counter {}
  _ = update(&s, Inc)
  s.count == 1
}

example first_of_none {
  let xs: List<Int> = []
  xs[0] == 0
}
```

```
$ paka check main.paka          # exit 0; the field lines of M2-04 follow the note
main.paka:8:22: note[hole]: ??step takes Int
$ paka examples main.paka       # exit 3; standard error empty
dec_from_two fail at main.paka:23:11
  left: 1
  right: 2
dec_stops_at_zero pass
first_of_none trapped at main.paka:34:5
  trap out_of_bounds
  index 0, length 0
  in example first_of_none
inc_once unfinished at main.paka:8:22
  ??step
  in update, called from example inc_once
$ paka build main.paka -o counter   # exit 1
main.paka:8:22: error[hole-in-build]: a release build has no holes; finish ??step
```

Fix `??step` to `1` and `dec_from_two`'s claim to `1`: four `pass` lines, exit 0.

First trap wins, a built-in's check at the call, depth, assertion:

```
xs[5] + (1 / 0)        // xs has 3 items: out_of_bounds at the [, detail "index 5, length 3"
(1 / 0) + xs[5]        // divide_by_zero at the /, detail "1 / 0"
f(xs[5], 1 / 0)        // out_of_bounds: arguments left to right
xs[5] = 1 / 0          // divide_by_zero: the right side runs first
pop(&empty)            // out_of_bounds at pop, detail "pop on an empty List"
to_int(0.0 / 0.0)      // bad_conversion at to_int, detail "to_int(NaN)"
assert(len(xs) > 0)    // xs empty: assert at assert, no detail line
fn down(n: Int) -> Int { 1 + down(n + 1) }
down(0)                // stack at the inner down, first line only; kind and status compared
let n = ??n            // check error cannot-infer at the ??
let n: Int = ??n       // accepted; note[hole]: ??n takes Int; reaching it traps hole
if false { ??later }   // accepted; runs clean; paka build refuses
example bad { 1 + 1 }  // check error type-mismatch at 1, expected Bool, found Int
```
