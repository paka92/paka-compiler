# M6-23 · Whether release IR may promise that call arguments do not overlap

Status: draft, awaiting the owner's approval.

Base: GENESIS 3.2 ("the compiler therefore knows that `inout` data overlaps nothing else"),
M2-05 §3 ("Release mode may mark inout parameters `noalias` on the strength of Rule A alone; that is
M6-23's signature to give") and M6-01 §1.1, which keeps every fact the checker proves out of the IR
until a signed decision lets it in. `noalias` is on M6-01's never list until this record signs it.
The evidence is M6-22's run (docs/results/M6-22.md). This is the one evidence report the task's note
asks for; a reviewer told to break it comes next, then the owner.

The question: may `paka build` write LLVM's `noalias` on function parameters, so that a wrong
checker answer becomes silent undefined behaviour instead of a slow loop?

## 1. Points

**1.1 Promise `noalias` on the pointer parameters of user functions, inout and read-only.** A
parameter that the emitter passes as a pointer (a read-only List, String, Map or record, and an
inout of any type) gets `noalias` in the `define` line of a function compiled from a user `fn`. M6-24 then
emits it, with its linter rule, as signed in 1.3.

```
define internal i32 @p_sweep(ptr noalias %a0, ptr noalias %a1, i64 %a2)
;                            src: List<Float>  dst: inout List<Float>
```

- Why read-only too: LLVM's `noalias` only forbids a write, during the call, to memory reached
  through the parameter by a pointer not derived from it. During a call the callee writes the
  caller's storage only through its own inout parameters (no globals, function values carry no data,
  borrows cannot be stored), and Rule A refuses every call where an inout overlaps another argument.
  So the one fact both rest on is Rule A, and M6-22's detector checks exactly that fact: an inout
  argument sharing storage with any other argument at call start. Two read-only arguments may share
  storage; with no write, `noalias` holds.
- Why the gain needs both: stencil runs 1.75 times faster with `dst` alone marked and 4.4 times
  faster with both, where it matches Rust and C++ (section 3).
- Alternatives:
  - never promise (no risk; stencil stays 4.4 times behind Rust, and GENESIS 3.2's sentence is not
    kept in release);
  - inout parameters only, as M6-24 is written (same evidence and same risk, a third of the gain on
    stencil);
  - only where a function has one pointer parameter (true by construction under M6-01 §1.1, since
    nothing else can reach the storage; no checker fact is used, but stencil, the one measured case
    that gains, has two and keeps its slow loop).

**1.2 Where it is written, and where never.** Only on `ptr` parameters of functions compiled from a
user `fn`, never on `%out` (the result slot), on `main` or `p_update`'s entry, on runtime
declarations, on emitter helper functions, on call sites or on returned values. Int, Float, Bool and
function values are passed by value and carry nothing.

- What it covers: only the words the parameter points at (a List's pointer, length and capacity).
  A pointer loaded from them, such as a List's item block, is not derived from the parameter in
  LLVM's sense, so the vectorizer still compares item blocks at run time before a vector loop. That
  check runs once per loop entry; stencil keeps it and still matches Rust (section 3). Removing it
  would need scoped alias metadata, which M6-01 bans and this record does not ask for.

**1.3 Signed means tied to the checker that was tested.** The emitter holds one constant, the
SHA-256 of paka/src/body/own.rs (Rules A to D and `RULE_A_OFF`), and writes `noalias` only through
one helper. A normal test hashes the file and fails when it differs, with the fix in its message:
rerun M6-22's million-program run, add its numbers to docs/results/M6-22.md and update the constant
in the same pull request. Any change to the rules, even a rename, therefore costs one five-minute
run.

```
// The overlap rules M6-22's run tested (M6-23 1.3); a changed file must be run again.
const OVERLAP_RULES_SIGNED: &str = "sha256:...";
```

- Alternatives: sign once and trust later edits to review (a later change to the rules weakens a
  promise nobody looks at again) · sign the whole compiler version (every unrelated change forces
  a rerun).
- Limit: the hash covers the rule file, not the code that forms places for it (the parser, the
  core form). A change there is covered by the normal tests, three-mode conformance and the fuzz,
  not by a rerun.

**1.4 If a hole appears later.** A hole is an accepted program whose arguments overlap at run time,
found by anything: the detector, a divergence between back ends, a report.

1. The same day: the helper stops writing `noalias` (one line) and that ships alone; release is
   then correct and slower, as today.
2. The checker is fixed, the case goes into tests/conformance/ownership, and the generator learns
   the shape if it could not make it.
3. The million-program run is repeated and recorded, the constant is updated, and the helper writes
   `noalias` again. The owner is told; a new approval is needed only if the fix changes what M2-05
   accepts.

## 2. Evidence and its limits

| What | Result |
|---|---|
| Million-program run (M6-22) | 1,000,000 programs; 96,617 refused, all `inout-overlap`; 903,383 accepted; 140,910 calls passing an inout with another part of the same local; 0 flagged |
| Same seeds, Rule A off | the detector flags overlaps, so the run can see a hole |
| Hand cases | every rule and sample of M2-05 in tests/conformance/ownership, seven added by M6-22 |
| Holes found so far | one, by a hand case: `put(&m[k], &k)` (a String key inside an `&` place's index, Rule B); fixed before this record |

What the run does not cover:

- **Calls only.** The detector watches calls to user functions. Operators, list and map literals,
  records and interpolation (Rule C) are covered by hand cases only. They matter less here, since
  `noalias` is written on user function parameters only; a built-in such as `append` is a runtime
  call or inline IR and carries no promise.
- **The interpreter's storage, not release pointers.** The detector compares places in the
  interpreter. Sharing that only the release back end makes (a `for` name borrowing the walked List,
  constant item blocks copied before their first write) is outside it; §1.7's freeze and M6-01's
  copy rule keep those apart, and only three-mode conformance and the fuzz test them in release.
- **No pools or handles.** They do not exist (M2-10, M2-14). If they are ever added, this record is
  signed again before they reach release.
- **Generated shapes.** The generator draws fields, List items, slices and Map entries beside an `&`
  place. A shape it cannot make is covered only by hand cases; the one hole found so far was of
  that kind.

The risk: a wrong fact does not trap. LLVM may reorder or vectorize a load past a store, and the
program prints a wrong number in release only, often only at `-O3` and only for some inputs. What
would catch it: three-mode conformance, which compares release with the interpreter on every case;
M6-21's release-only generator; and M6-25's 24-hour fuzz, which runs after M6-24 with the promise
on. None of them proves absence; together with the detector run they are the evidence there is.

## 3. Measured gain

Stencil from bench/programs, its release IR from `paka build` with `noalias` added by hand to
`sweep`'s parameters, then the same `clang -O3` and link. One machine, best of two runs; all print
the same checksum.

| stencil | Time | Inner loop at `-O3` |
|---|---|---|
| as today | 5.0 s | scalar; `dst`'s length and item pointer read again after every store |
| `dst` marked | 2.8 s | `dst`'s words kept in registers; `src`'s still read again |
| `src` and `dst` marked | 1.15 s | vectorized, two at a time; bounds checks folded into the loop's count and left only in the scalar remainder; one item block comparison per row |
| Rust, C++ | 1.03 s, 1.06 s | |

- M6-19 noted stencil keeps its trap branch because `dst`'s lengths are reloaded. With both marked
  they are not, and the bounds checks leave the loop body.
- saxpy_dot and nbody show no change: clang inlines their kernels into `update`, where the Lists are
  locals and LLVM already sees they are apart. The promise pays only for a function that is not
  inlined (several callers, recursion, size). A hand-written `scale(dst: inout List<Float>, a)`
  kept out of line ran 2.1 times faster marked, its bounds check gone and its loop vectorized.

## 4. Rules that follow

- The promise is one M6-01 row: `noalias` on a user function's `ptr` parameter, proof this record
  and the signed hash. M6-05's linter allows the word only in a `define` line of a user function, on
  a parameter, and nowhere else.
- The hash test of 1.3 runs with the normal tests; the million-program run stays an ignored test
  run by hand when the hash changes.
- The helper of 1.3 is the only writer, so 1.4's first step stays a one-line change.

## 5. What this changes in TASKS.md

- M6-24: the promise covers read-only pointer parameters as well as inout ones, at 1.2's places,
  with 1.3's hash test. Its done-when 'a two-array kernel vectorizes without a run-time overlap
  check' becomes 'stencil's `sweep` vectorizes with no bounds check in its loop body'; the item
  block comparison LLVM adds (1.2) stays.
- M6-01's never list: `noalias` moves to the table as the row in section 4.
- M6-25: runs with the promise on, as its `needs` already says.

## 6. Recommendation

Pick 1.1 as written: `noalias` on the inout and read-only pointer parameters of user functions,
tied to the tested rule file by its hash, with 1.4's plan. Both rest on the one fact the million
programs tested, and only both together bring stencil level with Rust; the inout-only form takes the
same risk for a third of the gain.

Owner must weigh:

- This widens M6-24 beyond inout parameters; the evidence is the same, the gain is not.
- The evidence is a model check in the interpreter plus hand cases; it cannot prove no hole is left,
  and one hole was found by hand during M6-22.
- A future hole means wrong results in release, not a trap, until it is found.
