# Paka M1 subset

The language of milestone 1: exactly what `examples/light.paka` needs. Everything else is rejected
with a named code. Tasks M1-03 and M1-07 to M1-20 are built from this text and from the case folders
under `tests/cases-pending/`.

Status: provisional. The start, end and grant rules hold until M2-15 rules; the rest holds until the
M2 language reference replaces this file. Three rulings come from DECISIONS.md (M1-06.1 to M1-06.3)
and are marked **decided**. What this spec had to settle on its own is listed in section 16.

```
enum Msg { Start }

fn update(m: Msg) -> List<Effect<Msg>> {
  [Print("let there be light"), Exit]
}

app light {
  start:  Start
  update: update
  grants: [Console]
}
```

## 1. Commands, streams and statuses

| Command | Does |
|---|---|
| `paka run <file>` | reads, checks and interprets the program |
| `paka build <file> -o <output>` | reads and checks the program, then writes a native executable |

Both commands accept and reject the same programs with the same diagnostic. An executable written by
`paka build` gives the same standard output, standard error and status as `paka run` on its source.

| Status | Meaning |
|---|---|
| 0 | the program ended normally (section 9.3); for `paka build`, the executable was written |
| 1 | a diagnostic was reported: the program was rejected or the tool failed |
| 2 | bad usage of the `paka` command (owned by M1-03) |
| 3 | the program stopped on a run-time error (sections 9.4 and 9.5) |

A diagnostic is one line on standard error, ending with a newline:

```
path:line:col: error[code]: message
path: error[code]: message
```

- `path` is the file argument exactly as given on the command line.
- The second form is used only by the codes marked "no position" in section 10.
- `message` is at least one byte and holds no newline. Its wording is not fixed.
- A run reports at most one diagnostic, then exits with status 1. Standard output stays empty and the
  program does not start. `paka build` does not start clang.
- There are no warnings. An accepted program makes the tool write nothing of its own to either stream.

The program never reads standard input, command-line arguments or the environment.

## 2. Source text and positions

- A program is one file. Its bytes are read as they are; there is no decoding step.
- Allowed bytes: `0x20` to `0x7E` and line feed `0x0A`. Any other byte anywhere, tab and carriage
  return included, is `invalid-byte` at that byte.
- A line ends at a line feed. Lines are numbered from 1.
- Columns are numbered from 1 and count bytes: the column of a byte is 1 plus the number of bytes
  between the start of its line and it. Every byte before a reported position is ASCII, so this is
  also the character count.
- The position of a token is the position of its first byte.
- The end of the file is a token named END. Its position is the line and column the next byte would
  have: after a final line feed that is column 1 of the following line. In an empty file it is 1:1.
- A final line feed is optional.

## 3. Tokens

Space and line feed separate tokens and mean nothing else. A line feed ends nothing.

| Token | Spelling |
|---|---|
| keyword | `enum` `fn` `app` `type` `view` `example` `match` |
| UPPER | `[A-Z][A-Za-z0-9_]*` |
| LOWER | `[a-z][A-Za-z0-9_]*`, when it is not a keyword |
| STRING | `"`, then zero or more bytes from `0x20` to `0x7E` other than `"` `\` `{` `}`, then `"` |
| punctuation | `{` `}` `(` `)` `[` `]` `<` `>` `:` `,` `->` |
| END | end of file |

- A name takes the longest run of letters, digits and underscores. `enumerate` and `Match` are names.
- `>>` is two `>` tokens. There is no `>>` token.
- The value of a STRING is the bytes between its quotes, unchanged. There are no escapes.
- `type`, `view`, `example` and `match` are keywords only so that they can be rejected by name.

At the start of a token the lexer looks at the next byte, and one more where noted:

| Next bytes | Result |
|---|---|
| letter | name or keyword |
| `"` | string, scanned as below |
| one of `{ } ( ) [ ] < > : ,` | that token |
| `->` | that token |
| `//` | `unsupported-comment` at the first `/` |
| `??` | `unsupported-hole` at the first `?` |
| digit | `unsupported-integer` at the digit |
| a byte outside `0x20`–`0x7E` other than line feed | `invalid-byte` at the byte |
| anything else (`-`, `/`, `?`, `_`, `=`, `;`, `.`, `&`, ...) | `unexpected-character` at the byte |

After the opening quote of a string the lexer reads byte by byte. The first of these that it meets
decides:

| Byte | Result |
|---|---|
| `"` | the string ends |
| line feed, or end of file | `unterminated-string` at the opening quote |
| `\` | `unsupported-escape` at the `\` |
| `{` or `}` | `unsupported-interpolation` at that byte |
| a byte outside `0x20`–`0x7E` | `invalid-byte` at that byte |

Lexing stops at the first lexical error. Section 5 says when it is the one reported.

## 4. Grammar

Quoted words are keywords or punctuation. `start`, `update` and `grants` are LOWER tokens with that
text; they are not keywords and may be used as names elsewhere.

```
program  = { enum_def | fn_def | app_def } END
enum_def = "enum" UPPER "{" UPPER { "," UPPER } "}"
fn_def   = "fn" LOWER "(" LOWER ":" type ")" "->" type "{" expr "}"
type     = UPPER [ "<" type ">" ]
expr     = STRING | list | UPPER [ "(" expr { "," expr } ")" ]
list     = "[" [ expr { "," expr } ] "]"
app_def  = "app" LOWER "{" { entry } "}"
entry    = start ":" UPPER
         | update ":" LOWER
         | grants ":" "[" [ UPPER { "," UPPER } ] "]"
```

- Definitions may come in any order and any number. Entries of an app may come in any order.
- A function has exactly one parameter and a result type. Its body is exactly one expression.
- An enum has one or more variants. Variants carry no payload.
- There are no trailing commas, and a call has at least one argument: `Exit()` is not in the grammar.

## 5. Syntax diagnostics

The tokens are matched against the grammar from the first one on. The offending token is the first
token T such that the tokens before T, followed by T, are not the start of any program of the grammar.
A lexical error counts as a token that fits nowhere. The diagnostic is chosen by the first line of
this table that applies, and its position is that of T (for a lexical error, the position section 3
gives):

| Offending token | Code |
|---|---|
| a lexical error | the lexical code of section 3 |
| keyword `type`, `view`, `example` or `match` | `unsupported-type`, `unsupported-view`, `unsupported-example`, `unsupported-match` |
| a LOWER where a call argument starts (right after the `(` or a `,` of a call), when the next token is `:` | `unsupported-labelled-argument` |
| a LOWER where an app entry starts, with text other than `start`, `update`, `grants` | `unsupported-app-entry` |
| anything else, END included | `unexpected-token` |

So a syntax error earlier in the file wins over a lexical error later in it, and the other way round.
Rules about letter case need no code of their own: `enum msg` is `unexpected-token` at `msg`.

## 6. Names

Built-in names:

| Name | Kind | Detail |
|---|---|---|
| `String` | type | no type argument |
| `List` | type | one type argument |
| `Effect` | type | one type argument |
| `Print` | effect | one argument of type `String`; needs grant `Console` |
| `Exit` | effect | no argument; needs no grant |
| `Console` | grant | |

- Enum, function and app names, every variant name and the six built-in names share one pool. A name
  may be declared once in it. A second declaration is `duplicate-name` at the later name; the
  built-ins count as declared before the file.
- Variants are written bare (`Start`, never `Msg.Start`).
- A parameter name is not in the pool and clashes with nothing. Nothing in the subset can use it.
- The keys of an app block are not names.
- A name is looked up by where it stands:

| Place | Must be | Otherwise |
|---|---|---|
| a type | `String`, `List`, `Effect` or an enum of the program | `unknown-type` |
| an expression | a variant of the program, `Print` or `Exit` | `unknown-name` |
| `update:` | a function of the program | `unknown-name` |
| `start:` | a variant of the program, `Print` or `Exit` (then section 8 applies) | `unknown-name` |
| `grants:` | `Console` | `unknown-grant` |

## 7. Types

A type is well formed when its name is a type with the right number of type arguments (one argument
for `List` and `Effect`, none for `String` and enums) and its argument, if any, is well formed. It is
tested from the outside in: the name (`unknown-type`), then the argument count
(`wrong-type-arguments`), then the argument. Both codes are reported at the type's name.

Two types are equal when they have the same name and equal arguments.

Nothing is inferred. Every expression is checked against an expected type; the expected type of a
function body is the function's result type. Each code is reported at the first token of the
expression it names.

| Expression | Checked against expected type E, in this order |
|---|---|
| STRING | E must be `String`, else `type-mismatch` |
| `[e1, ..., en]`, n ≥ 0 | E must be `List<T>`, else `type-mismatch`; then each `ei` against `T`, left to right |
| a variant `V` of enum `N`, with k arguments (bare means 0) | k must be 0, else `wrong-argument-count`; E must be `N`, else `type-mismatch` |
| `Exit`, with k arguments | k must be 0, else `wrong-argument-count`; E must be `Effect<T>` for some `T`, else `type-mismatch` |
| `Print`, with k arguments | k must be 1, else `wrong-argument-count`; E must be `Effect<T>` for some `T`, else `type-mismatch`; then the argument against `String` |
| any other UPPER | `unknown-name` |

## 8. Checking order and the app

A program that fits the grammar is checked in three steps. The first failed test gives the diagnostic.

1. **Declarations**, in source order: each definition name and, for an enum, each of its variant names
   after the enum's own name, is added to the pool (`duplicate-name`).
2. **App count**: no app is `no-app` (no position); a second app is `multiple-apps` at the second
   app's name.
3. **Definitions**, in source order:
   - enum: nothing more.
   - function: the parameter type is well formed, the result type is well formed, the body checks
     against the result type. A function is checked whether or not anything uses it.
   - app, in this order whatever the order of its entries:
     1. no key appears twice, else `duplicate-app-entry` at the second key;
     2. `start` is present, else `missing-start`; `update` is present, else `missing-update`;
        `grants` is present, else `missing-grants`; each at the app's name;
     3. the `update` value names a function, else `unknown-name`; that function's parameter type is
        an enum `M` of the program and its result type is exactly `List<Effect<M>>`, else
        `bad-update-signature`; both at the value;
     4. the `start` value is a known expression name, else `unknown-name`; it is a variant of `M`,
        else `bad-start`; both at the value;
     5. each grant, left to right, is `Console`, else `unknown-grant`; and has not appeared earlier
        in the list, else `duplicate-grant`; both at that grant.

**Decided (M1-06.3):** the app block names the first message with `start:`; a headless app without it
is rejected at check time. Every M1 app is headless.

An app has no state in M1: there is no `state:` entry and `update` takes the message only.

## 9. Running

### 9.1 Start

The runtime calls the function named by `update:` once, with the variant named by `start:`. No other
message is ever sent: no M1 effect produces one. The function returns its list of effects.

### 9.2 Effects

The runtime performs the returned effects one at a time, in list order. Before performing an effect it
tests the grant the effect needs (section 9.4).

- `Print(text)` writes the bytes of `text` and then one line feed (`0x0A`) to standard output. All of
  these bytes are handed to the operating system before the next effect is looked at: a short write
  is continued, an interrupted write is retried. Any other write error, or a write that accepts no
  bytes, is a failure (section 9.5).
- `Exit` ends the program at once with status 0. Effects after it in the list are not performed and
  not tested, and nothing is reported about them.

### 9.3 End

The program ends with status 0 and an empty standard error when `Exit` is performed, or when every
effect in the list has been performed and none was `Exit`. An empty list ends the program the same
way.

### 9.4 Missing grant

**Decided (M1-06.1):** an effect whose grant is not in the app's `grants` list is a trap. The effect is
not performed, the effects after it are dropped, and the program ends with status 3 after writing one
line to standard error:

```
<app>: effect <Effect> refused: grant <Grant> is missing
```

`<app>` is the name written after `app`, never the name of the executable. In M1 the only such line
is, for the app `light`:

```
light: effect Print refused: grant Console is missing
```

The test is made when the effect's turn comes, not before: `[Exit, Print("x")]` without `Console` ends
with status 0.

### 9.5 Failed write

**Decided (M1-06.2):** when `Print` cannot write, the program ends with status 3 after writing one line
to standard error. The effects after it are dropped. Bytes already written stay written.

```
<app>: effect Print failed: <reason>
```

| Cause | `<reason>` |
|---|---|
| the write fails with ENOSPC | `no space left on device` |
| the write fails with EPIPE | `broken pipe` |
| any other failure | `write error` |

The program never ends by a signal. With standard output on a pipe whose read end is closed, it ends
with status 3 and the `broken pipe` line whether it was started with SIGPIPE ignored or not.

### 9.6 Both back ends

The two lines above are fixed byte for byte, each ending with one line feed, so the interpreter and a
native executable agree on standard error as well as on standard output and status (M1-20). A failure
to write to standard error is ignored and changes no status.

Refused effects and failed writes are the only run-time errors a program of this subset can reach.
The status of a fault inside the runtime itself is set by the M1-14 document.

## 11. Case folders

A case is a folder `tests/cases-pending/<stage>/<name>/`, later `tests/cases/<stage>/<name>/`.
`<stage>` is `lex`, `parse`, `check` or `run`; `<name>` matches `[a-z0-9_]+`. A case folder holds
exactly these files and nothing else:

| File | In | Content, byte for byte |
|---|---|---|
| `main.paka` | every case but `lex/source_missing` | the source |
| `stdout` | an accept case | the expected standard output; may be empty |
| `status` | an accept case | the expected status in decimal digits, then one line feed: `0\n` or `3\n` |
| `reject` | a reject case | `main.paka:<line>:<col>: error[<code>]` then one line feed; for a code with no position, `main.paka: error[<code>]` then one line feed |

A case is an accept case (`stdout` and `status`) or a reject case (`reject`), never both. A folder
with neither, with only one of `stdout` and `status`, or with both kinds, fails.

The runner starts `paka run main.paka` with the case folder as working directory, so every
diagnostic path is `main.paka`. It walks stages and names in sorted order.

- An accept case passes when the standard output equals `stdout` byte for byte and the process exits
  with the status in `status`. Ending by a signal fails. Standard error is not compared by the case
  runner.
- A reject case passes when the status is 1, standard output is empty, and standard error is exactly
  one line that starts with the content of `reject` without its line feed, followed by `: ` and at
  least one more byte, and ends with its only line feed.

`lex`, `parse` and `check` hold only reject cases; `run` holds only accept cases. Accepting
`examples/light.paka` at the first three stages is tested against section 14 and by the unit tests of
M1-07, M1-09 and M1-10. `run/light/main.paka` is byte for byte `examples/light.paka`.

Every reject case fits the grammar up to its offending token, so the lex group passes with the lexer
alone (M1-08) and still passes when the parser and checker arrive.

Expectations are written by hand. No tool writes or rewrites them.

## 16. Choices made here

Neither GENESIS.md nor DECISIONS.md settles these. Each is provisional and gives the alternative that
was turned down.

1. **Bytes.** Only `0x20`–`0x7E` and line feed are allowed; tab, carriage return and non-ASCII bytes
   are `invalid-byte`, in strings too. Turned down: accepting tabs, CRLF line ends or UTF-8 in
   strings, which light.paka does not need.
2. **Positions.** Lines and columns start at 1 and columns count bytes. Turned down: counting
   characters, which cannot differ here because a non-ASCII byte is itself the error.
3. **Line feeds.** A line feed is plain white space; the whole program may stand on one line. Turned
   down: a line feed that ends an app entry or the body expression. The lasting rule belongs to M2-02
   and M4-47.
4. **One diagnostic.** A run reports the first problem only: lexical and syntax problems in source
   order, then the fixed order of section 8. Turned down: lexing the whole file before parsing (a
   `match` would then be reported as a stray `=`), and reporting several diagnostics.
5. **Code spelling.** Codes are lower-case words joined by hyphens, with `unsupported-` for what Paka
   has and M1 lacks. Turned down: numbered codes such as `E0007`.
6. **Strings.** No escapes and no `{` or `}`; the empty string is allowed. Turned down: defining
   `\n`, `\"` or interpolation now, which belongs to M2-03.
7. **Names.** ASCII letters, digits and underscore; the first letter's case separates UPPER from
   LOWER (as M2-02.3 rules), and a name cannot start with an underscore. Turned down: one kind of
   name with the meaning looked up.
8. **Keywords.** Only the six definition kinds and `match` are reserved. Turned down: reserving every
   word of the paper's samples (`inout`, `var`, `migrate`, ...) before M2 decides them.
9. **Functions.** Exactly one parameter and a result type; the body is one expression. Turned down:
   general parameter lists and functions without a result.
10. **Enums and lists.** One or more variants; a list may be empty. Turned down: exactly one variant
    and non-empty lists, which would each need a rule and a code of their own.
11. **One pool with the built-ins.** `String`, `List`, `Effect`, `Print`, `Exit` and `Console` are
    taken, so a program cannot declare them. Turned down: separate pools for types, values and
    grants. Loosening this later breaks no program.
12. **One app.** A file holds exactly one app. Turned down: several apps with one chosen by name on
    the command line.
13. **No state.** No `state:` entry; `update` takes only the message. Turned down: a state type with
    default values, which needs `type` definitions.
14. **App entries.** Any order, each once, and `grants:` is required even when empty. Turned down: a
    fixed order, and a missing `grants:` meaning no grants.
15. **The update function.** Its shape is exactly `(x: M) -> List<Effect<M>>` for an enum `M`.
    Turned down: allowing no result for an app that asks for nothing, as the paper's counter does.
16. **Exit.** `Exit` ends the program at once with status 0; effects after it in the list are dropped
    without a message. Turned down: rejecting a list with effects after `Exit`.
17. **No Exit.** A program whose effects are all performed and has nothing left to wait for ends with
    status 0. Turned down: status 3 with a line saying `Exit` was never asked for, and waiting for
    ever.
18. **Print.** The text and one line feed, written whole before the next effect is looked at.
    Turned down: buffering all output until the end, which would blame a failed write on no effect
    in particular.
19. **Run-time lines.** The two standard error lines are fixed byte for byte, start with the app's
    name and use three fixed reasons. Turned down: the executable's name, and the operating system's
    own error text. DECISIONS.md leaves the wording open; M1-20 needs both back ends to agree.
20. **Where "missing" is reported.** `missing-start`, `missing-update` and `missing-grants` point at
    the app's name; `no-app` has no position. Turned down: the closing brace and the end of the file.
21. **Case folders.** Fixed file names `main.paka`, `stdout`, `status`, `reject`; `reject` holds the
    start of the diagnostic line as the tool prints it. Turned down: one file with named fields, which
    the runner would have to parse.
22. **A case without a source.** `lex/source_missing` has no `main.paka`, to give `file-unreadable` a
    case. Turned down: leaving that code to M1-03's own test alone.
23. **Two more build codes.** `clang-failed` and `runtime-missing` are added beside `clang-missing`.
    Turned down: one code for every build failure.
