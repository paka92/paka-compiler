# Paka M1 subset

The language of milestone 1: exactly what `examples/light.paka` needs. Everything else is rejected
with a named code. Tasks M1-03 and M1-07 to M1-20 were built from this text and from the case folders
under `tests/cases/`.

Status: the language is defined by `spec/paka.md`, which replaces the language text of this file.
Still in force: the commands, streams and statuses (section 1), running (section 9), the diagnostic
codes (section 10; the lex and parse codes follow the reference), the case folders (section 11) and
the checks outside them (section 13). Sections 2 to 5 describe the M1 lexer and parser. The tool
now lexes and parses the full language of the reference, so those sections are history. Sections 6
to 8 and 16 describe the M1 checker, which the tool still follows; `unsupported-form` stands in for
what the build cannot yet emit, and the reference wins wherever they differ. Section 12 lists the M1
cases as first written and section 15 their coverage; the live set is `tests/cases/`, from which the
parser work removed or moved the cases the full grammar accepts. Section 14 still holds for the
lexer. The two M1 cases the reference turned into accept cases, `check/unknown_grant` and
`parse/variant_payload`, keep their folders and now hold the run expectation (section 11).

Rulings taken from DECISIONS.md are marked **decided**: M1-06.1 to M1-06.3, M1-14.5, M1-14.6, M2-15.7
and the M2-15 rule for a program without an app. What this spec had to settle on its own is listed in
section 16.

```
enum Msg { Start }

fn update(m: Msg) -> List<Effect<Msg>> {
  [Print("let there be light"), Exit]
}

app light {
  start:  Start
  update: update
  grants: [Console]
}
```

## 1. Commands, streams and statuses

| Command | Does |
|---|---|
| `paka run <file> [argument...]` | reads, checks and interprets the program; the arguments after the file go to the program (section 9.1) |
| `paka build <file> -o <output>` | reads and checks the program, then writes a native executable |

Both commands accept and reject the same programs with the same diagnostic. An executable written by
`paka build` gives the same standard output, standard error and status as `paka run` on its source,
when both are given the same arguments.

| Status | Meaning |
|---|---|
| 0 | the program performed `Exit` or `ExitWith(0)` (section 9.3); for `paka build`, the executable was written |
| 1 | a diagnostic was reported: the program was rejected or the tool failed |
| 2 | bad usage of the `paka` command (owned by M1-03), or the program was given the wrong number of arguments (section 9.1) |
| 3 | the program stopped: it ended without `Exit`, an effect was refused or an effect failed (sections 9.3 to 9.5) |
| 5 to 255 | the program performed `ExitWith` with that status (section 9.3) |
| 4 | the runtime itself failed (section 9.6); never an expected result |

A diagnostic is one line on standard error, ending with a newline:

```
path:line:col: error[code]: message
path: error[code]: message
```

- `path` is the file argument exactly as given on the command line, byte for byte; it need not be
  UTF-8.
- The second form is used only by the codes marked "no position" in section 10.
- `message` is at least one byte and holds no newline. Its wording is not fixed.
- A run reports at most one diagnostic, then exits with status 1. Standard output stays empty and the
  program does not start. `paka build` does not start clang. When it does, clang's own standard
  output and standard error are discarded.
- There are no warnings. An accepted program makes the tool write nothing of its own to either stream.
- When the diagnostic cannot be written to standard error, the failure is ignored: the tool does not
  panic and the status is still 1.

The program never reads standard input or the environment. Its command-line arguments are the ones
after the file (section 9.1).

## 2. Source text and positions

M1 lexer and parser, superseded: the tool follows `spec/paka.md` section 2.

- A program is one file. Its bytes are read as they are; there is no decoding step.
- Allowed bytes: `0x20` to `0x7E` and line feed `0x0A`. Any other byte anywhere, tab and carriage
  return included, is `invalid-byte` at that byte. It is found when the lexer reaches the byte, not
  by a scan of the file beforehand, so an earlier syntax error is reported instead (section 5).
- A line ends at a line feed. Lines are numbered from 1.
- Columns are numbered from 1 and count bytes: the column of a byte is 1 plus the number of bytes
  between the start of its line and it. Every byte before a reported position is ASCII, so this is
  also the character count.
- The position of a token is the position of its first byte.
- The end of the file is a token named END. Its position is the line and column the next byte would
  have: after a final line feed that is column 1 of the following line. In an empty file it is 1:1.
- A final line feed is optional.

## 3. Tokens

M1 lexer and parser, superseded: the tool follows `spec/paka.md` section 2.

Space and line feed separate tokens and mean nothing else. In M1 a line feed ends nothing; M2 changes
this (section 16, choice 3), so a program should keep each definition and each app entry on its own
line.

| Token | Spelling |
|---|---|
| keyword | `enum` `fn` `app` `type` `view` `example` `match` |
| UPPER | `[A-Z][A-Za-z0-9_]*` |
| LOWER | `[a-z][A-Za-z0-9_]*`, when it is not a keyword |
| STRING | `"`, then zero or more bytes from `0x20` to `0x7E` other than `"` `\` `{` `}`, then `"` |
| punctuation | `{` `}` `(` `)` `[` `]` `<` `>` `:` `,` `->` |
| END | end of file |

- A name takes the longest run of letters, digits and underscores. `enumerate` and `Match` are names.
- `>>` is two `>` tokens. There is no `>>` token.
- The value of a STRING is the bytes between its quotes, unchanged. There are no escapes.
- `type`, `view`, `example` and `match` are keywords only so that they can be rejected by name.

At the start of a token the lexer looks at the next byte, and one more where noted:

| Next bytes | Result |
|---|---|
| letter | name or keyword |
| `"` | string, scanned as below |
| one of `{ } ( ) [ ] < > : ,` | that token |
| `->` | that token |
| `//` | `unsupported-comment` at the first `/` |
| `??` | `unsupported-hole` at the first `?` |
| digit | `unsupported-integer` at the digit |
| a byte outside `0x20`–`0x7E` other than line feed | `invalid-byte` at the byte |
| anything else (`-`, `/`, `?`, `_`, `=`, `;`, `.`, `&`, ...) | `unexpected-character` at the byte |

After the opening quote of a string the lexer reads byte by byte. The first of these that it meets
decides:

| Byte | Result |
|---|---|
| `"` | the string ends |
| line feed, or end of file | `unterminated-string` at the opening quote |
| `\` | `unsupported-escape` at the `\` |
| `{` or `}` | `unsupported-interpolation` at that byte |
| a byte outside `0x20`–`0x7E` other than line feed | `invalid-byte` at that byte |

Lexing stops at the first lexical error. Section 5 says when it is the one reported.

## 4. Grammar

M1 lexer and parser, superseded: the tool follows `spec/paka.md` sections 3 and 4.

Quoted words are keywords or punctuation. `start`, `update` and `grants` are LOWER tokens with that
text; they are not keywords and may be used as names elsewhere.

```
program  = { enum_def | fn_def | app_def } END
enum_def = "enum" UPPER "{" UPPER { "," UPPER } "}"
fn_def   = "fn" LOWER "(" LOWER ":" type ")" "->" type "{" expr "}"
type     = UPPER [ "<" type ">" ]
expr     = STRING | list | UPPER [ "(" expr { "," expr } ")" ]
list     = "[" [ expr { "," expr } ] "]"
app_def  = "app" LOWER "{" { entry } "}"
entry    = start ":" UPPER
         | update ":" LOWER
         | grants ":" "[" [ UPPER { "," UPPER } ] "]"
```

- Definitions may come in any order and any number. Entries of an app may come in any order.
- A function has exactly one parameter and a result type. Its body is exactly one expression.
- An enum has one or more variants. Variants carry no payload.
- There are no trailing commas, and a call has at least one argument: `Exit()` is not in the grammar.

## 5. Syntax diagnostics

M1 lexer and parser, superseded: the tool follows `spec/paka.md` sections 4 and 12.

The tokens are matched against the grammar from the first one on. The offending token is the first
token T such that the tokens before T, followed by T, are not the start of any program of the grammar.
A lexical error counts as a token that fits nowhere. The diagnostic is chosen by the first line of
this table that applies, and its position is that of T (for a lexical error, the position section 3
gives):

| Offending token | Code |
|---|---|
| a lexical error | the lexical code of section 3 |
| keyword `type`, `view`, `example` or `match` | `unsupported-type`, `unsupported-view`, `unsupported-example`, `unsupported-match` |
| a LOWER where a call argument starts (right after the `(` or a `,` of a call), when the next token is `:` | `unsupported-labelled-argument` |
| a LOWER where an app entry starts, with text other than `start`, `update`, `grants` | `unsupported-app-entry` |
| a `(`, `[`, type `<` or function body `{` that fits, when 64 of them are already open | `nesting-too-deep` |
| anything else, END included | `unexpected-token` |

So a syntax error earlier in the file wins over a lexical error later in it, and the other way round.
Rules about letter case need no code of their own: `enum msg` is `unexpected-token` at `msg`.

The labelled-argument line looks one token ahead and at nothing else. In `Print(m;)` the token after
`m` is a lexical error, not `:`, so `m` is `unexpected-token`. A `name:` after the `[` or a `,` of a
list is `unexpected-token` too: only a call has arguments.

## 6. Names

M1 checker, still followed by the tool. The language rule is `spec/paka.md` sections 1 and 4.

Built-in names:

| Name | Kind | Detail |
|---|---|---|
| `String` | type | no type argument |
| `List` | type | one type argument |
| `Effect` | type | one type argument |
| `Print` | effect | one argument of type `String`; needs grant `Console` |
| `Exit` | effect | no argument; needs no grant |
| `Console` | grant | |

- Enum, function and app names, every variant name and the six built-in names share one pool. A name
  may be declared once in it. A second declaration is `duplicate-name` at the later name; the
  built-ins count as declared before the file.
- Variants are written bare (`Start`, never `Msg.Start`).
- A parameter name is not in the pool and clashes with nothing. Nothing in the subset can use it.
- The keys of an app block are not names.
- A name is looked up by where it stands:

| Place | Must be | Otherwise |
|---|---|---|
| a type | `String`, `List`, `Effect` or an enum of the program | `unknown-type` |
| an expression | a variant of the program, `Print` or `Exit` | `unknown-name` |
| `update:` | a function of the program | `unknown-name` |
| `start:` | a variant of the program, `Print` or `Exit` (then section 8 applies) | `unknown-name` |
| `grants:` | `Console` | `unknown-grant` |

## 7. Types

M1 checker, still followed by the tool. The language rule is `spec/paka.md` section 3.

A type is well formed when its name is a type with the right number of type arguments (one argument
for `List` and `Effect`, none for `String` and enums) and its argument, if any, is well formed. It is
tested from the outside in: the name (`unknown-type`), then the argument count
(`wrong-type-arguments`), then the argument. Both codes are reported at the type's name.

Two types are equal when they have the same name and equal arguments.

Nothing is inferred. Every expression is checked against an expected type; the expected type of a
function body is the function's result type. Each code is reported at the first token of the
expression it names.

| Expression | Checked against expected type E, in this order |
|---|---|
| STRING | E must be `String`, else `type-mismatch` |
| `[e1, ..., en]`, n ≥ 0 | E must be `List<T>`, else `type-mismatch`; then each `ei` against `T`, left to right |
| a variant `V` of enum `N`, with k arguments (bare means 0) | k must be 0, else `wrong-argument-count`; E must be `N`, else `type-mismatch` |
| `Exit`, with k arguments | k must be 0, else `wrong-argument-count`; E must be `Effect<T>` for some `T`, else `type-mismatch` |
| `Print`, with k arguments | k must be 1, else `wrong-argument-count`; E must be `Effect<T>` for some `T`, else `type-mismatch`; then the argument against `String` |
| any other UPPER | `unknown-name` |

## 8. Checking order and the app

M1 checker, still followed by the tool. The language rule is `spec/paka.md` section 10.

A program that fits the grammar is checked in four steps. The first failed test gives the diagnostic.

1. **Declarations**, in source order: each definition name and, for an enum, each of its variant names
   after the enum's own name, is added to the pool (`duplicate-name`).
2. **App count**: a second app is `multiple-apps` at the second app's name.
3. **Definitions**, in source order:
   - enum: nothing more.
   - function: the parameter type is well formed, the result type is well formed, the body checks
     against the result type. A function is checked whether or not anything uses it.
   - app, in this order whatever the order of its entries:
     1. no key appears twice, else `duplicate-app-entry` at the second key;
     2. `start` is present, else `missing-start`; `update` is present, else `missing-update`;
        `grants` is present, else `missing-grants`; each at the app's name;
     3. the `update` value names a function, else `unknown-name`; **decided (M2-15):** with a
        `state:` entry the function is `fn(s: inout S, m: M) -> List<Effect<M>>`, without one it
        is `fn(m: M) -> List<Effect<M>>`, `S` being the state type and `M` an enum type of the
        program, else `bad-update-signature`; both at the value. This test reads the types as
        written and does not look at the function's body. A `state:` value that is not a record type
        with a default on every field is `bad-state` at the value, tested before the `update`
        value;
     4. the `start` value is a known expression name, else `unknown-name`; it is a variant of `M`,
        else `bad-start`; both at the value;
     5. each grant, left to right, is `Console`, else `unknown-grant`; and has not appeared earlier
        in the list, else `duplicate-grant`; both at that grant.
4. **Something to run**: the program holds an app, else `no-app` (no position).

**Decided (M2-15):** a program with no app is not a check error: its definitions are checked first
and any fault in them is reported. `paka run` then refuses it with one line and status 1, and so
does `paka build`; M1 has no other command, so in M1 the refusal is the `no-app` diagnostic. More
than one app stays a check error.

**Decided (M1-06.3):** the app block names the first message with `start:`; a headless app without it
is rejected at check time. Every M1 app is headless.

An app has an optional state (M2-15): see `docs/decisions/M2-15.md` section 1.1. The M1 back end
builds only the stateless form (section 10, `unsupported-form`).

## 9. Running

### 9.1 Start

**Decided (M2-15):** the run is a loop over a queue of messages that holds, at the start, the variant
named by `start:` alone. The state, when the app has a `state:`, is built from the field defaults
once, before the first message. The loop takes the message at the front, calls the function named by
`update:` with the state (as `inout`) and the message, and performs the returned effects (section
9.2); when the queue is empty and no `Exit` was performed the program stops (section 9.3). No
effect of this milestone puts a message in the queue, so the loop runs once; the file effects do
(M2-37).

The words after the file on the command line (`paka run main.paka a b`, or `./light a b` for a built
program) fill the fields of the start variant by position, each field a `String`. The count must
equal the field count, else the program does not start: one line on standard error, status 2, and
nothing is written to standard output.

```
<app>: expected <n> argument(s) (<fields>), got <m>
<app>: argument <i> is not text
```

`argument` is singular for 1, plural otherwise; the field list and its parentheses are left out when
there are no fields (`light: expected 0 arguments, got 1`). The second line is for an argument that
is not valid UTF-8; `<i>` counts from 1.

### 9.2 Effects

The runtime performs the returned effects one at a time, in list order. Before performing an effect it
tests the grant the effect needs (section 9.4).

- `Print(text)` writes the bytes of `text` and then one line feed (`0x0A`) to file descriptor 1
  itself, not to a buffered standard-output stream of the host language (**decided**, M2-15 section
  1.6). The text and the line feed are one buffer, given to the operating system in one write:
  `Print("")` writes one byte. All of the buffer is handed over before the next effect is looked at:
  a short write is continued, an interrupted write is retried. Any other write error, or a write
  that accepts no bytes, is a failure (section 9.5). Nothing is held back, so there is nothing to
  flush when the program ends.
- `Exit` ends the program at once with status 0. Effects after it in the list are not performed and
  not tested, and nothing is reported about them.
- `ExitWith(n)` needs no grant. It ends the program at once with status `n` when `n` is 0 or
  5 to 255, like `Exit`; otherwise it is the stop of section 9.3.

### 9.3 End

The program ends with status 0 and an empty standard error when `Exit` or `ExitWith(0)` is performed,
and with status `n` and an empty standard error when `ExitWith(n)` is performed, `n` in 5 to 255.
Statuses 1 and 2 belong to the tool, 3 to stops and traps, 4 to the runtime's own failures (section
9.6).

An `ExitWith` whose argument is an `Int` literal outside 0 and 5 to 255 is the check error
`literal-out-of-range` at the literal. Any other `ExitWith(n)` with such an `n` is checked when it
is performed, and is the stop (status 3):

```
<app>: effect ExitWith failed: status <n> is not 0 or 5 to 255
```

**Decided (M2-15.7):** when every effect in the list has been performed and none was `Exit`, no
message is left and the program stops: it ends with status 3 after writing one line to standard
error. The effects already performed stay done. An empty list stops the program the same way.

```
<app>: ended without Exit
```

For the app `light` the line is `light: ended without Exit`.

### 9.4 Missing grant

**Decided (M1-06.1):** an effect whose grant is not in the app's `grants` list is a trap. The effect is
not performed, the effects after it are dropped, and the program ends with status 3 after writing one
line to standard error:

```
<app>: effect <Effect> refused: grant <Grant> is missing
```

`<app>` is the name written after `app`, never the name of the executable. In M1 the only such line
is, for the app `light`:

```
light: effect Print refused: grant Console is missing
```

The test is made when the effect's turn comes, not before: `[Exit, Print("x")]` without `Console` ends
with status 0.

### 9.5 Failed write

**Decided (M1-06.2):** when `Print` cannot write, the program ends with status 3 after writing one line
to standard error. The effects after it are dropped. Bytes already written stay written.

```
<app>: effect Print failed: <reason>
```

| Cause | `<reason>` |
|---|---|
| the write fails with ENOSPC | `no space left on device` |
| the write fails with EPIPE | `broken pipe` |
| any other failure the runtime is handed | `write error` |

Only the first two rows are guaranteed and tested (section 13): they are the failures both back ends
can produce in the same way. EDQUOT (a disk quota) gives the first row's reason too (M2-15). Because
`Print` writes to descriptor 1 itself, a standard output that is closed when the program starts is
a failed write (EBADF, `write error`), never a silent success; `paka run` cannot show this, since
the Rust start-up of the tool reopens a closed descriptor on `/dev/null`, so only a built program
is held to it.

The program never ends by SIGPIPE or SIGXFSZ. With standard output on a pipe whose read end is
closed, it ends with status 3 and the `broken pipe` line whether it was started with SIGPIPE
ignored or not; a write past a file-size limit is an ordinary failed write. **Decided (M1-14.5,
extended by M2-15):** the native runtime sets SIGPIPE and SIGXFSZ to ignored at its entry: the Rust
start-up does the first for `paka run`, but an executable whose `main` comes from the IR does not
get that start-up.

### 9.6 Both back ends

The three lines of sections 9.3 to 9.5 are fixed byte for byte, each ending with one line feed, so
the interpreter and a native executable agree on standard error as well as on standard output and
status (M1-20). The case runner compares standard error too (section 11). A failure to write to
standard error is ignored and changes no status.

Ending without `Exit`, a refused effect, a failed write, an `ExitWith` out of range and a wrong
number of arguments are the only stops a program can reach in this milestone.

**Decided (M1-14.6):** a fault inside the runtime itself, such as a panic or effect data it cannot
decode, ends the run with status 4 after one line on standard error:

```
<app>: internal error: <reason>
```

The M1-14 document owns this line and its reasons. Status 4 appears in no expectation, so it always
fails a case.

## 11. Case folders

A case is a folder `tests/cases/<stage>/<name>/`.
`<stage>` is `lex`, `parse`, `check` or `run`; `<name>` matches `[a-z0-9_]+`. A case folder holds
exactly these files and nothing else:

| File | In | Content, byte for byte |
|---|---|---|
| `main.paka` | every case | the source |
| `stdout` | an accept case | the expected standard output; may be empty |
| `status` | an accept case | the expected status in decimal digits, then one line feed: `0\n`, `2\n`, `3\n` or an `ExitWith` status such as `7\n` |
| `args` | an accept case, optional | the command-line arguments after `main.paka`, one per line, each ending with a line feed; a case without this file is run with none |
| `stderr` | an accept case, optional | the expected standard error; a case without this file expects an empty standard error |
| `reject` | a reject case | `main.paka:<line>:<col>: error[<code>]` then one line feed; for a code with no position, `main.paka: error[<code>]` then one line feed |

A case is an accept case (`stdout` and `status`, with or without `stderr`) or a reject case (`reject`
alone), never both. A folder without `main.paka`, with no expectation file, with only one of `stdout`
and `status`, with `stderr` beside `reject`, or with both kinds, fails.

The runner starts `paka run main.paka` with the case folder as working directory, so every
diagnostic path is `main.paka`. It walks stages and names in sorted order.

- An accept case passes when the standard output equals `stdout` byte for byte, the standard error
  equals `stderr` byte for byte (or is empty when the case has no `stderr` file), and the process
  exits with the status in `status`. Ending by a signal fails.
- A reject case passes when the status is 1, standard output is empty, and standard error is exactly
  one line that starts with the content of `reject` without its line feed, followed by `: ` and at
  least one more byte, and ends with its only line feed. Only the path, position and code are
  compared; the wording of the message is not.

`lex`, `parse` and `check` hold reject cases, and `run` holds accept cases; the two M1 cases named
above are accept cases that stay in `check` and `parse`, where M2-15 section 4 put them. A reject case
stands in the stage that finds its diagnostic: `lex` for a lexical code, `parse` for a code of the
section 5 table reported at a well-formed token, `check` for a code of section 8. Accepting
`examples/light.paka` at the first three stages is tested against section 14 and by the unit tests of
M1-07, M1-09 and M1-10. `run/light/main.paka` is byte for byte `examples/light.paka`.

Four more stages hold accept cases only, each with the files of an accept case, and name the
command the runner starts in place of `paka run main.paka` (M2-04, M2-06 section 1.6):

| Stage | Command | Checks |
|---|---|---|
| `check-text` | `paka check main.paka` | the diagnostic text, in `stderr`, and status 1 (or no output and status 0) |
| `check-json` | `paka check main.paka --json` | the same, as the JSON object |
| `examples` | `paka examples main.paka` | the entries in `stdout` and status 0, 3 or 1 |
| `run-interp` | `paka run main.paka` | accept cases only the interpreter runs until M4-40; `paka/tests/native.rs` skips them |

Every reject case fits the grammar up to its offending token, so the lex group passes with the lexer
alone (M1-08) and still passes when the parser and checker arrive.

Expectations are written by hand. No tool writes or rewrites them.

## 16. Choices made here

M1 choices. Where `spec/paka.md` says otherwise, it wins.

Each choice is provisional and gives the alternative that was turned down. DECISIONS.md M2-02 has
already ruled on four of them for M2: line feeds (3), names (7), keywords (8) and the one pool (11).
Choices 7 and 11 follow that ruling. Choices 3 and 8 are narrower in M1 and say where M1 differs
until M2. Neither GENESIS.md nor DECISIONS.md settles the others.

1. **Bytes.** Only `0x20`–`0x7E` and line feed are allowed; tab, carriage return and non-ASCII bytes
   are `invalid-byte`, in strings too. Turned down: accepting tabs, CRLF line ends or UTF-8 in
   strings, which light.paka does not need.
2. **Positions.** Lines and columns start at 1 and columns count bytes. Turned down: counting
   characters, which cannot differ here because a non-ASCII byte is itself the error.
3. **Line feeds.** In M1 a line feed is plain white space and the lexer makes no token for it. M2-02
   rules otherwise for M2: a newline ends a statement, and a line continues only inside an open `(`
   or `[` or after a trailing operator or comma. Until then M1 accepts some layouts M2 will not, such
   as two app entries on one line; no accept case uses one, so no M1 case changes when the M2 rule
   arrives. Turned down: building the M2 newline rule now, which needs a newline token and rules for
   statements that M1 does not have.
4. **One diagnostic.** A run reports the first problem only: lexical and syntax problems in source
   order, then the fixed order of section 8. Turned down: lexing the whole file before parsing (a
   `match` would then be reported as a stray `=`), and reporting several diagnostics.
5. **Code spelling.** Codes are lower-case words joined by hyphens, with `unsupported-` for what Paka
   has and M1 lacks. Turned down: numbered codes such as `E0007`.
6. **Strings.** No escapes and no `{` or `}`; the empty string is allowed. Turned down: defining
   `\n`, `\"` or interpolation now, which belongs to M2-03.
7. **Names.** ASCII letters, digits and underscore; the first letter's case separates UPPER from
   LOWER, as M2-02 rules. Added here: a name cannot start with an underscore, and wrong case is a
   plain `unexpected-token` with no fix offered. Turned down: one kind of name with the meaning
   looked up.
8. **Keywords.** M1 reserves only the six definition kinds and `match`. M2-02 rules that keywords
   are reserved everywhere, those kept for later milestones included, so M2 reserves more words and
   a lower-case name that M1 accepts (`let`, `migrate`, ...) can stop being one. No accept case uses
   such a name. Turned down: reserving words now whose list M2 has not yet written.
9. **Functions.** Exactly one parameter and a result type; the body is one expression. Turned down:
   general parameter lists and functions without a result.
10. **Enums and lists.** One or more variants; a list may be empty. Turned down: exactly one variant
    and non-empty lists, which would each need a rule and a code of their own.
11. **One pool with the built-ins.** As M2-02 rules, all definitions share one pool. Added here:
    `String`, `List`, `Effect`, `Print`, `Exit` and `Console` are in it, so a program cannot declare
    them, and the diagnostic points at the later name only. Turned down: separate pools for types,
    values and grants. Loosening this later breaks no program.
12. **One app.** A file holds exactly one app. Turned down: several apps with one chosen by name on
    the command line.
13. **No state.** No `state:` entry; `update` takes only the message. Turned down: a state type with
    default values, which needs `type` definitions.
14. **App entries.** Any order, each once, and `grants:` is required even when empty. Turned down: a
    fixed order, and a missing `grants:` meaning no grants.
15. **The update function.** Its shape is exactly `(x: M) -> List<Effect<M>>` for an enum `M`.
    Turned down: allowing no result for an app that asks for nothing, as the paper's counter does.
16. **Exit.** `Exit` ends the program at once with status 0; effects after it in the list are dropped
    without a message. Turned down: rejecting a list with effects after `Exit`.
17. **No Exit.** No longer a choice: M2-15.7 rules that a program with no message left and no `Exit`
    performed stops with the line `<app>: ended without Exit` and status 3 (section 9.3). The first
    draft ended it quietly with status 0. Left to this spec: the line is exactly that text and names
    no message.
18. **Print.** The text and one line feed as one buffer, written whole before the next effect is
    looked at. Turned down: buffering all output until the end, which would blame a failed write on
    no effect in particular; and writing the line feed separately, which gives a failed write two
    places to happen.
19. **Run-time lines.** The three standard error lines are fixed byte for byte, start with the app's
    name and use three fixed reasons, of which only `no space left on device` and `broken pipe` are
    guaranteed. A standard output that is closed or not writable at the start is outside M1. Turned
